# Windows 实机日检查清单

> 状态：v0.1（2026-11-05 起草）｜用途：把「待人工执行」的用例拆成可排期的动作
> 权威：判定点只在 T v1.12 与产品方案 v1.19；本文件不复制判定文本，只规定**在哪台机器上、按什么顺序、用什么手段**制造条件。
> 数据源：`docs/testing/用例覆盖映射表-v0.2.csv`（状态与缺口）、`docs/testing/用例执行台账-v0.1.csv`（判定）、`fixtures/corpus/manual-only.txt`（人工语料）。

## 1. 这份清单要解决的问题

台账里「待人工执行」的行，载体一栏统一写着「真人工（Windows 实机/受控环境）」，看起来像同一类事。实际上它们分成六组，其中**只有三组真的需要 Windows**：共享冲突语义、Windows 特色环境（OneDrive／配额卷／UNC）、NTFS 大小写折叠。另外两组（实现缺口、大输入实测）在 Linux 上就能推到底——它们是「功能没做完」或「数值没测」，不是「平台差异测不到」。

把这个区别写下来有两个用处：

1. 不在 Linux 上做无意义的等待——能推的先推，实机日只做复核；
2. 不把 Linux 的预跑当成验收结论。ADR-0051 的口径是明文禁止的：**待人工行的判定只能是「待人工执行」，Linux 预跑不得冒充**。本清单 §3、§4 里完成的任何一项，都不会改变映射表的 ⛔ 状态，只会减少实机日当天的工作量。

## 3. W5：Linux 先把数值测完

W5 的缺口不是「测不了」，是「没测」。数据集脚本、测量夹具、结果台账都已就绪，Linux 上跑完的数值可以直接进 `fixtures/bench/results.md`，实机日只剩按同一夹具重测一遍。

已测：

| 实例 | 场景 | 结果行 |
|---|---|---|
| `F01-EXE-05` | C-2 按字节分片（`f01 --target-bytes`） | R-04／R-05／R-06 |
| `F02-EXE-05` | C-2 按行数分片（`f02 --lines`，含行数预扫描） | R-07 |
| `F03-EXE-05` | C-2 按份数分片（`f03 --parts`，双遍读盘） | R-08 |
| `F10-EXE-05` | C-1 十万文件清单 | R-01／R-02／R-03 |

未测（Linux 可做，夹具已支持到「调参数即可」的程度）：

| 实例 | 需要补的 | 说明 |
|---|---|---|
| `C01-EXE-05` | C-2 档转码（GB18030→UTF-8） | 流式转码已随 ADR-0055 落地（源编码已知时 64 KiB 逐块），缺的是 2 GiB 档的数值；映射表缺口写「>10 MB 流式未做」已过期，见 §6 |
| `C02-EXE-05` | C-2 档换行符改写 | `LineEndingRewriter` 已是流式，缺数值 |
| `C03-EXE-05` | C-2 档查找替换 | plain／CSV 单元格路已流式（ADR-0057），regex 路仅在静态可算窗口内流式（ADR-0064），无界量词/锚点仍整段——测得的数值要按模式分别记 |

命令形状（以 F02 为例，其余同理）：

```bash
cargo build --release
python3 fixtures/bench/measure.py c2 --split lines --lines 3000000 --rss-limit-mib 1024
python3 fixtures/bench/measure.py c2 --split parts --parts 9 --rss-limit-mib 1024
```

`--rss-limit-mib` 是保险丝不是阈值：超限即 kill 并停测，不产出结果行（手册 §3）。测量产物在 `/tmp/batchdesk-bench/`，测后清理；数据集本地产物不入库。

## 4. W4：Linux 先把两项实现补上

这两条的缺口栏写的是「功能未实现」，不是「测不了」。它们在 Linux 上做完就是做完了——密码是 ZIP 格式层的事实，预览失效是前端状态机的事实，两者都不依赖 Windows 内核。

| 实例 | 缺什么 | 动契约要先写 ADR 的原因 | 做完后仍然要实机走一遍的部分 |
|---|---|---|---|
| `C10-EXE-04` | 加密压缩包的解压：给密码能解开，密码错要有明确错误而不是"条目损坏" | 密码不能进计划文件（计划会被存/导出/进模板），只能经执行期上下文传入；这与"apply 期与计划期同源"的既有纪律是一次显式例外，必须落纸 | 用户在真实对话框里输密码的路径（壳层 → 执行器） |
| `C15-PRE-04` | 改并发后旧预览失效：现在是"参数变了才失效"，并发度不在失效因子里 | 并发度是执行期参数，改它是否该让计划失效属于产品语义（方案 §7.3 的"参数变更"范围），不是纯实现选择 | 任务运行中改并发、再点执行的整条交互 |

两项都不在本轮完成范围内——都要先裁决（W4 的 ADR 议题：密码的传递通道与并发度的失效语义），再写代码。

## 5. W1：占用怎么造（以及为什么 Linux 替不了）

R3 判定点（TC §2 R3）：撤销时目标被占用／只读／已被第三方改动，要①给出明确失败原因且不清空映射、②不造成二次破坏、③提示满足三层结构。

制造 "占用" 的两种手段：

- **Excel/WPS 打开目标文件**（语料 E01 的定义方式）：最贴近用户报告的场景，也最容易被杀软和其他句柄干扰；
- **PowerShell 持句柄**：`[System.IO.File]::Open($p,'Open','Read','None')` 以 `FileShare.None` 打开，独占性最干净，适合批量跑 17 条时避免"Excel 没真占住"的假阳性。

为什么 Linux 不能代替：POSIX 下删除/改名打开中的文件是合法操作，进程持有 fd 时 unlink 只减少链接计数，文件要到最后一个句柄关闭才真正消失——所以在 Linux 上"占用中的文件无法撤销"这个条件根本造不出来，跑出来的绿是无意义的绿。只读半边（`chmod 0444`）已在 Linux 侧由语料 E03 覆盖并断言到执行期跳过与报告，不必重复。

## 6. 顺带修掉的两处文档漂移

映射表的「缺口」列有两处写在功能实现之前，功能做完后没回头改。本批已改（数据源是 `scripts/gen_case_map.py`，CSV 由它重生成）：

- `TC-C01-EXE-05`：原写「实现缺口：>10 MB 流式转码未做（整文件读入内存）」。ADR-0055（2026-11-03）已把 `TranscodeRewriter` 改成源编码已知时 64 KiB 逐块流式，现缺口只剩"2 GiB 档没测"。
- `TC-C03-EXE-05`：原写「界定不出的正则仍整段」——这句仍准确（ADR-0064 只覆盖静态可算窗口），但它把"实测未跑"和"实现边界"混在一格，实机日容易读成"要先做功能"。

状态都没变（仍是 ⛔ 待实机）：改的是「缺什么」，不是「能不能自动化」。

## 7. W2／W3：环境准备

| 组 | 需要的条件 | 怎么准备 | 失败时的常见假象 |
|---|---|---|---|
| OneDrive 占位（W2） | 文件在云端、本地只剩占位 | 对目标文件右键「释放空间」，确认图标变云朵；关闭"始终保留在此设备" | 一打开资源管理器就触发按需下载，占位消失→测到的是普通文件 |
| 配额卷（W2） | 写入必然失败的卷 | 小容量 U 盘，或用 `diskpart` 建 VHD 并设 NTFS 配额 | 配额只限制用户不限制卷；用管理员跑会绕过 |
| UNC 断线（W2） | 执行中断开网络共享 | 映射到另一台机的共享，执行到一半 `net use /delete` 或禁用网卡 | 断线后系统自动重连，任务"看起来没失败" |
| 大小写折叠（W3） | 真不敏感卷上的改名/撤销 | NTFS 默认不敏感；若要敏感目录对照，用 `fsutil file setCaseSensitiveInfo` | 在 WSL 的 ext4 上测——那不是 Windows 的折叠语义 |

## 8. 实机日的执行顺序

先做环境类（W2），因为它们的准备成本最高、且会牵动语料 R05/E01/E02/E04 四条人工语料的记录；再做批量占用（W1，17 条可以一次环境跑完，逐条只换目标文件）；然后 W3（1 条，需确认卷的折叠状态）；最后 W6（C-6 大集，最耗时）。

每条执行完的落点：

1. 用例结果 → 映射表状态列（⛔ → ✅ 或 ◐）＋「缺口／待办」列写实测结论；
2. 语料结果 → `fixtures/corpus/manual-results.md` 追加一行（R05／E01／E02／E04）；
3. 性能数值 → `fixtures/bench/results.md` 按手册 §4 追加；
4. 台账 → 重跑 `python3 scripts/run_case_ledger.py`（数字不手写，ADR-0051）；
5. 签署 → `docs/testing/验收签署模板-v0.2.md` 的对应表单。
