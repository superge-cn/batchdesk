## 1. 问题背景

TRACEABILITY 的 03 行长期挂着一句自我指控：**「layout/tables 待 UI 把手（侧栏不可拖宽、列表无列宽/排序，持久化没人能改的值是假绿）」**。核实现状，这个"假绿"比措辞更具体：

- 内核 `ui_state.rs` 早就有 `LayoutState.sidebar_width` 与 `TableState{column_widths, sort}`，`apply_patch` 的白名单也收这两节（`crates/kernel/src/ui_state.rs:50-90`）；
- 壳层 `setUiState` 是通用 patch，写这两节早就写得住（`src-tauri/src/lib.rs:719`）；
- 而 `web/src/lib/ipc/types.ts` 的 `UiState` **只声明了 `navigation`**，注释写着"layout/tables 由后续联动消费、现在透传即可"；`web/src/lib/uiState.ts` 里 layout/tables 的读写函数数量是 **0**；
- 更要命的是浏览器 mock：`mockGetUiState()` 返回体里**根本没有 layout/tables 两个键**——也就是说即使界面写了，Playwright 与探针这条链上读回来也是空的。这条链如果先接界面，会得到"界面改了、刷新就丢"的假象，而且只有在真桌面壳上才复现。

动因与 ADR-0072 同型：**后端能力一直在，界面一次都没调过**。

## 2. 候选与否决理由

| 候选 | 做法 | 结论 |
|---|---|---|
| A. clamp 上下界写在 TS 常量里 | `const SIDEBAR_MIN = 176` 之类直接进代码 | **否决**。宽度区间属视觉值，权威在 U／CSS；TS 里再存一份就是第二个权威，改 token 时 TS 不会跟着红 |
| B. clamp 交给壳层做 | 界面只上报期望宽度，Rust 侧裁 | **否决**。ADR-0065 把窗口几何放壳层，是因为**摆放窗口的是壳层**；侧栏与列宽的呈现者是渲染层，壳层裁完渲染层还得再问一次"那实际是多少" |
| C. 尺寸以 CSS 自定义属性为唯一权威，TS 只读 | token 落 `tokens.css`，TS 经 `getComputedStyle(:root)` 读取，读不到才退回同值常量 | **选定**。同 `VirtualList` 用 DOM 实测行高而不是在 TS 抄一份 CSS 数值的既有做法；U 没定义这些 token 时按 AGENTS 走「占位 token ＋ TODO」，不发明新视觉值 |
| D. 排序进内核（计划生成时就排序） | `plan_*` 输出按列排序的条目 | **否决**。排序是**视图态**：内核计划序决定派发顺序与跳过判定（方案 §7.1），改它等于改执行语义；而且计划 JSON 进 C18 幂等比较，多一个用户可调的序就永远对不齐 |
| E. 排序不进表单快照之外的任何状态 | 把 `tables` 并入「参数变更→旧计划失效」的快照 | **否决**。方案 §7.3 的"参数"指生成计划用的参数；调列宽/排序不该把用户的预览作废（ADR-0047 的入口阻断会误伤） |
| F. 一次改完所有表格（含任务表、C05 预览表） | 四处＋TaskHistory 全接 | **部分否决**。把手只建一处共享（`TableHead.tsx`），但任务表第四列是操作按钮、C05 预览是非虚拟小表，语义不同；本轮接三个真实大表站点，其余如实记缺口（§6） |

## 3. 决策

1. **尺寸的唯一权威是 CSS token**。新增 `--layout-sidebar-width/-min/-max`、`--resize-handle-width`、`--resize-step`、`--table-column-min/-max` 于 `web/src/styles/tokens.css`；`.glass-shell` 的第一轨由 `232px` 改为 `var(--layout-sidebar-width)`；`.row` 的三条轨道改为 `var(--col-N, <原默认>)`——**默认轨道只在这里出现一次**，没拖过的列完全保持现状视觉。TS 侧只允许"读 token"与"读 DOM 实测"，`SIDEBAR_MIN_FALLBACK` 等常量只是 jsdom（无布局、无样式表）下的兜底，与 token 同值，不是第二权威。
2. **U v1.3 没有这些 token，按 AGENTS 登记为占位值**，并开 [OQ-39](./../OPEN-QUESTIONS.md) 请产品/视觉裁决上下界终值；终值确定前不得把它当成设计结论写进其它文档。
3. **列宽与排序写 `UiState.tables[<表 id>]`，读改写一律"先并再写"**。内核 `apply_patch` 是顶层浅合并＝整节替换，只带一张表会把别的表换掉——这条语义现在由内核测试 `patch_accepts_table_widths_and_sort` 明确钉住，前端 `rememberColumnWidth`／`rememberSort` 负责合并（`web/src/lib/uiState.ts`）。
4. **表 id 是稳定标识，不是文案**：`table.c09.plan`、`table.c09.result`、`table.feature.<功能码>`。功能页共用同一张预览表，因此 23 个视图各留一份记录，换页不会把上一张表的宽度带过来。
   命名空间前缀 `table.` 不是审美选择：`check_locales.py` 第 ⑥ 项会把源码里形如 `<域名>.xxx` 的字符串当作文案 key 核对，而 `c09`／`feature` 正是它的域名表成员——最初直接写成 `c09.plan` 就被门禁判成"引用了不存在的 key"。表 id 与文案 key 是两个命名空间，撞车的一侧让路（改 id 前缀），**不是放宽门禁**。
5. **排序只重排界面渲染的数组**，`PlanDocument.entries` 与派发顺序不动；排序值不进表单快照，因此**排序不会作废计划**（负向断言在 `App.uiHandles.test.tsx`／`FeaturePages.table.test.tsx`）。排序口径取常见电子表格语义：同列翻转、换列回升序，**不提供"取消排序"第三态**——回到计划序由 §11.3 的重置入口负责，避免再发明一种状态。
6. **落盘防抖 300ms**（设计 03 §11.1 的"原子写、防抖"）：一次连续拖动或连按方向键只写一次盘；写失败静默，与 navigation 分节同口径（UiState 是可丢的本机状态）。
7. **键盘与鼠标两条路都要有把手**。拖拽走 Pointer Events；分隔符 `role="separator"`＋`tabIndex=0`＋方向键按 `--resize-step` 步进。只有鼠标就等于键盘用户没有把手。
8. **先修 mock 再接界面**：`mockGetUiState` 现在原样回读 `layout`/`tables`（返回副本），并加了独立断言文件 `web/src/lib/ipc/mock.uiState.test.ts` 钉住"写了能读回、不擦兄弟分节、重置清空"。这条链与壳层不同口径时，界面测试就是在测一条不存在的通路。

## 4. 代价与边界

- **恢复路径不做存在性校验**：启动读回的 `sidebarWidth` 只 clamp 后应用；列宽/排序直接生效，表结构变了（列 id 不存在）就是一条没人看得见的记录——本轮不引入"清理孤儿列宽"的机制，因为内核 `deny_unknown_fields` 已挡住字段级漂移，表 id 级的孤儿属可丢的本机状态（§11.1）。
- **jsdom 没有布局**：单元格实测宽度为 0 时把手从 `--table-column-min` 起步，保证键盘路径在测试与真实浏览器里都不断链；副作用是测试里的数值来自 token 而不是内容宽度，这是刻意的（断言的是链路，不是排版）。
- **占位尺寸未经视觉评审**：上下界终值待 OQ-39；若 U 终值不同，只需改 `tokens.css` 一处。
- **`layout` 只接了 `sidebarWidth`**：`sidebarCollapsed`、AI 面板宽度/开关、任务面板开关属 F15 与后续面板工作，界面仍无入口（不谎报成已接）。

## 6. 完成后仍欠

- **TC/T 无对应用例**：阶段 0 的 296 条实例里没有"列宽/排序/侧栏宽度"的判定点，映射表由 `scripts/gen_case_map.py` 从 TC 生成，开发代理不自行加实例编号。本批的断言是**实现级**证据，不构成用例级验收 → 提请人类在下次 TC 升版时补实例（AGENTS「何时停下来问人」）。
- **尺寸终值待裁决**：OQ-39。
- **未接把手的表格**：「任务与撤销」表**已于 2026-11-06 接列宽把手**（`table.tasks` 四列，鼠标＋方向键；**排序仍未接**——比较器要按 `TaskSummary` 的真实字段名写，没逐字段核实就凭记忆写属于禁止的补全式幻觉，这个决定钉成断言：接上排序时那条断言会红，逼着一起改台账）。C05 回滚/改名预览表（非虚拟小表）仍未接把手。
- **实机项**：拖拽手感、跨显示器 DPI 下的宽度稳定性属真 WebView/Windows 实机日，不在本轮证据范围内。

## 7. 补记（2026-11-06）：OQ-39 已裁

- **六个尺寸现值全部批准**（侧栏 176–384px、默认 232px 未变；列宽下限 88px、上限 640px；键盘步进 16px），  权威位置仍是 `web/src/styles/tokens.css` 一处；等 U 升版正式登记这组 token 后 OQ-39 关闭。
- **可拖语义取 A**：U §4.3-4「列宽稳定」判的是**因内容自动抖动**，用户显式拖宽不构成违反，故所有列都给把手。  被否决的两条备选记录在此——B（仅名称列可拖）会让状态列没有调宽入口；C（永远保留一个弹性列）是为极端态加规则。
- **登记不做**：`.row` 的默认轨道里 `--col-1` 与 `--col-2` 都是 `minmax(0,Nfr)`，即现状有**两列弹性**，  与 §4.3-4「名称列是唯一弹性列」的字面不符。这是本批之前就存在的偏差（把手只是让它可见，不是引入它）；  改它会重排 C09 与 23 功能页所有表格的默认排版、属视觉复核射程，用户裁决为登记不改，本篇 §6 以此为准。
