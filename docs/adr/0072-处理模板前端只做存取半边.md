## 1. 问题背景

C37 的后端一直是齐的：内核 `recipe.rs` 有 v1→v3 迁移与 `validate`、`strip_path_params`，平台 `ConfigStore` 有增删查改与导入导出，壳层注册了 `saveRecipe`／`getRecipe`／`listRecipes`／`deleteRecipe`／`exportRecipe`／`importRecipe` 六条命令。**前端一行调用都没有**——`web/src` 里除了 `SettingSource` 的一个字符串常量，没有任何 `Recipe` 痕迹。设计 12 §5 写着「侧栏入口『处理模板』；保存入口在预览/参数页；应用只回填参数并重新预览」，界面侧整块缺失。

真动手时撞到一个预先登记过的坑：**模板存的是动作，壳层路由用功能码**。

- `TemplateStep.kind` 是 `PlanAction`（`split`／`rename`／`csv-rows`／`edit-content`…）；
- 壳层 `planOperation` 按 `f01`…`c14` 分派，各自采集参数与校验都不同；
- 一对多：`split` = f01/f02/f03/f05、`edit-content` = c01/c02/c03、`csv-rows` = f08/f09。

这正是 [OQ-36](./../OPEN-QUESTIONS.md) 记的那条，状态是**待裁决**，并明确写着「裁决前不实现；`getRecipe`／`importRecipe`／模板 CRUD 不受影响，勿把它们误认为已具备 `loadRecipe`」。于是这一刀只能切一半：**存取、管理、导入导出可以做；把模板变成计划的 `loadRecipe` 不能做。**

顺带发现三处必须一起处理的细节：

1. **路径键表本身是错的**。`PATH_PARAM_KEYS` 里有 `source`——但 `source` 在本仓库是**源编码**（F04/F06/F07/F08/C01/C11–C14 的 `--source`），删它等于导入模板时把编码扔掉；而界面真用的 `file`／`files`／`output`／`manifest`／`list`／`archive`／`dir` **不在**表里，于是导入一份自家存的模板，绝对路径会原样留在参数里，违反不变量 13。
2. **保存路径不剔除**。`ConfigStore::save_recipe` 只 `validate()`（脚本键与结构），路径剔除只发生在**导入**（`migrate_recipe_value`）。也就是说界面存一次就带一次路径。
3. **六条命令从未进契约**。设计 01 §4.4 只列了配置/日志/授权，处理模板命令只在 `lib.rs` 里存在——前端一接，它就成了事实上的对外契约。

## 2. 决策

1. **前端范围＝存取半边**：模板库视图（列表／查看步骤／删除／导出／导入）＋功能页预览处的「存为处理模板」。**不做「一键套用」**：不给按钮、不给禁用按钮、不给 TODO 占位，页面顶部用横幅写明它卡在 OQ-36。理由：点了没反应比没有按钮更糟，而"看起来能跑"会把未裁决的缺口伪装成已完成。
2. **`kind` 取计划里实际出现的动作**（`PlanEntry.action`），不建「功能码→动作」的对照表。那张表正是 OQ-36 的一对多来源，写死了必漂移；计划是内核给的产物，动作就在里面。**一份计划出现多种动作时拒绝保存**（C07 的清单可能 move/copy 混排）——挑一个等于把另一部分语义悄悄丢掉。
3. **参数快照就是 `plan.params`**，界面**不再抄第二份路径键表**；剔除只在壳层 `saveRecipe`（新）与内核 `strip_path_params`（既有）做，判据留一处。
4. **路径键表按本仓库参数名的真实语义重写**：真路径（`file`／`files`／`sources`／`output`／`outputDir`／`root`／`roots`／`manifest`／`list`／`archive`／`dir`／`sourcesRoot`／`targetRoot`／`unclassifiedDir`…）入表；**`source`／`target` 不入表**（是编码）。只做精确小写匹配，所以 `targetBytes`／`targetEncoding` 这类不会被误伤。
5. **六条命令补进设计 01 §4.4.2**（v1.51），并写明 `loadRecipe` 未实现及其原因——契约不能只描述已实现的部分，否则下一个接手的人会以为模板能直接出计划。
6. **模板库是顶层视图**，不占功能码：`navCatalog` 的 `TopLevelView` 加 `templates`（与 `tasks`／`settings` 同级），侧栏 TAG 记 `TPL`。功能码三处相等性门禁（ADR-0067 那批）因此不受影响——它比的是 `[fc]\d\d`，顶层项本来就在比对之外。

## 3. 后果

- 落地：`web/src/TemplatesPage.tsx`（新）、`navCatalog` 加顶层项、`App` 接线、`FeaturePages` 预览处加保存表单、`lib/ipc` 加六条薄封装与 mock 夹具、`labels.tsx` 加动作文案映射（18 个 `PlanAction`）、双语 53 个 key。
- 内核：`PATH_PARAM_KEYS` 重写＋`RecipeDocumentV3::strip_paths()`；壳层 `saveRecipe` 落盘前调用它。验收 `recipe::tests::strip_path_params_drops_real_paths_and_keeps_encodings`、`strip_paths_covers_every_step_and_reports_each_key_once`（kernel 411→413）。
- 界面验收：`TemplatesPage.test.tsx` 4 项（列表动作显示中文而非 `split`、删除两段式、导入 E1007 只显示码位＋本地化摘要、导出文本框）、`FeaturePages.template.test.tsx` 3 项（动作取自计划条目且扩展名归一、混排动作拒绝保存、空计划禁用）、`App.navigation` 加一条「模板可达且没有假应用按钮」、Playwright `templates.spec.ts` 1 项（真实 Chromium 下同一条语义）。Vitest 73→81，Playwright 16→17。
- **代价**：模板库现在是个"存得进去、取不出来用"的库。这是**如实反映契约缺口**，不是疏忽——`loadRecipe` 一旦裁决，套用路径就是"回填参数 + `planOperation` + 强制重新预览"，界面已经就位（`paramsSnapshot` 与 `PlanAction` 都在手上）。
- **留给产品的三选一**（不替产品定）：① 模板 schema 升 v4，`TemplateStep` 增 `feature` 字段（迁移＋设计 03 升版＋导入校验同步）；② 约定 `paramsSnapshot` 必带 `kind`（不改 schema，把契约藏进参数）；③ `loadRecipe` 只出「动作级」通用计划、不区分功能（推翻"与 `planOperation` 同出口"）。三种都影响 schema 或命令面，属人类裁决。
