# 0070. UTF-16 分片每片写 BOM：靠前缀补写，不靠区间碰巧包含

- **状态**：已采纳
- **日期**：2026-11-05
- **决策者**：开发代理（K08 语料收口）
- **关联**：[方案 v1.19 §5.1/§5.3](../baseline/产品方案-v1.19.md)、[T v1.12 §3.2 K08](../baseline/功能测试方案与验收标准-T-v1.12.md)、[ADR-0015](./0015-F01分片计划与撤销语义.md)、[设计 01 v1.50 §5](../design/01-内核接口与IPC契约.md)

## 1. 问题背景

方案 §5.1 的 BOM 策略写死了两件事：UTF-8 只首片写 BOM；**UTF-16/UTF-32 因无 BOM 无法被识别，每片都必须写 BOM**。
F05（CSV 分割）一直是"源字节直通"——分片就是源文件的一段字节区间，只有首片碰巧包含文件开头那个 BOM，
第 2 片起是无 BOM 的 UTF-16，Excel 与任何解码器都会当乱码。K08（T v1.12 §3.2）钉的正是这条：
输入 UTF-16 带 BOM 的多行 CSV，预期"每片均写 BOM"。

此前的处理是**整类阻断**：`file_block` 见 UTF-16 就报 E3001「先走 C01 转码」。阻断是安全的，但把功能推给了用户，
而 K08 要求的是产品行为本身成立——所以 K08 的台账一直是 `partial`，缺口写着"分片后每片写 BOM 属 F05 输出策略，未实现"。

不做决定的代价是可量化的：24 条自动化语料永远差一条；用户拿 UTF-16 的 CSV 分片后，除首片外全部打不开。

## 2. 候选与结论

| 候选 | 一句话定义 | 结论 |
|---|---|---|
| A | 支持"转码分片"：解码 → 按目标编码重新计量 → 写出，每片自行编码并加 BOM | 否决（本轮）：这是完整转码切片，要重做 F01–F05 的分片计量口径（§5.1 要求按**输出侧**字节计），改动面远大于 K08 的需要，且属 ADR-0015 §6 明确留给后续切片的事 |
| B | 仍只做源字节直通，但**每片在区间之前补写一次源文件自己的 BOM** | **选用** |
| C | 什么都不做，维持 E3001 阻断 | 否决：K08 判定的就是"每片写 BOM"，阻断等于把判定推给用户，台账只能继续 partial |

## 3. 选择理由

**为什么 B 够用**：UTF-16 分片不需要换编码就能被识别——它缺的只是文件开头那 2 个字节。BOM 是自描述的，
每片原样带上源文件同一个 BOM，片内字节仍是源文件的连续区间（记录边界已由扫描期确定），语义与"直通"完全一致。

**为什么 A 现在不做**：转码分片要求"解码→按目标编码计量→写出"，一旦引入，分片大小基准、超长行判定、
`expected.size`、进度计量全都要按输出字节重算。把它塞进 K08 这一条语料，等于用一个语料的缺口撬动五个分片功能的计量口径——
顺序反了：先让"同一编码下的分片"正确，转码分片另立切片（ADR-0015 §6 的适用边界不变）。

**为什么 C 不行**：§5.1 已经规定了产品行为，实现缺失不能靠错误码长期遮住；而且用户手上的 UTF-16 CSV 并不是罕见输入
（Excel「Unicode 文本」导出就是它）。

实现上还有两个必须钉住的细节：

1. **扫描必须按码元投影**。UTF-16 的逗号、引号、CR、LF 在字节层被 NUL 隔开（`,` = `2C 00`），
   而且宽字符的高位字节可能**恰好等于**结构字符——「上」= U+4E0A 在 UTF-16LE 下是 `4E 0A`，
   按字节扫描会把记录从中间切断。故 `CsvRecordScanner::new_utf16` 把每个码元投影成"ASCII 保留、非 ASCII 置 0"的一字节骨架，
   再走同一状态机；**记录长度仍按源字节计**（每码元 2 字节），否则分片区间会算错。
2. **前缀只在需要时补**。表头区间从 0 起且含 BOM，保留表头时每片复制出的首段字节本来就是 BOM——再补一个就是双 BOM。
   所以"该片是否补写"由计划逐条判定（`PlanCsvSplit.shardBom`）：首个区间不从 0 起才补，且 `expected.size` 计入前缀。
   这也让"覆盖 BOM 判断"留在计划期（纯函数、可预览），执行层只做"有前缀就写"。

**无 BOM 的 UTF-16 仍阻断**：源文件没有 BOM 时，每片补什么形态（甚至是否该补）是猜测，且会改变源字节语义。
按"不静默猜测"的既有口径维持 E3001，提示先走 C01——这是本条决策的边界，不是遗漏。

## 4. 后果与退路

- **后果**：`FsAdapter::copy_ranges_atomic` 多一个 `prefix` 参数（默认实现返回 E5001，未实现适配器不会被静默降级）；
  `PlanCsvSplit` 多一个可选字段 `shardBom`（追加式，旧计划仍可反序列化，前端不认也不影响执行）；
  UTF-16 扫描多一条码元投影路径，F05 的 `kernel csv` 单测从 18 项增至 23 项。
- **后果（要长期接受的不便）**：UTF-16 与 UTF-8 的 BOM 规则不同——UTF-8 只首片写、UTF-16 每片写；
  这个差异源自"能否被识别"，不是风格选择，实现里注释写明，避免后来者"统一"掉。
- **退路**：转码分片落地时，`prefix` 参数会被"目标编码写出"取代，届时删掉 `shardBom` 并改写 `copy_ranges_atomic` 的语义即可，
  分片区间模型（`range` + `csv.header`）不需要动。若日后证明 UTF-16 无 BOM 源也应支持，需要新增"是否合成 BOM"的显式参数，
  属新的产品可见决策，走 §11.6，不在本篇范围内扩。
