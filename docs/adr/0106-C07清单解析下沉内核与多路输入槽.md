## 背景

A3-3 收口后，25 个计划入口里只剩 C07 是 `pending-wiring`：事实可采，但接线要解决
两件别的事——

1. **两份独立输入**：一份清单 CSV ＋ 一个源目录。此前 Web 侧只有单槽 `File[]`，
   清单和源目录的文件只能混在一个数组里。
2. **清单解析必须与内核同口径**：方案 §5.8 要求清单解析**编码感知**
   （UTF-8／UTF-8 BOM／GB18030 共存），并且要处理引号内换行、CRLF、两列校验。

查代码时发现第二件事的前提不成立：**同一段清单解析逻辑已经在 CLI
（`crates/cli/src/main.rs`）与桌面壳（`src-tauri/src/plan_manifest.rs`）各复制了一份**——
同样的 `csv_dedup_inspect` 调用、同样的 `record.len() < 2` 校验、同样的错误措辞。
Web 侧再写第三份，三份只要有一处不一致（分隔符、BOM、引号），用户就会看到
「桌面能识别、浏览器不能」。这类漂移不会报错，只会让同一条清单在两个形态里得出
不同的计划。

## 决策

### 1. 纯字节处理下沉 kernel（三形态共用一份实现）

新增 `kernel::c07::parse_manifest(data: &[u8], delimiter, source) -> Result<Vec<PlanC07Row>>`：

```
字节 → 编码（显式优先，否则检测）→ 解码 UTF-8 → 分隔符（显式优先，否则嗅探）
     → 记录切分（引号/CRLF/引号内换行）→ 两列校验（不足两列 → E1004，带行号）
```

符合不变量 1：不读盘、不取时钟、不读环境，纯函数。CLI、桌面壳、WASM 三个调用方
只保留各自环境的两件事——**把文件读成字节**、**采集逐行事实**（存在性／大小／目标占用）。

与既有口径一致的部分刻意保持不变：整份清单解析（清单很小，不设采样窗口）；
`has_header` 恒 false（首行即数据，C07 清单没有表头约定）；少于两列的行**拒绝**
而不是跳过（跳过会让用户以为该行已处理）。

### 2. `source`（清单编码）是必需入口，不是可选优化

实测（`crates/kernel/src/c07.rs` 的
`parse_manifest_reports_e3001_when_the_encoding_cannot_be_determined`）：

```
"年度报告0.docx,归档目录\n" × 12 行（GB18030，约 300 字节）
  → 检测结果：EUC-KR（候选集外）→ E3001「编码无法判定」
```

原因在检测器：UTF-8 严格校验失败后走 chardetng 统计判定，中英混排的短样本会被
猜成韩文编码。**而 C07 清单的内容正是文件名，中英混排是常态**——这不是理论边界，
是这类清单在三个形态里都会撞上的现实。

处理方式只有一条：**给用户显式指定编码的入口**，而不是在检测失败时自动猜 GB18030。
方案 §5.2 的置信度策略明确「中低置信必须由用户选择」，自动兜底等于把低置信结论
静默采用，与本项目一贯的静默偏差防线相反。

于是三形态各加一个参数（口径一致）：

| 形态 | 入口 | 缺省 |
|---|---|---|
| CLI | `batchdesk c07 --source <encoding>` | 空＝检测 |
| 桌面壳 | `ManifestParams.source` | 空＝检测 |
| Web | 表单字段 `source` ＋ WASM `parse_c07_manifest` 第三参数 | 空＝检测 |

### 3. Web 侧输入按字段名**分槽**

`PickedFiles = Readonly<Record<string, File[]>>`：C07 的清单进 `manifest` 槽、
源目录进 `sourceRoot` 槽；其余视图仍只有一份输入（槽名 `files`），由 `viaFiles`
摊平回 `File[]`，planner 签名不变。

**不把两类文件混在一个数组里**：混在一起就只能靠扩展名猜哪个是清单。猜错的后果是
拿源目录里某个 CSV 当清单解析——行数对得上、计划能出来，条目却全是另一回事。

`planWithFiles(caller, view, files, form)` 保留为单槽便捷形态（等价于
`planWithPickedInputs(..., { files }, ...)`），多槽视图必须走
`planWithPickedInputs`。

### 4. 字节型 WASM 通道（`BYTE_OPS`）

`parse_c07_manifest(data: &[u8], delimiter?, source?)` 的入参是原始字节，装不进
既有的 `{ op, payload: string }` 协议。三个备选：

| 方案 | 问题 |
|---|---|
| `Blob.text()` 后传字符串 | **错**：恒按 UTF-8 解，GB18030 清单会先被解成替换字符，内核再检测也救不回来 |
| base64 | 要引编解码依赖（Rust 侧新依赖须过 deny），且两侧各写一份 |
| 数字数组塞进 JSON | 5 万行清单 → 数 MB 的 `[1,2,3,...]` |
| **协议加一支：`bytes` 走结构化克隆** | 零依赖、零转换；代价是 worker 多一个分支 |

采用最后一支：`contract.ts` 单列 `BYTE_OPS = ["parse_c07_manifest"]`，`WasmCall`
增加 `{ op: ByteOp; payload: string; bytes: Uint8Array }`，worker 按 op 分派。
`planHandler` 仍只认 `plan_` 前缀，字节型入口不会被它误取。

### 5. 目标占用：如实标注为不支持，而不是「一定空闲」

WASM 的 `plan_c07` 对 `targetOccupied` 恒传 false：浏览器没有目标文件系统可查
（设计 02 §3.1：Web 不写用户磁盘）。后果是**计划里不会出现「目标已存在」冲突**，
条目的动作与源文件事实不受影响。

这是能力边界，不是「目标一定空闲」的断言，因此：

- 计划通道的注释写明（`planChannel.ts` 的 `planC07`）；
- 界面在 C07 的目标根字段给**浏览器专属提示**（`FieldSpec.webHintKey`，
  桌面形态仍走 `hintKey`——同一字段在两形态能力不同，提示不能共用一条）；
- 记入 TRACEABILITY 的缺口列。

## 边界与未决

- **清单大小无上限约束**：`parse_manifest` 整份读入内存（与 CLI/桌面既有口径一致）。
  超过 §13.10.2 内存建议档时应给强提示——三形态都尚未接入，记为缺口。
- **`targetOccupied` 恒 false**：见决策 5；等 Web 侧有目标文件系统（OPFS 执行器，
  设计 02 §3.1）后才有意义补。
- **Web 仍无执行器**：本条只让 C07 能出真计划，`apply`／`undo` 依旧缺 OPFS FsAdapter。
