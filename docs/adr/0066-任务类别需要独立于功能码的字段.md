# 0066. 任务类别需要独立于功能码的字段

- **状态**：已采纳（2026-11-05，设计 01 v1.49 §2.3）
- **日期**：2026-11-05
- **决策者**：开发代理（工程契约字段追加；不改产品行为，不改判定强度）
- **关联**：设计 01 §2.3（`TaskSummary`）、§7（Journal 撤销与「回滚为终态」）、设计 12 §...（任务与撤销视图）、
  [ADR-0052](./0052-取消处置的询问与保留语义.md)（取消后询问是否一并撤销）、[ADR-0039](./0039-C18-横切干跑收口与计划幂等.md)（任务 id 由 `derived_ulid` 确定性派生，没有可读前缀）、
  `src-tauri/src/tasks.rs`（`TaskJob`、`insert`、恢复路径）、`web/src/lib/ipc/types.ts`、`web/src/TaskHistory.tsx`

## 1. 问题

「任务与撤销」视图要区分**执行任务**与**回滚任务**，因为两条入口对回滚任务必然无效：

- `retryTask` 只接受 apply 任务，对回滚任务返回 E1002 `only failed apply tasks can be retried`；
- 回滚是终态（设计 01 §7、界面措辞「回滚为终态，不可二次回滚」），对回滚任务再点「撤销」没有意义。

界面的判据写成了 `task.kind !== "undo"`。实测：`TaskSummary.kind` 由
`src-tauri/src/tasks.rs` 的 `insert()` 填写，apply 取 `plan.plan.kind`，undo 取
`journal_plan_kind(plan_id)`——**两者都是被处理计划的功能码**（`f12`／`c09`…），
壳层从不发出字面量 `"undo"`。也就是说这两处判别是**死分支**，回滚任务照样拿到
「重试失败项」与「撤销」两个按钮，点了才被壳层拒。

为什么一直没被发现：浏览器 mock 的 `summary()` 把 `kind` 硬编码成 `"c09"`，而既有
Vitest 用例自己造了 `kind: "undo"` 的夹具——**测试测的是壳层不会发出的形状**；且那条
断言恰好被状态门禁间接满足（夹具状态是 `completed`，重试本来就只显示失败态），
所以把它换成真实数据后仍然全绿，直到补上「回滚部分失败」这条真实可达形态才红。

## 2. 候选与结论

| 议题 | 候选 | 结论与理由 |
|---|---|---|
| 判别放在哪 | a) 约定 undo 任务的 `kind` 写字面量 `"undo"`；b) 从 `taskId` 前缀推导；c) `TaskSummary` 追加独立字段 `job` | **c**。a 破坏契约里 `kind: OperationKind` 的语义（它是功能码，用于导航、日志与报障），而 `OperationKind` 带 `(string & {})` 逃逸口，类型层拦不住违约；b 不可行，任务 id 是 `derived_ulid` 种出来的 ULID，没有可读前缀（设计 01 §... C18 幂等契约）；c 只是追加字段，两个语义各自清楚 |
| 兼容旧快照 | a) 必填且不接受缺失；b) Rust 侧 `#[serde(default)]`＋恢复时以 `StoredJob` 重算 | **b**。S03 快照里缺 `job` 的旧任务仍能加载（缺省 Apply），而恢复路径本就知道 `StoredJob::Apply/Undo`，**以存储事实为准重算**比信任旧快照字段更稳（与 v1.46 补 `planId` 同一手法） |
| 强制力位置 | 界面隐藏入口即可？ | 界面只做显示／隐藏；放行与拒绝仍在壳层（`retryTask` 的 E1002 一字不改）。不变量 11：渲染层不承载强制力 |

## 3. 实现

- `src-tauri/src/tasks.rs`：新增 `enum TaskJob { Apply, Undo }`（`rename_all = "lowercase"`，`#[default] Apply`）；
  `TaskSummary.job` 带 `#[serde(default)]`；`insert()` 按 `StoredJob` 变体填 `job`；
  启动恢复循环里 `summary.job` 由 `persisted.job` 重算。
- `web/src/lib/ipc/types.ts`：`TaskJob` 类型 ＋ `TaskSummary.job`（契约侧必填，wire 始终带）。
- `web/src/TaskHistory.tsx`：重试与二次撤销的门禁改为 `task.job !== "undo"`。
- `web/src/lib/ipc/mock.ts`：`MockTask` 保留 `kind: TaskJob` 并新增 `planKind`，`summary()` 如实填
  `kind = planKind`、`job = kind`（此前 `kind` 硬编码 `"c09"`，与真实壳层同形但缺判别字段）。

## 4. 已接受的坑与边界

- **旧快照的中断回滚任务**：靠恢复路径重算才正确；若将来有人改成直接信任快照里的 `job`，
  升级前写入的快照会把回滚任务当执行任务（变异证据见 §5）。
- **不改变任何可达行为**：用户仍可从功能页或 C09 工作台对**执行计划**发起撤销；被取消的只是
  「对一次回滚再回滚」这条本就无效的入口。
- **老壳层 ＋ 新界面**：`job` 缺失时 TS 类型要求它在，运行时读到 `undefined` 会让门禁判为「非 undo」，
  即退回本次修复前的行为（多给按钮），不会崩。真实桌面壳始终发出该字段。
- 本字段只用于列表判别；`TaskDoneEvent.kind` 的既有取值（`apply`／`undo`）保持不变，两处语义此后各自有名。
