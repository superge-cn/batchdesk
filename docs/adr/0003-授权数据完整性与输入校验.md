# 0003. 授权数据完整性与输入校验

- **状态**：已采纳
- **日期**：2026-10-27
- **决策者**：项目负责人（按 D-R4 决策）
- **关联**：方案 §8.2（试用模式与防时钟回拨）、§8.3（离线激活码）、§8.4（设备绑定）、§8.5（本地防篡改）、§8.8（许可证结构与状态机）、§8.9（校验点与失败提示）、§9.6／§9.7（日志与隐私）、§12.4（LicenseService）；ADR-0002（二进制加固与混淆边界）、ADR-0001（工作区结构）

## 1. 问题背景

方案第 8 节已定"签名不可伪造""篡改命中降级 G0"等原则，但**"哪些数据被签名覆盖、畸形输入怎么处理"没有工程约定**。这两类缺陷的共同特点是功能测试全绿却留下入口：**漏签一个字段即可单独改它**（如把试用起算时间往后挪），**未做类型与规模校验的输入即可让解析在启动路径上崩溃或静默放行**。

触发条件：授权模块尚未开工（`crates/kernel` 的判定与复核路径、`src-tauri` 的注入层均未建立），现在定义覆盖范围与校验策略成本最低。一旦签发端（服务端）与客户端各自定型序列化方式，再统一要同时改两端与已发出的许可证。

不做决定的代价：签名覆盖范围随字段演进无声漂移；两端序列化不一致导致验签靠"碰巧通过"。

## 2. 候选与结论

| 候选 | 一句话定义 | 结论 |
|---|---|---|
| A 只做验签 | 有签名即视为可信，覆盖范围与输入校验不设约定 | 否决：漏签字段可被单独篡改；畸形输入致启动崩溃或静默放行 |
| **B 显式定义"签名覆盖范围＋输入校验＋状态完整性"** | 凡参与授权判定的数据都必须被签名覆盖或被显式校验，未被覆盖的一律视为不可信 | **选用** |
| C 多锚持久化＋更强的本地对抗 | 把试用状态分散写入多个隐蔽位置，并叠加反调试 | 否决（理由见下） |

## 3. 选择理由

**A 为什么不够好**：签名只保证"被签的那串没被改"，不保证"该签的都签了"。授权判定同时依赖载荷（§8.8 字段表）与本地状态（§8.2 的试用起算／最近运行／累计天数）；后者若不在签名覆盖内，改本地文件即可延长试用。同理，激活码与许可证文件是**外部输入**，不做规模与结构校验，畸形数据会在解析路径上二选一地失败——崩溃（启动 DoS），或被容错逻辑吞掉而 **fail-open**。

**C 为什么否决**：把状态分散写入多个隐蔽位置（注册表、WMI 类实例、事件日志、备用数据流），与三条既定约束冲突——① §9.7 要求本地数据位置可见且可一键清理；② §8.5 明确不采取激烈手段、不伤害正常用户；③ 隐蔽持久化是杀软与合规审查的高危特征（§11.2 已单列"杀软误报"风险）。而本产品试用期为 14 天全功能＋5 次单项（§8.2；次数由 3 调为 5 见方案 §11.6-23），**重置收益远小于上述代价**。对抗强度让位于可交付性与用户信任，与 §8.0"成本策略、接受残余盗版"的立场一致。

**B 的落地约束**（字段与算法以实现为准，以下为决策方向）：

- 签名的目标串必须**确定性序列化**（字段顺序与编码固定）：签发端（服务端）与验签端（客户端）遵循同一规范，**禁止依赖语言默认的映射／结构序列化顺序**；
- **用于授权判定的本地状态必须整体被签名（或 HMAC）覆盖**：§8.2 的试用起算／最近运行／累计天数，以及后续任何新增的判定状态——**新增状态字段必须同步扩展签名范围**；
- **完整性保护的基线自身必须被签名覆盖**（哈希／校验清单若不被签名，改清单即可放行）；
- 外部输入（激活码、许可证文件、本地状态）必须做**结构与规模校验**：大小上限、字段类型、结构版本、字段白名单；畸形一律按"未授权"处理，**不得崩溃、不得 fail-open**；
- 验签链包含**产品代号／SKU 匹配**（§8.3 载荷已含该字段，用于防跨产品混用）；
- **设备指纹采集不足时拒绝生成指纹**（不得退化为通用哈希）——这是 §8.4 匹配算法的前提；
- 本地审计事件中的**设备指纹与许可证 ID 只记前缀**（对齐 §9.6／§9.7 的脱敏口径）。

**异常处置分流**（落地 §8.5 的既定行为与其恢复通道）：

- **疑似篡改**（签名或完整性校验失败）→ 降级 G0 并记录审计（§8.5 既定）；
- **非篡改的损坏／不可读** → 不静默放行：已激活用户走许可证恢复／重新激活通道（§8.5 已定义的通道），试用用户降级至免费版并提示恢复入口；
- 两条路径**都禁止因数据异常而延长或重启试用期**——否则"损坏本地文件"即成为重置手段。

## 4. 后果与退路

- **后果**：① 签名覆盖范围与字段白名单成为**演进约束**——新增授权字段或判定状态时必须同步签发端与验签端，漏改即验签失败（fail-closed：宁可误拒，不得误放）；② 测试必须覆盖"被签字段被改动"与"畸形输入"两类用例，不能只测正常路径；③ 客户端与服务端的序列化规范由本 ADR 约束，任一端的实现偏差是缺陷，不是"环境差异"。
- **退路**：若 14 天试用＋5 次单项的实测重置率超出预期，再评估加强（联网兜底或额外锚点）——**须先推翻本节对候选 C 的否决**，并按方案 §11.6 评估对 §9.7 承诺的影响。
- **待办挂账**（不阻塞本决策生效）：① §9.7"一键清理"不含授权／试用状态、§8.2 与 §8.5 的异常处置口径，需走**方案 §11.6** 回填措辞；② 发行产物的加固断言见 ADR-0002；③ 服务端签发工具的序列化实现须与客户端对齐，待签发工具开工时同步验证。
