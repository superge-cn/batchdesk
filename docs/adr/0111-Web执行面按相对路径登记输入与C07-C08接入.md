# 0111. Web 执行面按相对路径登记输入：C07/C08 接入

- 日期：2026-11-22
- 状态：**已采纳**（A3-9 落地：`stagedPath` 对目录选择类视图按「源根/相对路径」登记输入、`stageInputs` 按槽筛选；执行档位从 16 个视图扩到 **18 个**）
- 相关：[ADR-0110](./0110-Web计划输出路径派生与CSV族执行面.md)（此前把 C07 记作 `relative-paths`、把 C08 记作 `port-missing`）、[ADR-0108](./0108-Web执行沙箱与产物下载.md)（沙箱执行）、[ADR-0104](./0104-Web计划通道真计划不配假执行.md)（C02 纵切）、设计 02 §3.1.1

## 背景

A3-8 收口时，执行档位剩三个视图：C07 与 C08 记为「相对路径没进 staging」和「缺 `ArchiveService`」，C10 记为「缺 `ArchiveService`」。

A3-9 逐个核对执行臂实际调用的内核路径，发现 C08 的归类是**凭印象的错误**：

- `plan_c08` 产出的条目动作是 `PlanAction::Move`（`crates/kernel/src/c08.rs`），执行走通用执行器的 move 分支，**不需要** `ArchiveService`；
- C08 与 C07 缺的是同一件事：计划的源是 `sourceRoot/相对路径`，而 staging 只登记裸文件名。

浏览器里 `sourceRoot` 字段是 `kind: "directory"` 的目录选择器，没有文本值可填；`planC07`/`planC08` 因此取**所选目录名**作源根（`pickedRootName`），计划里的源就是 `目录名/相对路径`。而 `stageInputs` 把所有选中文件按 `file.name` 登记进沙箱——键与计划的源永远对不上，执行器逐条报 `E2001 file or directory does not exist`。

## 决策

### 1. staging 键按视图的**计划源口径**分两类

| 视图族 | 计划的源事实 | staging 键 |
|---|---|---|
| F01–F09、C01–C03、C11–C14 | `displayPath(file.name)`（普通多选，无目录层级） | `file.name` |
| C07、C08（目录选择） | `join_root(sourceRoot, 相对路径)`，`sourceRoot`＝所选目录名 | `<根名>/<相对路径>` |

判据是「计划里的 `source` 字符串是什么」，不是「用户怎么选的」。这两者本来应当一致；不一致时以计划为准——执行器只认计划。

### 2. 目录选择类视图只登记**源目录**槽

C07 有两份独立输入（`manifest` 与 `sourceRoot`），但清单只参与**计划**：`parse_c07_manifest` 已在计划期把清单解析成行，执行时不需要清单文件出现在沙箱里。把清单也 stage 进去会多一个可能与源目录同名的条目（`清单.csv`），对执行毫无用处。

`STAGED_SLOTS` 因此只对 C07 声明 `["sourceRoot"]`（C08 同形声明，虽然它当前只有一槽——写明是为了「以后加槽不会悄悄把新槽也 stage 进去」）。

### 3. 普通多选给目录类视图时先拒绝

`stagedPath` 若拿不到 `webkitRelativePath`（普通多选），抛 `E1001`，**不**拿裸文件名凑数——凑出来的键与计划的源永远对不上，结果会是「每条都源缺失」这种看着像内核故障的假象。这条与 `planC08` 的既有校验（无相对路径即 `E1001`）同口径。

### 4. `webStagedFiles` 同时供界面算建议档

§13.10.2 的建议档按「执行期真正读进沙箱的文件」算，不按「用户选了什么」算。C07 的清单不进沙箱，因此不计入总量。界面与通道共用 `webStagedFiles`，避免两处各写一份筛选规则。

### 5. 档位表删掉不再存在的 `relative-paths` 与死条目 F10

- `relative-paths` 一档随本次修复从 `WebApplyGap` 删除（A3-8 的同一纪律：枚举里不留永不出现的值）；
- F10 在 `WEB_APPLY_GAPS` 里的 `port-missing` 是**死条目**：F10 的计划档位是 `unsupported`（`directory-walk`），永远走不到执行。一并删除。

执行档位因此是 **18 native**（F01–F09、C01–C03、C07、C08、C11–C14）/ **1 unsupported**（C10，`port-missing`）。

## 被否的方案

- **给前端加一个「把相对路径拼进计划」的开关**：等于让前端决定计划里的源路径，与 `planC0X` 的「计划事实由内核给定」冲突；且 staging 与计划仍可能各拼一套。
- **在执行器里按文件名后缀模糊匹配源**：`sub/a.txt` 与 `a.txt` 会互相顶替，静默匹配到错的文件比报错更危险（与 A3-3 拒绝扁平文件名匹配同一理由）。
- **为 C08 装配 `ArchiveService`**：C08 的动作是 move，装配端口是给不存在的依赖加实现——先查端口在哪，再决定要不要装配。

## 后果

- **好的**：C07（清单驱动移动/复制）与 C08（规则归档）在浏览器里能真执行、真出产物、真撤销；两族的源都是相对路径，因此这条口径对将来任何「整目录选择」的视图都适用。
- **代价**：`stagedPath` 从「一个字段」变成「按视图分派」，新增目录类视图时必须同时在 `RELATIVE_ROOT_VIEWS` 与 `STAGED_SLOTS` 登记——两处都由档位用例兜底（档位是 native 但没登记相对路径口径时，staging 用例会对不上）。
- **仍未解决**：C10 需要真正的 ZIP 编解码端口（`ArchiveService` 在 Web 侧没有实现）；F10 的计划侧本身不可用（无目录树），执行面无从谈起。

## 推翻条件

若浏览器支持把「目录授权＋目录树遍历」交给 Web（File System Access API 的 `showDirectoryPicker` + 递归枚举，或 OPFS 落盘），源根不再是「所选目录名」而是真实目录句柄，`RELATIVE_ROOT_VIEWS` 的字符串拼接要改为句柄相对路径；届时另开 ADR 推翻本文第 1、3 条。
