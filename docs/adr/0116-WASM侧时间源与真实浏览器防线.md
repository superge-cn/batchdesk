# ADR-0116：WASM 侧的时间源与「真实浏览器才算数」的防线

- 状态：已采纳·A3-15 落地（2026-11-23）
- 相关：ADR-0115（OPFS 落盘：本 ADR 的 e2e 用例由它引出）、ADR-0104（Web 计划通道）、设计 02 §3.1／§3.2、设计 04（`MemoryFs`）
- 影响范围：`crates/wasm/Cargo.toml`（`js-sys`，仅 wasm32 target）、`crates/wasm/src/lib.rs`（`epoch_millis`＋`ulid_like_id`）、`web/e2e/browser-storage.spec.ts`（新增真 WASM 用例）

## 1. 背景：一个从 A2 起就存在、测试全绿却浏览器必崩的 P0

A3-15 为验证 OPFS 落盘（ADR-0115）加了一条**真执行**的 e2e：在真实 Chromium 里选文件 → 生成 C02 计划 → 执行 → 检查 OPFS。它第一次跑就红了：

```
E0000 · wasm plan call failed
```

在 Worker 里打真实错误后得到：

```
[wasm-error] plan_c02 RuntimeError: unreachable
```

根因在 `crates/wasm/src/lib.rs` 的 `ulid_like_id()`：

```rust
let since_epoch = std::time::SystemTime::now()      // ← wasm32 上直接 panic
    .duration_since(std::time::UNIX_EPOCH)
    .unwrap_or_default();
```

`std::time::SystemTime::now()` 在 `wasm32-unknown-unknown` 上**没有实现**（std 该目标没有时钟），调用即 `unreachable`。而 `ulid_like_id()` 被 **28 个 plan 入口**共用——也就是说：**从 A2 阶段起，Web 侧只要真的选了文件、真的走到 WASM，任何一个计划入口都会崩**。

### 为什么三道测试都没抓到

| 测试 | 为什么抓不到 |
|---|---|
| Rust native 测试（`cargo test --workspace`，含 `export_surface`） | 跑在 native 目标，`SystemTime::now()` 正常 |
| vitest（jsdom） | `lib/wasm/client.ts` 被 mock 成 `vi.fn()`，**一行 WASM 都没执行** |
| Playwright e2e（A3-14 之前） | 全部走 `mock IPC`：`FeaturePages` 只在 `pickedFiles.length > 0` 时才走 WASM，而既有用例只 `fill()` 文本字段、不选文件 |

三道防线各自成立，合起来留了一个**全空的交叉区**：`wasm32 运行时 × 真实浏览器 × 真的调 WASM`。

## 2. 决策

### 2.1 wasm32 的时间源走 JS 的 `Date.now()`

```rust
#[cfg(target_arch = "wasm32")]
fn epoch_millis() -> u128 {
    js_sys::Date::now() as u128
}

#[cfg(not(target_arch = "wasm32"))]
fn epoch_millis() -> u128 {
    std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)
        .map(|elapsed| elapsed.as_millis())
        .unwrap_or(0)
}
```

`ulid_like_id()` 改用它；熵源从「纳秒＋计数器」改为「毫秒＋计数器」，唯一性由单调计数器保证（同一毫秒内多次调用不撞）。

`js-sys` 只声明在 `[target.'cfg(target_arch = "wasm32")'.dependencies]`——native 构建的依赖树不变。它是 wasm-bindgen 官方 crate（MIT／Apache-2.0，在 `deny.toml` 白名单内），且 `wasm-bindgen` 生态本就把 `js-sys` 作为传递依赖拉进树里，本次只是提为直接依赖。

### 2.2 防线放在 e2e，不放在语料

AGENTS.md 要求 P0/P1 挂语料。**这里不适用**：语料框架（`fixtures/corpus`）是「输入样本 → native 上跑 kernel 计划/执行」的回归，而本缺陷只在 **wasm32 运行时**出现，语料跑在 native 上永远是绿的——挂一条语料只会制造「已覆盖」的假象。

对应的防线是 `web/e2e/browser-storage.spec.ts` 的第二条用例：

> 真实 Chromium → 选文件（`setInputFiles`，`pickedFiles.length > 0` 强制走 WASM）→ 计划预览出现 → 执行 → 产物落 OPFS。

它同时钉住三件事：真 WASM 能跑、计划入口不 panic、产物落盘链路端到端可用。CI 的 web job 跑 `pnpm test:e2e`，这条会自动执行。

### 2.3 同类陷阱的通用判据

**凡是「适配层/壳层」提供的能力，都要问一句：这个 API 在目标运行时存在吗？**

| 能力 | native | wasm32 | 处置 |
|---|---|---|---|
| 时钟 | `SystemTime` | **没有**（panic） | 本 ADR：走 `js_sys::Date` |
| 文件系统 | `std::fs` | 没有 | `MemoryFs`（ADR-0108） |
| 线程 | 有 | 单线程 | 不用（`AtomicU64` 计数器无锁即可） |
| 熵 | `getrandom` | **没有**（需 `wasm-bindgen` feature） | 用 `Date.now()`＋计数器做熵源（本 ADR） |

### 2.4 防线横向铺开：六个族各一条真 WASM 用例

修完时间源之后，`web/e2e/real-wasm.spec.ts` 把真 WASM 铺到**成本最高、彼此不共享代码**的六个族——任何一族在 wasm 里不可用，都会在该族的用例上红：

| 视图 | 走的 wasm 路径 | 用例断言 |
|---|---|---|
| C02 换行转换（在 `browser-storage.spec.ts`） | `LineEndingRewriter` ＋ 执行后 flush | 计划出得来、产物落 OPFS |
| C10 解压 | 中央目录解析（TS）→ `plan_c10` → `MemoryArchiveService::extract_entry`（zip 解码） | 两层目录按层级还原、产物点名 |
| F10 目录清单 | `stage_dirs`／`stage_listing` → `MemoryDirectoryLister`（BOM CSV） | 产物 `素材.csv` 出现 |
| F12 批量改名 | 目录第一层条目 → `plan_f12`（前端 ULID）→ `rename` | 产物是新名字 |
| C07 清单移动 | 字节型 `parse_c07_manifest` → `plan_c07` → `move` | 产物落在 `目标根/子目录/名字` |
| C11 CSV 去重 | `csv_merge` 事实 → `plan_c11` → `csv-dedup` | 产物 `rows.csv` 出现 |

**结果**：五条新用例全绿，**没有发现第二个 P0**——说明时间源是这一轮唯一的 wasm32 运行时缺口。但这不改变结论：**验证过 ≠ 不会再坏**，这道防线的价值在于「下次谁改坏了某一族的 wasm 路径，CI 会红」。

**覆盖边界（如实）**：这些用例不覆盖全部 22 个可执行视图，只覆盖六个**动作族**。同一族内其余视图共用同一段执行臂代码（例如 C12–C14 与 C11 同走 `csv-*`），风险已从「未知」降为「可接受」；真要逐视图铺开，成本会远超收益。

## 3. 替代方案与取舍

| 方案 | 结论 |
|---|---|
| 用 `web-time` crate（跨平台 `SystemTime` 垫片） | **不采纳**：只为这一次调用引入一个 crate，收益不如直接用 `js_sys`（wasm-bindgen 生态标准件） |
| 用 `wasm-bindgen` 的 `js_sys::Date` 但只在 wasm 分支 | **采纳**（本 ADR） |
| 让调用方把 `now` 传进来（与 `apply` 的 `request.now` 同风格） | **不采纳**：28 个入口都要加参数、前端 25 个 mapper 都要传时间——把「环境差异」扩散成「协议差异」，且前端时钟同样可被篡改（零强制力下无所谓，但没必要） |
| 只在 e2e 里加用例、不改 native 测试 | **采纳**（见 §2.2），但同时在 `epoch_millis` 上写了完整注释 |
| 把 `wasm-bindgen-test` 接进 CI | **暂不**：需要额外的浏览器/node runner 与构建步骤；e2e 已覆盖同一交叉区，先不扩基建 |

## 4. 后果

- Web 计划面**从「默认崩溃」变成「真的可用」**：所有 28 个 plan 入口共用修好的 `ulid_like_id`。这是行为层面的重大修复，不只是测试变绿。
- native 依赖树不变（`js-sys` 只在 wasm32 target 下引入）；wasm 产物体积变化可忽略（`Date.now` 是 JS 全局，`js-sys` 只是绑定）。
- `cargo deny check` **全量通过**（advisories／bans／licenses／sources 均 ok；网络恢复后补验）：`js-sys 0.3.107` 来自 crates.io，MIT/Apache-2.0 在白名单内。
- 推翻条件：若将来 CI 接入 `wasm-bindgen-test`（能直接在 wasm32 跑断言），可把 e2e 的那条用例下沉为 Rust 测试；但 e2e 仍应保留——它验的是「浏览器整链路」，不只是单函数。

## 5. 证据

- 修前：`browser-storage.spec.ts` 真执行用例红，Worker 打出 `plan_c02 RuntimeError: unreachable`；native `plan_c02_core` 同输入正常出计划（说明是 wasm32 运行期问题）。
- 修后：`playwright test` **34 项全绿**（27 既有 + 2 OPFS + 5 真 WASM 族冒烟），真执行用例 **1.6 s** 完成并断言 OPFS 里有产物；C10／F10／F12／C07／C11 各 1.4–1.7 s。
- `cargo test --workspace`：16 个 result 全 ok；`cargo fmt --check`／`clippy -D warnings` 0。
- `cargo build -p batchdesk-wasm --target wasm32-unknown-unknown` 通过（`js-sys 0.3.107` 编译进来）。
- `vitest` 42 文件／358 项；`tsc --noEmit`／`vite build` 0。
- 沉淀教训（memory）：**native 绿 ＋ vitest 绿 ≠ 浏览器绿**；凡是 mock 掉 WASM 的测试，都不能证明 WASM 在目标运行时可用。
