## 1. 问题背景

F11（按清单批量创建文件夹）把每条清单路径**按层级展开**成多条 `create-dir` 条目（父先子后）。但两侧入口的事实采集都只探**叶子路径**：

- CLI `run_f11`：`existing_targets` 只收 `target_for_list_path(root, 整条相对路径)` 的存在性；
- 壳层 `plan_f11_shell`：同样只 `root.join(row.path).exists()`。

后果是"清单要求 `a/b`，而 `a` 位置上是个**文件**"这类冲突在计划期看不见：预览里 `a/b` 是一条正常待执行条目，直到 apply 期 `create_dir` 失败才暴露。这正是映射表 `TC-F11-PRE-03` 长期挂着的登记缺口（"父路径为文件的前置报告未做"），也违背方案 §7.1"预览必须暴露冲突、执行按计划落盘"的两段式含义。

另一半问题在界面：23 个功能页的计划卡片只显示 `警告 {plan.stats.warning}` 这个**计数**，`plan.warnings` 的类别与建议文本一个都不渲染（只有 C09 工作台 `App.tsx` 逐项列出）。于是"集中报告"到了 UI 就退化成一行数字，用户看不到哪几行被排除、为什么被排除。

## 2. 候选与结论

| 议题 | 候选 | 结论 |
|---|---|---|
| 冲突表达 | a) 新增错误码（如"父级为文件"）；b) 复用条目级 `conflict.kind` ＋ `resolution=skip` ＋ 计划级 warning 集中报告 | **b**：篇 06 的 E2xxx 已把"冲突且策略为 skip"归在 E2007，F11 的既有 `existing-target` 也走同一形态；扩码位需要人类走方案 §11.6，而这里没有新增强制语义 |
| 事实形状 | a) `existing_targets` 扩成 `{path,kind}` 结构体；b) 保留 `existing_targets`，另加 `existing_files`（两份都是**逐级前缀**） | **b**：只增字段、不动既有比较语义，`existing_target_is_a_skip_conflict` 等既有用例零改动；结构体改造会波及 c07/c08 等共用同一采集形状的入口 |
| 采集范围 | a) 只探叶子（现状）；b) 探每一级前缀并区分文件/目录 | **b**：kernel 需要祖先级事实才能判定，这是"计划期能看见"的必要条件；CLI 与壳层同口径，采集逻辑在壳层抽成 `f11_existing_facts` 以便单测 |
| 被挡住的多深 | a) 只标直接父级；b) 文件一旦出现，其**整条子树**都标 `parent-is-file` ＋ skip | **b**：`a`（文件）→`a/b`→`a/b/c` 都建不出来；且要处理"该级已由前一行计划过"的去重路径（`planned` 命中仍须把 blocker 传给更深层级） |
| 界面 | a) 继续只显计数；b) 功能页渲染 `plan.warnings` 逐项点名（与 C09 工作台同形状、同 `.warnings`／`.warning <risk>` 类） | **b**：集中报告的"集中"指**逐项列在该计划之下**，不是折成一个数字；不新增视觉值，复用既有 token 化样式 |
| e2e 数据源 | a) 只在 jsdom 层断；b) 另在浏览器 mock 给 F11 一条同形状夹具，用 Playwright 断真实 DOM | **b**：mock 只承担 UI 语义（ADR-0046 边界），不代表真机文件结果；夹具规则"清单出现多级路径 ⇒ 给一条 `parent-is-file`"按 kernel 报告形状构造 |

## 3. 选择理由

- **不新增产品行为**：跳过（skip）＋集中报告都是方案 §5.15/§5.8 已给定的处理方式，本次只是把一类此前漏报的冲突纳入既有处理形态；未引入阈值、未改判定强度，因此不需要 §11.6 裁决。
- **强制力位置不变**：判定仍在 kernel 纯函数（`plan_f11`），入口层（CLI/壳层）只负责"把事实采齐"；不变量 1／2 未被触碰——`plan` 依旧零落盘。
- **可断言且防空转**：kernel 三条新用例（正向点名、跨行传播 blocker、**没有该事实时不得冒出该告警**的对照）＋ CLI 一条端到端用例（真实文件挡住父级：计划期 skip、集中报告存在、apply 退出码 0 且无冲突分支照常创建、被挡分支零落盘）＋ 壳层一条事实采集用例＋ Vitest 两条（逐项点名／无 warnings 时空块不得出现）＋ Playwright 两条（F11 点名／F12 不出现）。
- **先红是实测的**：把 kernel 的 `blocked_by` 临时置为 `None` 后，2 条 kernel 用例与 1 条 CLI 用例分别失败（对照用例仍绿，证明它不是同义反复）；把功能页的 warnings 渲染条件临时加上 `plan.kind !== "f11"` 并重新 `pnpm build` 后，Playwright 正向用例失败、对照用例通过。恢复后全绿（见 §5）。

## 4. 后果与已接受的不完美

- **两处入口的采集成本上升**：从每条 1 次 `metadata` 变成每级 1 次。清单行数与层级深度都远小于文件批量操作，且此前 C-1 实测显示 10 万条目录树的遍历／写出都在秒级（`fixtures/bench/results.md` R-01…R-03），不构成瓶颈；若将来要处理十万行级清单，应改为一次遍历的批量事实采集。
- **长路径面沿用既有形态**：CLI 与壳层的 F11 事实采集都用 `std::fs::metadata`，未经篇 04 的长路径前缀适配层（这是既有入口的普遍形态，非本次引入）。Windows 上路径 >260 且未开启长路径支持时，该级前缀会被读成"不存在"，表现为**漏报** `parent-is-file`；但创建动作本身走适配层，不会因此写坏数据。推翻条件：Windows 实机日在 R01 类长路径场景发现漏报，或 platform 暴露公开的 metadata／kind API 时，统一把入口层事实采集改到适配层。
- **`existing_files` 的语义约束写在字段注释里**：它必须是 `existing_targets` 的子集且同样覆盖逐级前缀——调用方漏采前缀时 kernel 无从校验（kernel 不读盘）。因此两侧入口各有一条用例守住采集面本身。
