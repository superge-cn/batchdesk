# 工程决策记录（ADR）

本目录只记录**工程实现细节**的决策。产品行为与视觉的改动**不走这里**（见下方边界声明）。

## 1. 何时写 ADR

判据一句话：**"半年后有人会问为什么，且答案不在四份基线里" → 写 ADR。**

具体地，命中以下任一条即写：

- 选了一个**方案（approach）**而不是另一个，且代价不对称（换回去很贵）；
- 引入或排除一个**依赖／工具链／构建方式**；
- 定了一个**仓库级约定**（目录结构、命名、门禁、测试分层）；
- 留下一条**明知不完美但选择接受**的取舍（并写清什么条件下会推翻它）。

**不写** ADR 的情形：日常实现选择、可随手改的局部细节、基线已定义的产品行为。

## 2. 编号与命名

- 编号 **NNNN** 四位递增，**永不复用**（即使某篇被否决，编号也保留）；
- 文件名：`NNNN-短标题.md`（中文短标题，与 D-R1 的语言约定一致）；
- `0000` 保留给模板，不写真实内容。

## 3. 状态流转

```
提议（Proposed） ──采纳──▶ 已采纳（Accepted） ──被新决策取代──▶ 已取代（Superseded by NNNN）
        │
        └──不采纳──▶ 已否决（Rejected，保留归档，写明否决理由）
```

- **不修改已采纳 ADR 的正文**。结论变了就新写一篇，并在新旧两篇的"关联"字段互相指向；
- 唯一允许的原地修改：在文首补 `状态：已取代（Superseded by NNNN）` 一行。

## 4. 与方案 §11.6 的边界声明（重要）

| 改动性质 | 归属 | 载体 |
|---|---|---|
| 产品行为（功能定义、优先级、授权分组、阈值、交互规则） | 方案 §11.6 的书面确认流程 | 《办公辅助工具产品方案》 |
| 视觉（颜色、字体、间距、状态外观、组件形态） | U 的修订 | 《UI 视觉规范》 |
| **工程实现细节**（结构、依赖、构建、测试策略、仓库约定） | **ADR** | 本目录 |

**边界冲突处理**：如果一个"工程决策"实际上会改变产品行为，**它就不是 ADR，必须走 §11.6**。
写法上的自检：ADR 的"问题背景"里若出现"用户会不会……""这个功能该不该……"，说明走错了地方。
