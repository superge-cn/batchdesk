## 1. 问题背景

OQ-36 的账面说法是"`TemplateStep.kind` 是动作、壳层按功能码路由，一对多，反推不出来"。核实时先把分布做出来（`src-tauri/src/lib.rs:208-233` 的路由逐条对内核各 `plan_*` 模块实际产出的动作）：

| 动作 | 功能码 | 能否反推 |
|---|---|---|
| `split` | f01／f02／f03／f05 | ✗ |
| `edit-content` | c01／c02／c03 | ✗ |
| `rename` | f12／f13／c04 | ✗ |
| `merge` | f04／f06 | ✗ |
| `csv-rows` | f08／f09 | ✗ |
| `move` | c07／c08 | ✗ |
| `delete`／`listing`／`create-dir`／`csv-extract`／`archive`／`extract`／`csv-dedup`／`csv-filter`／`csv-sort`／`csv-columns`／`copy` | c09／f10／f11／f07／c10／c10／c11／c12／c13／c14／c07 | ✓（唯一） |

**25 个功能码里 16 个反推不出来。** 用户裁决取①：schema 升 v4，`TemplateStep` 增 `feature` 字段。

而真正关键的一句话在**基线**里（方案 §15.2.5）：

> 应用模板**只回填参数并调用 `planOperation`** 生成计划；**必须重新预览**，不得直接 apply。

这与设计 03／01 命令表里 `loadRecipe {recipeId} → PlanDocument`（只给模板 id 就"直接产出预览计划"）不是同一件事：模板按不变量 13 **不保存源路径**，只凭 `recipeId` 就无法完成事实采集，产不出计划——要么改命令入参（命令面变更），要么承认套用是界面动作（回填＋`planOperation`）。**这条冲突不在本篇里自行定案**，登记为 OQ-40。

## 2. 本批做了什么、刻意不做什么

做（都属于①的确定含义，不触碰未定契约）：

1. `TemplateStep` 增 `feature: Option<String>`；`CURRENT_RECIPE_SCHEMA_VERSION` 3 → 4。
2. **保存即记录**：功能页「存为处理模板」把当前功能页 id 传进去（`FeaturePages.tsx` 的 `feature: view`）——这个信息在保存那一刻本来就存在，之前被丢弃。
3. **迁移不猜**：`feature_for_action` 只登记上表右列那 11 项**唯一**映射；v3 文件载入时按它补 `feature`，一对多动作保持 `None`。显式值优先于推断。
4. `None` 的语义写死为**不可套用**，不是"绑定到通用出口"；界面据此如实显示「未绑定功能：这一步只有动作……」，仍不提供假按钮。
5. `single_step_binding()` 把套用判据收成一处：单步＋有绑定才谈得上套用，多步与未绑定各报各的原因（`multi-step`／`re-save`）。
6. **门禁化**：这张表在两个地方各有一份（内核 `feature_for_action`、浏览器 mock `ONE_TO_ONE_FEATURES`）。`check_docs.py` 新增 `check_recipe_feature_table`：逐项比动作集合与绑定的功能码，含**自校**（任一侧解析出少于 8 项即报"核对失效"，避免探测器静默永真）。动因与 ADR-0071 同源——两份清单必然漂移，而 mock 比壳层宽松就会让 Playwright 走一条真机不存在的通路。

刻意不做：

- **不实现 `loadRecipe`**：它的入参形态就是 OQ-40 要裁的东西；现在实现等于替人类定命令面（AGENTS「何时停下来问人」：命令面与 schema 变更走人）。
- **不做"从参数键存在性反推功能码"**（②的做法）：`paramsSnapshot` 的定义是「计划自带那份原样交壳层」（ADR-0072），塞伪键就不再原样，且导入校验要新增规则。
- **不迁就 64 个旧模板的猜测**：迁移只补唯一项，剩下老实标未绑定，让用户重存一次。

## 3. 后果

- 存量化解绑：v3 模板里 `delete`／`listing`／`copy` 这类唯一动作自动获得绑定，一对多动作需重存。
- 「一键套用」的**数据前提**已具备（知道该回填到哪一页），**唯一还缺的是输入通道**——这是一个决策而不是工作量。
- 内核多了一张功能码表。它与壳层路由的关系靠：`feature_for_action` 只登记唯一项＋`planOperation` 的 `other =>` 分支仍是最终把关＋`check_recipe_feature_table` 盯住两处副本一致。这张表**故意不完整**，补全它＝开始猜功能。
- 类型改名 `RecipeDocumentV3` → `RecipeDocument`：与设计 01 §4.4.2 的 DTO 名一致，`RecipeDocumentV2` 只作为迁移输入保留。`export_returns_v3_json` 随之改名并把断言改成跟着常量走——写死过一次的版本号，正是这次要修的假绿来源。
