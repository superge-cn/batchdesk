# 0057. C03 流式替换的重叠窗口与正则边界

- **状态**：已采纳（2026-11-03，A 类流式改造第 4 批）
- **日期**：2026-11-03
- **决策者**：开发代理（工程实现决策；产品行为、错误码与阈值不变）
- **关联**：方案 v1.19 §4.8（大文件三档策略）、§5.14（C03 实现要点：尾部重叠窗口）、§9.1（超大文件内存恒定）；设计 01 v1.45 §5；ADR-0050（替换计数口径）、ADR-0054（`RecordFeeder`）、ADR-0055 §4（C03 未动边界）；`crates/kernel/src/replace_content.rs`

---

## 1. 问题

`ReplaceRewriter::rewrite` 用 `read_to_end` 整段读入源文件再整段变换——内存 O(文件)，与方案 §4.8 的「10 MB – 2 GB 纯流式」档位不符，也与 §9.1「超大文件内存占用恒定」冲突。

方案 §5.14 已点名这道障碍：「块读时保留'最大模式长度量级'的尾部重叠窗口，保证跨块的匹配不漏（这是流式替换最容易出错的地方）」。ADR-0055 §4 把它登记为「C03 未动」，理由是 regex 模式的最大匹配长度不可知、plain 单独流式会造成路径分叉。

## 2. 候选与结论

| 议题 | 候选 | 结论 |
|---|---|---|
| 路径划分 | a) plain / cell / regex 统一走同一套窗口化扫描；b) 按**模式语义**分支：plain 精确重叠、cell 记录级增量、regex 保留整段 | **b**：a 对 regex 只能取「模式长度」当窗口，而 `a+`、`.*` 的实际匹配长度与模式长度无关——窗口一旦小于匹配长度就会**静默漏替换**，正是 §5.14 警告的失败模式；「结果正确」优先于「路径统一」。b 的分支轴是模式语义而非文件大小，同一输入永远走同一路径，行为可预测 |
| plain 重叠量 | a) 固定 4 MB 块尾重叠；b) 精确 `find.len() - 1` | **b**：plain 的最大匹配长度就是 `find` 的字节长度，重叠 `len-1` 是可证下界；再大只是白读 |
| 块大小 | a) 沿用 64 KiB；b) 按 §4.8 的 4 MB | **a**：内核侧块大小只影响内存上界与系统调用次数，`rewrite_atomic_with` 由适配层开文件、内核按 64 KiB 读（与 `TranscodeRewriter` 同口径）；§4.8 的 4 MB 是**适配层**固定块读取的建议值，不是内核重写器的契约值 |
| cell 模式 | a) 保持整段；b) `RecordFeeder` 增量记录 → 逐字段替换 → `write_record` 逐条写出 | **b**：单元格替换是**记录内局部**操作，不跨记录；`RecordFeeder` 与 `parse_records` 语义已由 ADR-0054 逐条钉住，逐条序列化与整段序列化逐字节一致 |
| regex 模式 | a) 保留整段；b) 用模式长度当窗口；c) 边读边增长窗口直到匹配落定 | **a**：b 会漏匹配（不可接受）；c 理论上正确（只接受 `match.end < 缓冲末尾` 的判定，否则继续读），但把「单条匹配长度」变成新的内存上界，且需要为「超长匹配」定义处置（新错误码，超出本次授权）——留作独立议题，本批不夹带 |
| UTF-8 校验 | a) 每块独立 `from_utf8`；b) 累积缓冲整体校验，尾部未完成序列视为「等下一块」 | **b**：a 会把跨块被切开的多字节字符误判成 E3001（源本是合法 UTF-8）。尾部不完整只在 EOF 时才算错 |

## 3. 实现

- `ReplaceRewriter::rewrite` 按结构分派：`structure == Csv && csv_mode == Cell` → `rewrite_cells`；否则 `mode == Plain` → `rewrite_plain`；`mode == Regex` → 既有整段路径。
- **`rewrite_plain`**：64 KiB 块读入累积缓冲；每次只判定「起点 < 安全边界（`len - (find.len()-1)`，EOF 时即 `len`）」的匹配，命中即写出前缀＋替换文本并跳过匹配（不重扫），未判定部分留在缓冲尾部；UTF-8 按 §2 的 b 方案整体校验。匹配语义与 `str::replace` 的非重叠、从左到右一致。
- **`rewrite_cells`**：首块读入后按 `delimiter` 参数或首块 `sniff_delimiter` 定分隔符（与整段路径同一函数、同一 E 码）；`RecordFeeder` 增量产记录，逐字段 `Matcher::replace`，`write_record` 逐条写出；收尾时若 `RecordFeeder` 仍处于引号内，按既有 E3004 拒绝（临时文件由 `rewrite_atomic_with` 丢弃，源文件不变）。
- **计数口径不变**（ADR-0050）：C03 的替换计数仍在计划期上报，`EditOutcome` 保持 `default()`。

## 4. 已接受的坑与边界

- **regex 仍 O(文件)**：`ReplaceMode::Regex` 的执行期内存不随本 ADR 改变，映射表缺口按此措辞保留（不得写成「C03 已全流式」）。
- **cell 模式的内存单位是「单条记录」**：引号内换行会把一条记录撑大，这是 CSV 语义的固有驻留（与 ADR-0054 同口径），不是回退。
- **cell 模式的非法 UTF-8 行为不变**：`parse_records` 与 `RecordFeeder` 都用 `from_utf8_lossy`；计划期已按 E3001 拦截非 UTF-8 源，执行期保持既有（不改）语义。
- **等价性是护栏，不是红→绿**：流式化的可观察行为与整段路径应当**逐字节相同**，因此本臂没有「先红」的失败信号（不同于 ADR-0056 的缺陷修复）；护栏为分块等价性单测——用 1 字节/3 字节/整段三种喂法比对 `replace_bytes` 结果，且跨块边界必须落在匹配、替换文本与多字节字符中间。
- **分隔符嗅探只看首块（64 KiB）**：`delimiter=auto` 时整段路径用全文件 `sniff_delimiter`，流式路径用首块；CSV 的分隔符必然出现在首行，现实输入下两者一致，只在「首行超 64 KiB 且分隔符只出现在更后」这类极端文件上可能不同，此时按「嗅探不到 ⇒ E1002（缺少分隔符参数）」处理，与既有拒绝口径同码。要彻底消除该差异需把嗅探改成增量判定，不在本批。
- **未做**：行区间限定（`5.14` 提到的「全文件/指定行区间」中的后者）仍是计划期外的事，本批不碰。

## 6. 补记（2026-11-04）：regex 臂由 ADR-0064 接手，本 ADR 的 §4 第一条已不成立

本 ADR §4 写的「**regex 仍 O(文件)**」在 [ADR-0064](./0064-C03正则流式替换的窗口界定.md) 之后
不再全局成立：能**静态算出匹配长度字节上界**的正则子集已窗口化流式；含无界量词、锚点、
单词边界、内联标志组、分组量化或零宽匹配的模式**仍整段**。§2 当年否决的「c) 边读边增长
窗口直到匹配落定」，缺的正是「怎么知道窗口够大」这个前提——ADR-0064 用静态界定回答它，
而不是猜一个窗口值。

同时 ADR-0064 §4 记下一处本 ADR 留下的潜伏缺陷：plain 臂的安全边界按 `len - overlap` 取值，
缓冲区**整块都是合法 UTF-8** 时该边界可能落在多字节字符中间，半个字符被写进输出、半个留在
缓冲里，下一块的 UTF-8 校验会对一份完全合法的文件报 `E3001`。当时的等价性测试用「中ab」
反复 ＋ 非 3 倍数的块大小，恰好让不完整尾巴替 `valid_up_to` 兜住了这一分支，因此没暴露。
