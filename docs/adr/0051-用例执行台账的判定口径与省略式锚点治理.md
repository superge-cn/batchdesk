## 1. 问题背景

映射表把 TC §3 的 296 条阶段 0 实例逐条对到了载体与锚点，并已被 CI 门禁校验（条数、ID 唯一、锚点实名、✅ 不挂缺口、载体/状态一致、E4 必须引用取消锚点）。但它**不回答两个问题**：

1. **这次真的跑过吗**——"有锚点"与"锚点在本次运行里存在且为绿"是两件事。此前只有零散的"CI run 全绿"记录，从未按实例核对。
2. **锚点还找得到吗**——改名／删除测试后，锚点文字会变成死引用；"同上（…）"这类省略式写法也无法机器核对。

开发计划 §5 第 72 行把"跑用例（阶段 0 出口硬前置）"列为最该做的事，而 T §4 的出口口径是"执行率 100%"。要谈执行率，先得有一份**按实例**的执行证据。

## 2. 候选与结论

| 议题 | 候选 | 结论 |
|---|---|---|
| 台账怎么产生 | a) 人工逐条填；b) 脚本先跑四套载体、再把每条锚点解析到实测清单，CSV 与 md 同源产出 | **b**：人工填 296 行必然漂移（本轮实测就抓到 4 处条数过期、1 处列错位、5 处死引用）；脚本产出可复跑，数字与清单同批 |
| 判定层级 | a) 只记 pass/fail；b) 按解析可信度分层：逐名／模块级整组／前端文件级／待人工，外加四类缺陷判定 | **b**：一条锚点写"kernel `csv` 18 项"时整组确实在跑，说它"没证据"是错的；说它"证明了该实例判定点"同样是错的。分层＋明文口径边界才有信息量 |
| 与映射表的分工 | a) 台账另立一套覆盖结论；b) 覆盖与缺口仍以映射表状态／缺口列为准，台账只加"证据是否真跑"这一层 | **b**：两份台账各答一问，避免同一个"✅"承载两种含义 |
| 门禁强度 | a) 只校验行数与 ID 对齐；b) 再加：判定词法合法、载体↔判定一致（真人工⇔待人工执行）、清单文件必须存在、**计数不符／名不符／实测失败必须为 0** | **b**：这三类是"证据链已断"，留成常态就失去门禁意义。已用注入样例证明该规则能报错（改一行判定为"实测失败"、一行改成词法外取值 → 三条错误、恢复后 exit 0） |
| 省略式锚点 | a) 允许"同上"；b) 生成时就地展开（`expand_same_as`：RBK-01 的"同上"展开成本功能的 EXE-01 锚点）；c) 解析器猜上一行 | **b**：16 条"同上"里，解析器按上一行继承会把 `无（…）` 当成证据（实测就发生过一次误判）；在数据源展开才是可核的。同时 `default_pre_slots` 加形态守卫——传错元数会把"✅"写进锚点列（TC-C07-PRE-04 就是这样错位的） |
| 待人工行 | a) 计入"已执行"；b) 判"待人工执行"，且载体必须含真人工／受控环境 | **b**：34 条全部指向 Windows 实机日／受控环境，Linux 预跑不得冒充 |

## 3. 选择理由

- **一句话口径**：`实测通过` ＝"这条实例的证据本次存在且为绿"，不等于"T 的验收判定点已覆盖"。这句话写在台账 md §4 的第一条，避免被读成后者。
- **数字不手写**：md 的表格与统计由脚本按本次运行生成，改判定或锚点后必须重跑，不会出现"文字改了、统计没改"。
- **一次性把发现的漂移吃掉**：本轮 `encoding` 11→12、`generic_apply` 40→44（前两批自己加的测试没同步锚点）、`corpus.rs::K06`（写的是语料号不是测试名）、C07-PRE-04 的列错位，全部就地修正；剩余不可核对的锚点作为清单挂出来，不假装完成。

## 4. 后果与已接受的不完美

- **模块级判定的强度弱于逐名**：台账里"实测通过（模块级）"的行，其证据是整组测试为绿；若将来要把它们全部升级成逐名，需按 §3 待办清单改写 43 条锚点（工作量可控，属测试层，不改产品代码）。
- **7 条锚点确实没有对应测试**：S01 的 `preflightPlan`／`applyPlan` 阻断面（4 条）与 S02 的"各功能隐含成立"（2 条）＋ C17a 一条——不是文字问题，是**缺测试**；已列入待办，需要补壳层断言或显式断言后再复核。
- **1 条锚点是"无"**：`TC-C15-PRE-04`（运行中调参下一批生效）既无 kernel 断言也无 UI；改判 ⛔ 待实现更准确，但改判属覆盖口径变更，留待你确认（方案 §11.6）。
- **解析器不是万能**：中文描述型锚点若既不含模块反引号也不含测试名片段，只能判"不可机器定位"——这正是设计意图（暴露问题而不是猜答案）。
