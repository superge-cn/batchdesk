# ADR-0118：Web staging 的内存峰值与跨线程复制收口

- 状态：已采纳·A3-18 落地（2026-11-24）
- 相关：ADR-0108（执行沙箱与 staging）、ADR-0115（产物落盘）、ADR-0110（输出路径派生）；设计 02 §3.1.1、方案 §13.10.2（本地建议档）
- 影响范围：web/src/lib/web/applyChannel.ts、web/src/lib/wasm/client.ts、web/src/lib/web/opfsStore.ts

## 1. 背景

`stage_inputs` 的协议原本是「清单 + 一段**连续**字节」：调用方把所有待执行文件读进内存、拼成一个 `Uint8Array`，再一次性交给 Worker。注释里的理由是「只过一次边界」。

这个理由只在**小文件**成立。按 §13.10.2 的本地建议档（单文件 ≤100MB、任务总量 ≤500MB）算峰值：

| 阶段 | 峰值占用 |
|---|---|
| 逐文件读出的 `bytes`（仍被 `entries` 引用） | ≈ 总量 |
| 拼接出的 `data` | ≈ 总量 |
| `postMessage` 结构化克隆（无 transfer list） | ≈ 总量 |
| wasm-bindgen 把 `&[u8]` 拷进 wasm 线性内存 | ≈ 总量 |

也就是说，**500MB 的任务在主线程上要到 GB 级**——「建议档只提示不阻断」给了用户确认放行的路，但实现本身撑不住那个量级。这不是性能优化题，是**与已声明的建议档不自洽**。

同一批还发现一处谎报：`clearPersisted`（清浏览器内的产物）对**任何**异常都返回 `true`，包括权限/句柄占用这类真失败——界面会说「已清理」而文件还在。

## 2. 决策

### 2.1 逐文件登记，不拼接

`stage_inputs` 每次只带**一个文件**（清单一项）。峰值从「总量×2」降到「单文件×2」，与文件数无关。

代价是 round-trip 随文件数线性增长（每个文件一次 wasm 调用）。这个代价是可接受的：每次调用是常数级（JSON 编解码 + 一次 `insert_file`），万级文件量下增加的是百毫秒量级；而峰值内存是**会崩**的那一类问题。

### 2.2 先算键，再登记

`stagedPath` 在「普通多选但视图需要相对路径」时抛 `E1001`。逐文件登记把「算键」挪进了循环，如果边算边传，前几个文件已经进沙箱、后面才报错——沙箱里会留下**半批输入**。所以要求：**先把每个文件的键都算出来**（全部校验通过），才开始登记。

### 2.3 字节用 transferable 传，不克隆

`worker.postMessage(message, [bytes.buffer])`：把底层缓冲区**转移**给 Worker，主线程不再保留第二份。前提是调用方不复用该缓冲区——`stageInputs` 与 `parse_c07_manifest` 都是「读一次、立即交出」，没有复用。

### 2.4 OPFS 清理只把「不存在」当成功

`removeEntry` 抛 `NotFoundError` 时，对「清理」而言已是目标状态，返回 `true`；**其它失败一律返回 `false`**，界面据此如实提示。把「删不掉」说成「已清理」是最难排查的一类谎报。

## 3. 代价与边界

- 多文件时 round-trip 变多；单文件 500MB 的场景仍需「读出的字节 + wasm 内拷贝」两份（协议层面的下界）。
- 没有引入任何新的数值阈值：分批不按固定字节数切，而是「一文件一次」，避免在实现里另立一个 §13.10.2 之外的数字。
- staging 仍是**整文件**读入（不切片）：File API 的 `slice()` 可以做到块级，但需要 `stage_begin/chunk/end` 三段协议与沙箱侧的追加写，超出本批半径。

## 4. 什么条件下推翻本文

- 使用形态转向「少量超大文件」（例如单文件 1GB 以上）：需要分块协议把单文件峰值也压到块级；
- Worker 侧需要保留入参缓冲区（例如同一批输入要重复执行多次）：transferable 会失效，要改回复制并显式衡量代价。
