# ADR-0117：F13 正则改名接入 UI 面（桌面壳路由＋前端视图＋Web 计划执行）

- 状态：已采纳·A3-17 落地（2026-11-24）
- 相关：ADR-0026（F13 计划引擎）、ADR-0113（改名族的条目口径与 staging）、ADR-0114（F10 的目录事实）、ADR-0105（计划能力分档）、ADR-0108（执行沙箱）；设计 01 §4.4.2、设计 02 §2.1／§3.1.1、设计 12 §3.1
- 影响范围：src-tauri/src/lib.rs（路由＋采集）、src-tauri/src/ai.rs（FunctionCatalog）、src-tauri/src/recipe_apply.rs（两张配方表）、web/src/navCatalog.ts、web/src/App.tsx、web/src/FeaturePages.tsx、web/src/lib/ipc/{types,mock}.ts、web/src/lib/web/{planChannel,applyChannel}.ts、web/src/locales/*

## 1. 背景

F13（正则批量改名）自 ADR-0026 起就有 kernel 计划引擎、CLI 命令与 24 条语料锚点，台账逐条记的是「F13 缺 UI」。核对后缺口是**两层都不通**：

| 层 | 状态 |
|---|---|
| kernel `plan_f13` | 已实现（正则编译、捕获引用校验、两阶段编排、冲突扫描全套复用 F12） |
| CLI `f13 --dir --regex --replace --scope` | 已实现 |
| WASM `plan_f13` | 已导出（A2 批次），`web/src/lib/wasm/contract.ts` 的 `PLAN_OPS` 里也有 |
| 桌面壳 `plan_operation_impl` | **无 `"f13"` 分支** —— 界面点下去只会得到「未知 kind」 |
| 前端 | **无视图**（`navCatalog` 的 `FeatureView` 不含 f13） |
| Web 计划/执行通道 | `planChannel` 无 `planF13`；执行档位表里也没有它 |

也就是说：功能可计划、可执行、有测试，但**用户在两形态都点不到**。这类「实现齐备、入口为零」的缺口不会被任何测试抓住——`cargo test` 与 vitest 都只测已存在的入口。

## 2. 决策

### 2.1 补 UI 而不是改产品范围

F13 是 T v1.12 §2.2 阶段 0 的 25 项之一，此前的登记是「切片完成（CLI，无 UI）」，不是被排除的功能。补 UI 是把已批准范围内的功能接通，**不新增功能定义、不改优先级**。补齐后功能视图 23 → **24**，阶段 0 的 25 项在桌面上都有入口。

### 2.2 桌面壳与 CLI 必须同口径：采集提成共用实现

F13 的条目与 F12 完全同形（路径＋当前名），桌面采集因此复用同一段逻辑，并在此过程中发现 F12 壳层与 CLI 的**既有偏差**：

| 项 | CLI `run_f12`／`run_f13` | 壳层 `plan_f12_shell`（改前） |
|---|---|---|
| 符号链接 | `symlink_metadata().is_symlink()` → 跳过 | **未跳过**（链接也进条目） |
| 条目顺序 | `items.sort_by(name)` | **未排序**（`read_dir` 原序） |

后果不是报错，而是「同一个目录，UI 与 CLI 得到不同的改名集合与不同的两阶段顺序」。本批把这段提成 `collect_rename_entries(dir)`，F12／F13 共用，按 CLI 口径收敛；`read_dir` 的原始顺序不再进入计划（两阶段编排与冲突裁决对顺序敏感）。

### 2.3 正则只在计划期校验一次

壳层与 Web 都**不预检正则**：编译、捕获引用校验（`$1`／`${name}`／`$$`）、非法 pattern 的 `E1002` 全在 `kernel::regex_rename::plan_f13` 里做。理由与 C04/F12 相同——两套校验必然分叉，而用户看到的预览必须来自真正会执行的那份计划。

### 2.4 Web 侧沿用改名族的既有口径

- 条目＝目录**第一层**名字（`webkitdirectory` 的相对路径），不递归（ADR-0113）；
- staging 键＝`根名/相对路径`，子目录条目的整棵子树一起进沙箱（`RELATIVE_ROOT_VIEWS` 加 f13）；
- `existingTargets` 恒空（浏览器没有目标文件系统，与沙箱执行环境一致）；
- `scope` 用小写字符串（内核 `RenameScope::parse`），F12 才收 PascalCase 枚举——翻译仍只在 `renameScope(raw, style)` 一处。

执行档位 22 → **23**（视图全集 24，剩 C09／F11 两个能力边界）。

### 2.5 C05 对照预览扩到 F13

`kernel::preview::rename_preview` 的 `C05_PREVIEW_KINDS` 本就是 `f12`／`f13`／`c04`。界面此前只在 F12 页调用，本批用 `RENAME_PREVIEW_VIEWS` 明确登记 `f12`／`f13`。**C04 仍不接**：内核能算不等于界面已有，不把未接的能力写进档位表（A3-9 的教训）。

### 2.6 AI 目录与配方表必须同步

- `ai.rs::CATALOG` 是「壳层可路由」的唯一来源，且有 `catalog_covers_every_shell_routable_plan_kind` 断言——加路由就必须加目录项（f13 → Phase 2），`CATALOG_VERSION` 递增到 `2026-11-24.p3`；
- `recipe_apply::FEATURE_PATH_SLOTS`（必填槽 `dir`）与 `FEATURE_PARAM_MAP`（`m("f13")`：`pattern`/`replacement`/`scope` 走计划快照转发，不属「变换正文」）各加一行，浏览器 mock 的 `APPLY_SLOTS` 同步——三处由 `check_docs.py` 双表核对，漏一处 CI 红。

## 3. 代价与边界

- **F12 的桌面行为有变化**（跳符号链接＋排序）：这是修正方向（与 CLI 一致），但确实是用户可感知的变化，已计入台账与 CHANGELOG。
- F13 在浏览器里仍看不到空子目录与符号链接（`webkitdirectory` 能力边界，与 F12 相同），字段提示里如实写明。
- 改**目录名**时目录本身无法下载（产物只列文件），与 F12 相同。
- 模板套用：F13 的配方把 `pattern`/`replacement`/`scope` 存在计划快照里随模板保存，套用时由映射表原样转发；不含路径（`dir` 由槽位注入）。
- **替换模板的 `$1_` 会被按「组名 `1_`」解析**：`regex` crate 的 `$name` 词法把后续的字母/数字/下划线都吃进组名，因此 `$1_` 是「引用不存在的组」而不是「组 1 后接下划线」——内核按 `E1002` 拒绝（正确行为，不是缺陷）。真 WASM 的 e2e 第一次跑就红在这里；界面提示与字段示例因此写 `${1}_${2}`，并明确「后接字母、数字或下划线要加花括号」。

## 4. 什么条件下推翻本文

- 改名族改为**递归**处理（会同时改 F12/F13/C04 的条目口径与 staging）；
- 为 F13 单独做一个预览面板而不复用 C05；
- 产品决定 F13 不作为独立视图（改为 F12 的「模式」）——那要移除 `FeatureView` 项并同步三处清单。
