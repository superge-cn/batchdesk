# 0108. Web 执行沙箱：staging ＋ MemoryFs ＋ 产物下载

- 日期：2026-11-22
- 状态：**已采纳**（A3-6 落地：`kernel::memfs`（`FsAdapter` 第三个实现）＋ `crates/wasm::exec`（`Sandbox`）＋ 5 个导出 `web_exec_stage/apply/undo/product/reset` ＋ `web/src/lib/web/applyChannel.ts` ＋ F01/F02/F03 执行接线）
- 相关：[ADR-0104](./0104-Web计划通道真计划不配假执行.md)（真计划不配假执行，本 ADR 把它收窄为「执行没接的视图仍不配假执行」）、[ADR-0105](./0105-Web计划能力矩阵按事实齐备度分档.md)（计划分档，执行分档与之同构）、[ADR-0101](./0101-Web配额QuotaBased口径.md)（零强制力）、[ADR-0099](./0099-Web形态的平台规则承载.md)（平台规则承载）、设计 02 §3.1／§3.4、设计 04 §3.1、设计 05 §2、方案 §13.4／§13.6／§13.10.2

## 背景

A3-1～A3-5 把 Web 的**计划面**做完了：19 个视图能在浏览器里出真计划，6 个按事实齐备度显式拒绝。但执行面一直是空的——`apply`/`undo` 在浏览器里**不存在**，界面因此禁用执行链（ADR-0104 的「真计划不配假执行」）。结果是：19 个视图能出计划、一个都不能执行。

设计 02 §3.1 原本写的路线是「OPFS 上实现 `FsAdapter`」。A3-6 动手前先核对这条路线的两个前提，发现都不成立：

1. **用户源文件根本不在 OPFS 里**。浏览器只能通过 File API 拿到用户选中的文件字节，那是**只读引用**，写不回原位置（§13.2「用户磁盘不可写」）。所以「在 OPFS 上实现 FsAdapter」即使做完，也只覆盖「产物落在 OPFS」，仍然要先解决「输入怎么进 OPFS」——而这一步本来就要读字节、写副本。
2. **OPFS 是异步的，内核执行器是同步的**。`FsAdapter` 的方法签名全同步，`generic_apply`／`apply_plan`／`undo` 都在同步栈上跑（不变量 1：内核不取时钟、不做 IO 调度）。要用 OPFS，就得把 `FsAdapter` 改成 `async` 或引入阻塞桥——前者是对已冻结契约（设计 04）的破坏性改动，后者在浏览器主线程上不可行、在 Worker 里会把执行器切成状态机。

而「能不能执行」对用户的差别，与「产物落在哪」无关：用户要的是**产物字节**。浏览器本来就只能以**下载**交付产物（§13.4 降级口径），OPFS 只是中间站。

## 决策

### 1. 会话内内存文件系统（`kernel::memfs::MemoryFs`）

`MemoryFs` 是 `FsAdapter` 的**第三个实现**（另两个：`platform::fs::CliFsAdapter`、测试用 `TestFs`），跑在同一个 trait 上，因此 `generic_apply`／`apply_plan`／`undo` **一行不改**就能对它执行——不变量 2「plan/apply 同一套内核代码」在 Web 形态照样成立。它实现的语义与桌面逐条对齐，不是「够用就行」的子集：

| 语义 | 桌面 `CliFsAdapter` | `MemoryFs` |
|---|---|---|
| 写目标自动建父目录 | 是 | 是（`ensure_parents`） |
| 冲突策略 `skip`／`overwrite`／`sequence` | `ConflictPolicy` | 同名三档；`sequence` 按 `name (1).ext` 递增 |
| 原子写 | 临时名 + rename | 先在临时键上写，成功后一次替换 |
| 删除 | 进隔离目录（不变量 7） | 进 `/.batchdesk-quarantine`，可从 Journal 还原 |
| `create_dir` | 只建单级 | 只建单级（多级由调用方逐级建） |
| `remove_dir_if_empty` | 非空拒绝 | 非空拒绝 |
| 区间复制 | `copy_range_atomic`／`copy_ranges_atomic` | 只写请求的切片；`copy_ranges_atomic` 的前缀只写一次 |

路径一律经 `path::try_normalize` 归一（反斜杠换正斜杠、相对路径补 `/`），所以 `out\a.txt` 与 `out/a.txt` 是同一个对象——桌面传进来的是哪种写法，沙箱里都能对上。

`MemoryJournal` 同理：`JournalSink`／`JournalStore` 的内存实现，语义与 `FileJournal` 一致，只是不落盘（会话结束即消失，符合 §11.4-13「Web 日志仅会话内」）。

### 2. 同步内核 ＋ 异步浏览器：执行前 staging

浏览器给字节是异步的（`File.arrayBuffer()`），内核执行是同步的。解法不是把内核改成异步，而是**把异步部分全部前移**：

```text
stage_inputs（异步读 File → 清单 + 拼接字节 → web_exec_stage）
        ↓  沙箱内已是同步文件系统
apply_plan（web_exec_apply → generic_apply/apply_plan，全程同步）
        ↓
web_exec_product（逐产物取字节 → 主线程 Blob → 下载）
```

`web_exec_stage(manifest, data)` 的 `manifest` 是 `[{path, length}]`，`data` 是按同序拼接的一段连续字节。**为什么拼接而不是逐文件传**：wasm-bindgen 的数组入参每个都要过一次边界，拼接后只过一次；偏移由调用方（Worker）算，那里本来就在遍历文件列表。长度与实际字节数不符**直接 E1002**（`expects N bytes`），不静默截断——清单与字节错位会让 `a.txt` 拿到 `b.txt` 的内容，而计划看起来完全正常。

### 3. 产物＝Journal forward 的落盘路径

产物不靠「按计划条目猜路径」：`undo` 需要的是真实落盘位置，而 `WriteAtomic{path}`／`Rename{to}`／`Copy{to}` 才是执行器真正写的地方。`Sandbox::product_paths()` 从本次执行的 Journal forward 条目取路径，**去重**（`copy_ranges_atomic` 的多区间会写同一目标）后用 `stat` 确认仍是文件——被后续条目删掉或改名的自然不出现。这样「产物列表」与「撤销能回滚什么」是同一份事实，不会各说一套。

### 4. 执行能力分档：只接 F01／F02／F03

执行比计划多要**端口**，不是多要字节。`WEB_APPLY_VIEWS = {f01, f02, f03}` 是当前唯一能装配齐的三个：

- 分片三兄弟只需要 `FsAdapter` ＋ 授权（沙箱注入 `AlwaysAllowLicense`），没有额外端口；
- C01/C02/C03 走 `edit-content`／`transcode`，要 `ContentEditor`／`ContentRewriter`；
- F10 要 `DirectoryLister`；C08/C10 要 `ArchiveService`。

这些端口在 Web 侧没有装配。假装能执行会在 `generic_apply` 中途报「端口未提供」，用户看到的是一次执行失败——不如在**按钮之前**就说清楚。因此 `webApplySupport(view)` 对未接线的视图返回 `{ level: "unsupported", gap: "not-wired" }`，界面继续显示「浏览器版仅生成计划」并禁用执行/撤销。

**这与 ADR-0105 的计划分档同构，但不共用一份表**：计划缺的是**事实**（目录树、全量哈希），执行缺的是**端口**。两者会随着后续批次各自收窄，合成一张表就会互相污染。

### 5. 撤销范围 `products-only`，界面照实说

`web_exec_undo(planId)` 走 `undo_plan_with_ports`，回滚的是沙箱内的写入（写回原内容、删掉新建文件、从隔离目录还原）。但**已经下载到用户磁盘的副本，浏览器收不回来**——这是平台事实，不是实现缺陷。设计 02 §3.4 的 `scope: "products-only"` 就是为此而设，本轮把它从契约文字变成界面文字：产物面板固定显示「撤销只回滚浏览器内产物，已下载的文件需要你自行删除」。

同理，撤销后**不**清空沙箱历史（`mark_reverted` 之后 Journal 仍在，只是条目标记已回滚），用户还能看到「这次执行做了什么」；`reset_sandbox` 才是清空（换输入、换视图时调用）。

### 6. §13.10.2 建议档：提示，不阻断

执行前用 `File.size` 统计总量与单文件最大值（**只读元数据，不读内容**），超档（单文件 > 100 MB 或总量 > 500 MB）弹确认框，确认后才 `stage_inputs`。这**不是**配额强制（零强制力，设计 05 §2）：数值只写在一处（`applyChannel.ts` 的两个常量），措辞是「可能较慢，建议分批」，不是「不允许」。拒绝确认＝不执行，但用户可以改小输入再来。

### 7. 零强制力在沙箱里同样成立

沙箱执行注入 `AlwaysAllowLicense`，`web_exec_*` 五个导出**不含任何授权、配额、试用期判定入口**（设计 05 §2 白名单：apply/undo/产物读取）。Web 形态本来就没有可强制的信任根（§13.2），沙箱不引入新的判定点。

## 后果

- **19 个视图里 3 个（F01/F02/F03）在浏览器里可真执行、真出产物、真撤销**，执行的是与桌面同一套内核代码（`generic_apply`／`apply_plan`／`undo`），不是模拟。
- 界面按 `planOrigin === "wasm"` 分叉：`canWebApply` 为真时执行按钮可用，执行后显示产物面板（摘要＋逐个下载＋下载全部）；否则保持 ADR-0104 的禁用链与「仅生成计划」横幅。**同一次计划不会同时走桌面与沙箱**。
- 产物交付只有一条路：下载。`saveProducts` 按**文件名**去重，重名加 `N-` 前缀（`part.txt` → `1-part.txt`）——按路径去重会漏掉「不同目录同名」的情况。
- `export_surface` 的反漂移断言升级：`EXEC_OPS`（4 个协议 op）↔ `EXEC_BINDINGS`（4 个绑定）↔ `lib.rs` 的 `web_exec_*`（5 个导出，`web_exec_product` 是取值器不是操作，单列期望）。漏登记一边即红。
- 沙箱是**会话级单例**（`static SANDBOX: Mutex<Option<Sandbox>>`）：Worker 里只有一个执行上下文，同时只有一个计划在跑；换输入即 `reset`，避免上一次的输入文件被下一次计划误用。
- **不引入 OPFS**，设计 02 §3.1 的 OPFS 路线**降级为「未采纳的可选后续」**：若将来要支持「产物留在浏览器里跨会话」「目录授权直写」，那是另一个量级的工程（异步适配层 + 权限模型），届时应另开 ADR 推翻本文 §1／§2。

## 备选方案

- **按设计 02 §3.1 原文上 OPFS（异步 FsAdapter）**：`FsAdapter` 全同步是已冻结契约（设计 04），改签名会波及 `platform`／`kernel`／`cli`／`src-tauri` 全部调用点与 496 项 kernel 测试；且 OPFS 只解决「产物存哪」，不解决「输入怎么进来」。收益（产物跨会话留存）与代价不成比例。
- **主线程里用 `FileReaderSync`／阻塞读**：`FileReaderSync` 只在 Worker 里可用，且沙箱本来就在 Worker 内；真正的阻塞点不是读字节，而是「读字节是异步 API」。staging 已把这个异步点隔离在一次调用里。
- **用 `TestFs` 顶替（测试用的内存 FS）**：`TestFs` 是测试替身，语义按测试需要裁剪（不做冲突策略、不隔离删除），拿它跑真实用户数据会把「测试能过」当成「用户能用」。`MemoryFs` 是**产品实现**，13 项单测逐条对齐桌面语义。
- **未接线视图也给「尽力执行」**：执行到一半报端口缺失，用户看到的是失败而不是「浏览器不支持」。宁可按钮禁用＋说明缺口（ADR-0105 的同一裁决）。
- **超建议档直接拒绝**：等于把 §13.10.2 的建议档偷偷变成硬配额，与零强制力（设计 05）冲突。选择提示＋确认后放行。
