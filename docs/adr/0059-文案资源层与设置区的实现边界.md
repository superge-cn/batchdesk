# 0059. 文案资源层与设置区的实现边界

- **状态**：已采纳（2026-11-03，P2「i18n／设置 UI」两项 UI 欠账落地）
- **日期**：2026-11-03
- **决策者**：开发代理（工程实现决策；语言集合、默认语言、key 形式、整句模板、持久化字段均为设计 09 §1／§2／§4 与设计 03 §4.1 已定契约，本 ADR 不改）
- **关联**：设计 09 v0.2（本篇即其"实现落地"记录）、设计 12 v0.18 §2、设计 03 §4.1（`general.language`／`general.theme`）；ADR-0004（生成绑定）、ADR-0045（前端测试两层）；`web/src/i18n.tsx`、`web/src/SettingsPage.tsx`、`scripts/check_locales.py`

---

## 1. 问题

设计 09 只定了**契约**（两语言、key 形式 `area.component.element`、两语言 key 集合必须完全一致、整句＋占位符、选择写 `general.language`、切换即时生效），没定**实现**。落地时要回答六个问题：

1. 是否引入第三方 i18n 库（i18next／react-i18next／FormatJS）；
2. key 拼错如何在**编译期**就拦住，而不是等用户看到 `settings.saveErrro`；
3. "两语言 key 集合一致""禁止硬编码"如何变成 CI 可判定，且不误伤假数据与输入解析；
4. 语言/主题是"配置项"（走 `setConfig`）又要"即时生效"，两者如何不打架；
5. 首帧语言从哪来——等待 `getConfig` 会让每个组件测试都要 mock 异步；
6. 设置区五组 40+ 字段，如何不写成五份复制粘贴。

## 2. 候选与结论

| 议题 | 候选 | 结论 |
|---|---|---|
| i18n 库 | a) i18next＋react-i18next；b) 自写 Provider（约 230 行） | **b**。AGENTS §9 要求新增依赖先过许可/理由；本需求面只有"两语言、key 查找、占位符插值、持久化"四件事，i18next 的复数、命名空间、后端加载、语言探测、`Suspense` 全用不上。自写换来两条硬收益：`MessageKey = keyof typeof zhCN` 让 TS 直接拦住拼错的 key；零运行时依赖 |
| key 约束 | a) 只靠门禁脚本；b) 类型级 `MessageKey`＋脚本双保险 | **b**。类型级给开发者即时反馈（编辑器/`tsc` 报错）；脚本兜住类型逃逸（`t(\`c09.${x}\`)` 这类模板串在 TS 里会被推断成 `string`）与语言包缺 key。两者缺一都能漏 |
| 缺失 key 的回退 | a) 抛错白屏；b) 直接渲染 key；c) 回退默认语言＋DEV 告警；d) 回退默认语言且静默 | **c**。设计 09 §4 明确"不得显示空白界面"：生产回退 `zh-CN`（同 key 在中文本就存在），DEV 下 `console.warn` 让漏 key 在开发期可见；两级都失败才渲染 key 本身（最后一道兜底，宁可难看也不要空白） |
| 插值 | a) 引入模板库；b) 正则替 `{name}`，缺参**保留占位符** | **b**。设计 09 §2 规则 4 已禁止片段拼接、只允许"整句＋占位符"；缺参保留原样（不渲染 `undefined`）让漏参在界面上可见而不炸——`{count} 项` 比 `undefined 项` 更接近真相 |
| 持久化 | a) `localStorage`；b) `setConfig("general", {language})` | **b**。设计 09 §4 指定 `general.language`，设计 03 已有 `SettingValue.effectiveSource` 来源追踪；`localStorage` 会造出第二份真相，且桌面/Web 两形态行为分叉 |
| 首帧语言 | a) 首帧 `zh-CN` 再异步回读；b) 阻塞渲染直到 `getConfig` 返回 | **a＋回读**。b 会让每个组件测试与首屏都要等一个异步，且 `getConfig` 是本地存储读、延迟在毫秒级；代价是英文用户启动瞬间闪一次中文（见 §4）。测试与首帧用 `initialLang`/`initialTheme`/`persist` 三个可选 prop 注入，不必 mock 异步 |
| 主题归属 | a) 主题留在 `App` 本地 state（原状）；b) 与语言同放 Provider | **b**。两者是同形问题（偏好 → 根元素属性 → 写 `general`），放一起只需一处 `matchMedia` 监听与一处持久化；分开放会出现"语言写了盘、主题没写"这类半截状态 |
| 设置区结构 | a) 五组各写一份 JSX；b) 数据驱动注册表 `SCOPES: ScopeDef[]` | **b**。逐字段都要 label／hint／来源标记／变更分派，注册表让"加字段＝加一行"；也让 Playwright/Vitest 能按 `labelKey` 稳定定位 |
| 变更分派 | a) 每字段自带 `onChange`；b) 按 `FieldKind`（`select`/`text`/`number`/`auto`/`boolean`/`lines`）分派 | **b**。六种 kind 覆盖五组全部字段；`language`/`theme` 两种走 `setLang`/`setTheme`（即时生效＋写盘），其余走 `setConfig`；空串归一为 `null`（清用户档回落默认），`auto` 保留字面量 `"auto"` |
| 门禁形态 | a) 只查两语言 key 集合相等；b) 七项检查＋三类显式例外 | **b**。只查集合会漏"英文里残留中文""占位符集合不一致""源码引用了不存在的 key"三类真实缺陷；例外必须**整体豁免＋写理由**（浏览器假数据不是产品文案），单行用行尾 `// i18n-exempt` |

## 3. 实现

**资源与运行时**

- `web/src/locales/zh-CN.json`、`en-US.json`：395 key × 2 语言，key 集合逐字节一致。域前缀 `app.*`／`nav.*`／`common.*`／`task.*`／`c09.*`／`feature.*`／`tasks.*`／`settings.*`。
- `web/src/i18n.tsx`：`Lang`／`ThemePref`／`ResolvedTheme`／`MessageKey`／`DEFAULT_LANG`／`LANGS`／`interpolate`／`translate`／`isLang`／`isThemePref`／`I18nProvider`／`useI18n`。Provider 首帧 `getConfig("general")` 回读，`setLang`/`setTheme` 即时 `setState` ＋ `setConfig`；同步 `document.documentElement.lang` 与 `dataset.theme`；`system` 主题订阅 `matchMedia`。
- `useI18n()` 在无 Provider 时返回默认中文翻译器——组件单挂不炸，单测不必包 Provider。

**设置区**

- `web/src/SettingsPage.tsx`：五组并行 `getConfig(scope)` → `ScopeView`，逐字段渲染来源标记（`settings.source.user`／`settings.source.default`）；`reset(scope)` 走 `resetScope`（`general` 组重置后同步把语言/主题回到默认）；`E1007`（高版本只读）置只读横幅并回读，不静默吞掉。

**门禁**

- `scripts/check_locales.py`（仅标准库，与 `check_docs.py` 同风格）七项：① 两文件存在且为 JSON 对象；② key 集合完全一致；③ 值非空；④ 同 key 占位符集合一致；⑤ 非默认语言不残留中日韩字符；⑥ 源码引用的 key 都存在；⑦ 注释外无硬编码中文（`strip_comments` 手写状态机区分行注释/块注释/字符串/模板串）。三类例外：`web/src/locales/`（语言包本身）、`web/src/lib/ipc/mock.ts`（浏览器假数据）、`*.test.tsx`／`*.test.ts`；单行例外用行尾 `// i18n-exempt`。
- CI 两处调用：`test` job 的「文档一致性」段之后、`web` job 的「类型检查与构建」之前（`working-directory: web`）。

**验证**：`tsc --noEmit` 0 错、`vite build` 通过、Vitest 10 文件 **44 项**（`i18n.test.tsx` 7＋`SettingsPage.test.tsx` 5＋既有 32）、Playwright **15 项**（新增 `e2e/settings-i18n.spec.ts` 1 项）、`check_locales.py` exit 0。

## 4. 已接受的坑与边界

- **首帧闪一次中文**：英文用户启动时先渲染 `zh-CN` 再回读成 `en-US`。要在首帧就正确，必须在挂载前同步读配置（阻塞首屏）或把语言塞进 `index.html` 的服务端注入——两者都超出本批范围。桌面 `getConfig` 是本机 SQLite/JSON 读，闪动窗口约一帧到两帧，接受。
- **写盘失败只 `console.warn`，不阻断界面**：语言/主题是"看的选择"，用户点英文就该立刻看到英文；写盘失败的下次启动会回到旧值，但那比"点了没反应"好。这里刻意不弹错误——它是设置里唯一允许静默失败的路径，因为失败后果可逆且无数据风险。
- **错误码专用 key（`error.<code>.*`）仍未建**：设计 09 §5 要求"每个码位在中英文都有 summary/detail/action"，现在错误文案仍是壳层返回的 `message` 串直接呈现（外围再包一层 `settings.saveError` 这类整句模板）。这是 09 的**剩余缺口**，不是"错误文案已国际化"——映射表与台账不得写成已完成。
- **门禁的 key 域是硬编码清单**：`KEY_DOMAIN_RE` 只认 `app|nav|common|task|c09|feature|tasks|settings` 八个前缀。新增域必须同步登记，否则第 ⑥ 项检查会漏掉该域的引用。
- **`mock.ts` 整体豁免**：浏览器假数据里的中文永远不会被第 ⑦ 项发现。这是有意的——把夹具文案也资源化会让"假数据"与"产品文案"混在一个文件里；代价是假数据可以随便写中文。
- **英文排版只做了"存在性与可点"断言**：I18N-04 要求"不遮挡、不溢出"，实际只断言了关键控件 `boundingBox` 非零且可点，没有逐按钮的溢出/换行断言。真正的排版验收仍需人工/env 实机。
- **设计 09 §6 的 I18N-01…08 尚未进 TC 实例库**：TC v0.4 里 `I18N` 出现 0 次，映射表也没有 I18N 行。本轮只落实现与门禁，8 条用例的覆盖是"部分对应"（默认语言、切换、持久化、缺 key 回退有自动化；错误码文案、日期 locale、长文案排版没有）。
- **设置区不含 C37 Phase B 的模板 UI**：设置页只读写设计 03 的五个可写 scope；`Recipe` 的 CRUD/导入导出是另一件事（Wave 4）。
- **UiState 未接**：窗口/布局/最近目录的写入仍是后置项，设置区只管 Config。

## 5. 验证与"先红"说明

本轮是**新增能力**，没有"既有行为错误"可作红色信号，故不以红→绿收尾。改用两条替代证据：

1. **门禁脚本首跑红 18 处**——`SettingsPage` 两处模板串拼接（`${t(...)}：${message}`）、`FeaturePages` 的输入解析字面量 `"无"`、`mock.ts` 夹具文案均被第 ⑦ 项抓到，逐条修正（整句模板／行尾豁免／整体豁免）后才绿。这证明该门禁不是空转。
2. **`translate` 的缺 key 路径有单测**：`i18n.test.tsx` 断言"渲染结果里不得出现 raw key"，并断言缺参时占位符原样保留。
