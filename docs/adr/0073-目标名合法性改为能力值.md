# 0073. 目标名合法性改成「能力值」注入，内核不再写死 Windows 规则

- **状态**：已采纳
- **日期**：2026-11-05
- **决策者**：开发代理（工程实现决策）
- **关联**：[设计 04 §2／§2.1](./../design/04-文件系统适配层契约.md)、[设计 01 §4.1](./../design/01-内核接口与IPC契约.md)、[方案 v1.19 §4.7／§5.13](./../baseline/产品方案-v1.19.md)、[ADR-0012](./0012-Windows文件身份改用WinAPI.md)（同为「平台事实经端口注入」）、[ADR-0072](./0072-处理模板前端只做存取半边.md)

## 1. 问题背景

`crates/kernel/src/conflict.rs` 的 `validate_target_name` 从 F12 切片那天起就带两个**常量**：

```rust
const RESERVED_NAMES: &[&str] = &["CON", "PRN", "AUX", "NUL", "COM1"…];
const INVALID_CHARS: &[char] = &['<', '>', ':', '"', '|', '?', '*'];
```

配一句 `ch.is_ascii_control()`，没有任何平台判断地作用于所有调用方。它在四个地方拦人：

| 调用点 | 后果（在 Linux 上） |
|---|---|
| `rename.rs` 计划期 | 目标名命中即 `E1002 target name is not allowed`，条目被 blocked |
| `conflict.rs::scan_conflicts` | 预览期报 `reserved-name`／`invalid-char`／`trailing-dot-space` 警告 |
| `create_dirs.rs`（F11） | 清单里含这些字符的行整行进 `invalid-rows`，目录建不出来 |
| `archive.rs`（C10 解压） | ZIP 条目名被判"不安全"，整条跳过 |

而 POSIX 的文件名里**只有 `/` 和 NUL 不可出现**：`CON.txt`、`报告:2026.csv`、`notes.`、`notes␣` 都是合法文件名。也就是说，Linux 上「把一批文件重命名成含冒号的名字」「按清单建带点的目录」「解压一个含 `CON.txt` 的压缩包」这三件事，今天全是**被自己的规则挡住**，报的还是 `E1002`（参数非法）——用户看不出这是平台差异。

同一批还查出第二个缺陷：`platform/src/fs.rs` 的 `case_sensitivity()` 写成 `if cfg!(windows) { CaseInsensitive } else { Sensitive }`。macOS 的 APFS 默认**不区分大小写**，设计 04 §2 的平台表也写着「Windows / macOS → Insensitive」，代码却把 macOS 归到 Linux 那一档。后果不是报错而是**静默走错分支**：macOS 上 `a.txt → A.txt` 被当成两个不同名字，唯一性校验不判定占用、两阶段改名不触发，批内一次改名就可能撞名。

## 2. 候选与否决理由

| 候选 | 做法 | 结论 |
|---|---|---|
| A. 内核里判平台 | `if cfg!(windows) { … }` | **否决**。违反不变量 1（内核纯函数、环境事实经端口注入）与设计 04 §2 明写的「不写平台 if/else」；内核还要编到 WASM/OPFS；更要命的是测试只能覆盖编译它的那个平台——本次所有新用例都会退化成「在 CI 上只验了一个平台」 |
| B. 构建期开关 | cargo feature／`BATCHDESK_NAME_RULES` 环境变量 | **否决**。行为由产物或用户环境决定，同一份二进制无法按卷表达差异（Linux 挂 FAT/NTFS、macOS 挂 exFAT 都是真实场景）；feature 组合还要进 CI 矩阵 |
| C. 能力值注入 | 内核定义 `NameRules` 数据结构，适配层给出值，经计划输入注入 | **选定**。与 `CaseSense`／`long_path_supported` 同一个模式（已有先例），内核零平台判断，两套规则可在同一台机器上同时被测试 |
| D. 按卷探测 | 在计划根路径上探测（大小写翻转 `stat`、试写临时文件） | **本轮不做**。需要真实卷与现存条目（空目录无从探）、每个计划多一次 IO；它与 macOS/Linux 批次一起做，见 §5 残余 |

## 3. 决策

1. **`NameRules` 是数据，不是判断**（`kernel::conflict`）：

   ```rust
   pub struct NameRules {
       pub illegal_chars: &'static [char],   // 只列这些，不做额外推断
       pub reject_control_chars: bool,       // Windows 禁控制字符；POSIX 只禁 NUL
       pub reserved_names: &'static [&'static str],
       pub trailing_dot_space: bool,
   }
   impl NameRules { pub const fn windows() -> Self; pub const fn posix() -> Self; }
   ```

   `posix()` 的 `illegal_chars` 是 `['/', '\0']`、无保留名、`trailing_dot_space=false`。
   `validate_target_name(name, rules)` 与 `scan_conflicts(…, rules)` 改为接收规则值。

2. **规则随计划输入一起走**：`PlanF12Input`／`PlanF13Input`／`PlanC04Input`／`PlanF11Input`／`PlanC10Input` 各加 `name_rules`；F12/F13/C04 共用 `RenamePlanContext`，所以没有第三个入口。

3. **apply 期也要同一套**：`ApplyContext` 与 `ArchiveApplyContext` 各加 `name_rules`。C10 在 apply 期会重算 `select_entries`（报告与限额要用），若计划期用 POSIX、执行期用 Windows，就会出现「计划选中、执行判不安全」的分叉。这条与 `case_sense` 同处理：**环境事实两期都注入，不从计划文件里读**。

4. **端口只做采集**：`FsAdapter` 增 `fn name_rules(&self) -> NameRules;`；`platform::fs::name_rules()` 落成 `windows → windows()`、其余 → `posix()`。壳层与 CLI 在各计划入口调用它（纯函数，不触盘）。测试替身 `TestFs` 返回 `posix()`——与它一贯的 `CaseSense::Sensitive` 同一个前提，不是随手填的。

5. **空名/纯空白名对所有平台都拒绝**：这是产品级「无意义名」，不是平台规则。写进本条是为了下次不要把它当成"平台判断漏改"又搬进 `NameRules`。

6. **顺带修 macOS 的大小写能力**：`case_sensitivity()` 改为 `windows || macos → CaseInsensitive`，并抽成 `platform::fs::case_sensitivity()`，trait 方法委派。这是适配层该知道的平台先验（设计 04 §2 的平台表就是它），不属于「内核判平台」那条禁令。

## 4. 后果

- **内核**：`conflict` 新增 `NameRules` 与 4 条用例（POSIX 放行 Windows 专有名、POSIX 只拦 `/` 与 NUL、空名两套都拒、`scan_conflicts` 对 POSIX 合法名沉默）；`rename` 新增 1 条端到端回归（`CON.txt` 改扩展名：POSIX 出条目、Windows 仍 `E1002`）。kernel 413 → 418。
- **平台**：2 条能力用例（`name_rules_follow_the_host_platform`、`case_sensitivity_follows_the_host_platform`），后者三个平台各自成立——macOS 分支目前没有 CI job 跑，属残余。platform 103 → 105。
- **CLI**：`f12_reports_existing_conflicts_and_invalid_targets` **先红**——它原来用 `CON` 断言 `E1002`，在 Linux 上这条断言本来就靠"内核写死 Windows 规则"才成立。现拆成两半：`a/b`（两边都非法，与平台无关）＋ `CON`（`assert_eq!(blocked, cfg!(windows))`）。这条是本批次最有说服力的证据：**一个跨平台语义缺陷，是既有用例的假绿替它兜着的**。
- **代价**：5 个计划输入 + 2 个执行上下文各多一个字段（`Default` 不适用，字面量必须写全）；壳层/CLI 每处计划入口多一行采集。没有 IO 开销，也没有序列化变化——`name_rules` 不进 `plan.params`，计划 JSON 与计划幂等 harness 不受影响。
- **不变**：`E1002` 的语义（参数非法）与提示文案未改；`blocked` 机制、两阶段编排、长路径分级都没动。

## 5. 残余

1. **macOS 无 CI job**：`case_sensitivity` 的 macOS 分支只有代码与设计表一致，没有机器验过。macOS 批次启动时先把 `test`／`desktop` job 的 `runs-on` 加上 `macos-latest`。
2. **按卷探测未做**（候选 D）：大小写敏感的 APFS 卷、开了 casefold 的 ext4 目录、Linux 上挂的 FAT/NTFS 卷，当前一律按**平台**判定。要修就得把能力从 `case_sensitivity()` 改成 `case_sensitivity_at(root)`，并在计划入口传根路径——留到 macOS/Linux 批次，与「平台保护目录」一起做。
3. **C07／C08 不过名称校验**：它们的名字来自现存文件或用户清单行，本轮不接线；若将来 C07 允许改目标名，必须同步接 `name_rules`。
4. **F11 的 POSIX 语义变宽**：清单里 `a:b` 这类行现在能建出目录（以前整行进 `invalid-rows`）。这是修正，但会改变 T 语料里人工项的预期值——Windows 实机日按 Windows 规则跑，结论不变。
