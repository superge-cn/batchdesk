# 0107. C10 压缩侧接上 ＋ Web 计划缺口枚举收敛

- 日期：2026-11-22
- 状态：**已采纳**（A3-5 落地：WASM `plan_c10_compress`、`contract.ts` 的 `EXTRA_PLAN_OPS`、Web `mode=compress` 分支、`sources` 多文件槽；视图档位不变 **19 `native` ／ 6 `unsupported`**，缺口枚举删去 `archive-compress`）
- 相关：[ADR-0105](./0105-Web计划能力矩阵按事实齐备度分档.md)（能力分档）、[ADR-0104](./0104-Web计划通道真计划不配假执行.md)（计划通道）、[ADR-0103](./0103-C10-Web侧条目清单零依赖中央目录读取.md)（解压侧条目事实）、[ADR-0080](./0080-OQ41裁决二与套用映射表.md)（`mode` 必须随计划保存）、ADR-0074（密码只传一位）、设计 02 §2.1／§3.1、设计 04 §3.1、方案 §5.13（ZIP）

## 背景

A3-3 把 C10 解压侧接成 `native` 时，压缩侧被单列为缺口 `archive-compress`，理由是
「`plan_c10_compress` 未导出，且浏览器没有本地目录打包的事实源」。A3-4 之后再看，
这个理由只有前半句成立：

1. **导出是纯增量**：`kernel::archive::plan_c10_compress` 早已实现并有单测，缺的只是
   WASM 绑定与 Web 消费；内核输入只要「源清单 ＋ 文件数 ＋ 总字节 ＋ 输出路径」，
   这些浏览器都能从用户选中的 `File` 直接拿到。
2. **「本地目录打包」不是计划期事实**：计划只写「把哪些源压到哪个输出」，
   真正的打包发生在执行期（`apply_archive_plan`），而 Web 执行器本就未实现。
   把「执行没做」当成「计划不能算」，是把两件事混成了一件——解压侧同样是
   只出计划、不解包。
3. **缺口枚举也失真**：`archive-compress` 只服务一个视图的一个模式，却与
   「缺目录树」「缺全量哈希」并列，让人误以为 C10 整体不可用。

## 决策

### 1. 导出 `plan_c10_compress`，与解压共用 C10 视图

新增 `crates/wasm::plan_c10_compress`（core 版本便于 native 测试）。入参：

| 字段 | 来源 | 约束 |
|---|---|---|
| `output` | 表单 `output` | 必填；与源同路径/落在源目录内由内核阻断（E1002） |
| `sources` | 选中文件的相对路径 | 至少一条（内核 E1001） |
| `compression` | 表单 `compression` | 缺省 `deflate`（与 CLI 一致）；未知值 E1002 |
| `sourceFileCount` / `sourceBytes` | 浏览器统计 | **必填**（E1001） |
| `targetExists` | 恒 `false` | 浏览器无产物 FS 可查 |
| `protectedDirs` / `caseSense` | 恒空／POSIX | 与解压侧同口径 |

**为什么不给 `sourceFileCount`/`sourceBytes` 默认值**：缺省成 0 会生成
「compress 0 files, 0 bytes -> deflate ZIP」这种计划——格式完全正常、条目也有一条，
但显示的数量与用户选的文件无关。这与 `WebArchiveEntry.supported` 不加
`serde(default)` 是同一条理由：**缺事实就报错，不产出看起来正常的错计划**。

### 2. 契约层把「同视图第二条计划」单列

`PLAN_OPS` 保持「一功能一入口」的 25 项；新增 `EXTRA_PLAN_OPS = ["plan_c10_compress"]`，
`PlanOp` 取并集，`PLAN_OPS_COVERAGE` 仍覆盖全部导出。这样：

- 「25 个功能入口」的计数不与「C10 有两个模式」互相污染；
- 导出面反漂移断言从「`PLAN_OPS` ＝ Rust 导出」升级为「`PLAN_OPS ∪ EXTRA_PLAN_OPS`
  ＝ Rust 导出」——漏登记一边仍然编译/测试失败。

### 3. Web 侧：按模式选槽，不摊平

`planC10` 直接收分槽的 `PickedFiles`（与 C07 同形）：

- `mode=compress` → `sources` 槽（多文件选择器）＋ `output`；
- 其余 → `archive` 槽（单文件选择器）＋ `outputDir`／限额。

若走 `viaFiles` 摊平，两份输入会合成一个数组：只能靠扩展名猜谁是压缩包，
猜错就解错对象。`planWithFiles`（单输入便捷入口）为此增加按视图/模式解析槽名的
逻辑，并对 C07 直接拒绝（它有两份独立输入，单槽表达不了）。

### 4. 删掉 `archive-compress` 缺口

`WebPlanGap` 收敛为 `directory-walk`／`content-hash`／`pending-wiring` 三类。
前两类是**浏览器采不到的事实**，第三类只用于未登记视图的保守回退——
不再有「某功能的一半算不了」这种档位。

## 后果

- C10 在 Web 双向可用（解压＋压缩），视图档位仍是 19／6：**档位是视图级的**，
  压缩侧接上不会把 C10 从 `native` 再升级一次。
- 压缩计划仍**不能执行**（Web 无 OPFS 执行器，设计 02 §3.1）——界面继续禁用执行链。
  这是「真计划不配假执行」的同一裁决（ADR-0104），不是本 ADR 的遗留。
- 能力边界如实记录：`targetExists` 恒 false、整目录压缩不在 Web 能力内
  （拿不到目录树）、`sources` 仅来自用户显式选中的文件。
- 新增语言包键 `feature.field.mode.hint`、`feature.field.compressOutput.webHint`、
  `feature.field.sources.webHint`；删除死键 `feature.plan.gap.archiveCompress`。

## 备选方案

- **让压缩继续拒绝，只做执行器**：拒绝的理由是「没有事实源」，但事实源就是用户选中的
  文件，这个理由不成立；保留拒绝会让 C10 的一半永远不可用。
- **把 `plan_c10_compress` 塞进 `PLAN_OPS`**：会让「25 个功能入口」变成 26，
  下游计数（文档、测试、导出面断言）全部要重新解释，且语义上它不是新功能。
- **压缩计划也预判 `targetExists`**：浏览器没有产物 FS，只能猜；猜 false 是
  「不预判」，猜 true 会直接 skip 掉正确计划。选择不预判并明示。
