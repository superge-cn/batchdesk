# 0103. C10 Web 侧条目清单：零依赖中央目录读取

- 日期：2026-11-21
- 状态：**已采纳·全链路落地**（`web/src/lib/web/zipIndex.ts` 10 项对拍测试＋WASM `plan_c10`
  导出＋`PLAN_OPS` 清单↔Rust 源码对拍；2026-11-21 A2-7 收口，功能面 25/25）
- 相关：设计 02 §2（事实采集层）、设计 05 §2（导出面白/黑名单）、[ADR-0074](./0074-C10密码包的秘密注入面.md)（密码只在执行期）、[ADR-0099](./0099-Web形态的平台规则承载.md)、[ADR-0102](./0102-字节级探测算法下沉kernel.md)；AGENTS 不变量 9（依赖治理）/11（Web 零强制力）

## 背景

A2-6 收尾时 C10 被判**阻塞**并如实记在台账里：

> C10 的输入是**压缩包内条目**（`ArchiveEntryInfo`：名称/类型/大小/路径安全性）。
> 浏览器没有解压能力，File API 也拿不到包内清单——采不到事实就出不了真计划。
> 需先定「Web 侧压缩包读取」方案。

本 ADR 就是那个方案。调研的结论是：**当时的阻塞判断把「解压」和「列清单」混为一谈了。**

## 问题拆解：C10 的计划阶段只需要中央目录

`plan_c10(PlanC10Input)` 的事实依赖只有三项（`crates/kernel/src/archive.rs:160`）：

| 字段 | 来源 | 浏览器能否拿到 |
|---|---|---|
| `archive_size` | 文件大小 | ✅ `File.size` |
| `entries[]` | ZIP **中央目录**的十个字段 | ✅ 见下 |
| `existing_targets` | 目标目录已存在路径 | ❌ 无目录遍历（与 F10/F11 同一能力缺口） |

而 `entries[]` 的十个字段里，**没有一个需要解压数据**：

```
index / name / kind / size / compressed_size / gbk_fallback / encrypted / supported
```

解压是 `apply` 阶段的事，而 Web 侧 `apply` 本来就因为 **OPFS FsAdapter 未实现**而
不存在（设计 02 §3.1）。也就是说：**计划只需要读中央目录；读中央目录不需要解压器。**

## 候选方案

| 方案 | 代价 | 结论 |
|---|---|---|
| ① 引 JS 解压库（fflate / @zip.js/zip.js） | 入口都是「解出内容」：小包会把整包读进内存并解码全部条目；`@zip.js` 约 200 KB 且带 worker/stream 机制。要过依赖与许可证评审（不变量 9），而只用到它 5% 的能力 | **否决**：用不上的能力＋供应链面 |
| ② **零依赖读中央目录**（本决策） | ~330 行 TS（含 Zip64/GB18030/AES 方法还原）；语义要与桌面逐字段对齐，**必须对拍** | **采纳** |
| ③ 服务端预解析（设计 07） | 把「能否出计划」绑到一个**尚未存在**的服务上；且要传整包或条目清单过网 | **否决**（现阶段）：等设计 07 落地再评估，不作为前置 |
| ④ 不接 C10 | 功能面永久缺 1/25；与「23 功能对齐」的收口目标冲突 | **否决**：能做而放弃 |

选 ② 的关键理由不是"省一个依赖"，而是**代价不对称**：中央目录是 ZIP 规范里
稳定、自描述的一段（签名＋固定字段），解析它的风险远低于引入一个会执行解压
状态机的第三方依赖；而如果将来 Web 侧真要做 `apply`（OPFS FsAdapter），届时
再引解压库是**另一个决策**（那时才需要真的解码字节），不会被本决策挡住。

## 决策

新增 `web/src/lib/web/zipIndex.ts`：`readZipEntriesFromFile(blob)` **只做两次随机读**
——末尾窗口（≤ 64 KiB，定位 EOCD）＋中央目录本体，不读任何条目数据。4 GB 的包
在浏览器里的读取量仍是几 MB。

与桌面 `platform::archive::ZipArchiveService::inspect` **逐字段同口径**（对着
`zip` crate 9.1.3 的实现核过，不是凭文档）：

| 字段 | 桌面口径 | 本模块 |
|---|---|---|
| `encrypted` | 通用标志位 **bit 0**（`ZipFlags::Encrypted`） | 同 |
| `supported` | `compression()` ∈ {Stored, Deflated} | 同，**且 AES 先还原真实方法**（见下） |
| `kind` | 原始名末字节 `/` 或 `\`（`zip::format::functions::is_dir`） | 同（看**原始字节**，先于解码） |
| `name` | bit 11 → 严格 UTF-8；全 ASCII 直读；否则 **GB18030** | 同（浏览器 `TextDecoder("gb18030")`） |
| `gbk_fallback` | 走了 GB18030 回退即 true（含解码失败） | 同 |
| `size` / `compressed_size` | 中央目录原值；哨兵值读 Zip64 扩展（0x0001） | 同 |
| `index` | 中央目录顺序号 | 同 |
| 读失败 | `E3003`「archive cannot be read」 | 同码 |

### 调研抓到的一处**真偏差**（本 ADR 最值得留的部分）

第一版把「方法 99（AES）」直接判为 `supported=false`，理由是桌面写的是
`matches!(Stored | Deflated)`。**这是错的**——桌面探针实测 AES 夹具的
`compression()` 是 `Stored`：

```
== fixtures/archive/password/aes256.zip
  idx=0 name=Some("a.txt") … enc=true sup=true     ← 桌面判"支持"
```

根因：AES 条目在中央目录把方法写成 **99**，真实方法藏在 AES 扩展字段
（0x9901）的数据区第 6–7 字节；`zip` crate 在解析时把它**还原**成真实方法
（`src/extra_fields/aex_encryption.rs` 的 `parse` → `CompressionMethod`）。
只认 99 会导致「加密包在 Web 侧条目全被跳过」——而 `select_entries` 对
`supported=false` 是**静默 continue**，计划会安静地少掉全部条目。

已修：方法为 99 且有 0x9901 扩展时，`supported` 按扩展里的真实方法判定；
无该扩展时保持 99（不支持）。测试用合成条目钉住「deflate → true / bzip2 → false /
无扩展 → false」。

## 证据（怎么验的，可复核）

1. **桌面真值**：临时探针（`crates/platform` 的 example，跑完即删）打印
   `inspect()` 对四个夹具的输出——Z01（GBK 名）、Z02（穿越）、ZipCrypto、AES-256。
2. **浏览器侧**：`web/src/lib/web/zipIndex.test.ts` **10 项**逐字段比对，四个夹具
   的期望值直接取自上面那次探针输出（不是"看代码猜的"）。
3. 覆盖到的形态：GBK 回退（Z01，`中文资料.txt`，77 字节）、UTF-8 标志位（Z02 三条
   含 `../escape.txt`）、ZipCrypto（`enc=true, sup=true, csize>size`）、
   AES-256（99 → 还原为 `Stored`）、目录条目（`/` 与 `\`）、非 ZIP 与超短文件
   （`E3003`）、Zip64 扩展（`size=5e9` 不截断）、条目数与结束记录不符（拒绝）。

```
Test Files  1 passed (1)
     Tests  10 passed (10)      ← vitest，2.17 s
```

## 已知偏差与能力差异（如实记录）

| 项 | 差异 | 影响 |
|---|---|---|
| GB18030 解码 | Rust 用 `Abort`（失败 → `None`）；`TextDecoder` 有损（坏字节 → U+FFFD 不报错） | 本模块把「含 U+FFFD」判为 `null`，与桌面**同向**（`None` 进 `unsafe_names` 被拦下，保守） |
| `existing_targets` | 浏览器无目录遍历 | 恒空 → 目标已存在的冲突**预览不出来**（与 F10/F11 同一缺口） |
| `protected_dirs` | 浏览器无系统目录概念 | 由调用方给空 |
| `case_sense` | 无法探测目标卷 | 与桌面同取 `Sensitive`（不猜） |
| `password_provided` | 只是「执行期会不会给密码」的事实 | 由调用方声明；**密码本身不进计划**（ADR-0074） |
| 本地文件头校验 | 只读中央目录，不校验本地头与 CD 是否一致 | 与桌面 `inspect` 等价（它也只看 CD）；损坏包在 `apply` 才暴露 |
| Zip64 | 只覆「扩展字段里的尺寸」路径 | 端到端未造 Zip64 夹具，靠单元测试钉住扩展解析 |

## 不做（明确边界）

- **不解压、不写盘、不校验密码**——这些是 `apply` 的事，且 `apply` 仍缺 OPFS FsAdapter；
- **不做 ZIP 内容安全判定**：路径穿越由内核 `select_entries` 拦（Z02 的
  `../escape.txt` 原样进事实层，内核记 `unsafe_names`），事实层**不预先过滤**——
  否则内核的拦截逻辑就永远测不到真实输入；
- **不引任何解压库**：将来做 Web `apply` 时另议（那时需要真解码）。

## 推翻条件

- 需要在 Web 侧**执行**解压（OPFS FsAdapter 落地）→ 需重新评估解压库（本决策只管计划阶段）；
- ZIP 规范出现本模块未覆盖的结构（如分卷、加密中央目录）→ 补测试或改用库；
- 服务端（设计 07）开始提供预解析 → 可省掉本模块，但那时的取舍是「省前端代码 vs 多一次上传」。
