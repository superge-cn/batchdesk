# 0110. CSV 行列变换族的执行面：输出路径按表单目录派生

- 日期：2026-11-22
- 状态：**已采纳**（A3-8 落地：`crates/wasm` 的 7 个计划入口接受 `outputDir`，目标路径＝输出目录＋源文件名；`skip` 不再自我跳过；执行档位从 9 个视图扩到 **16 个**）
- 相关：[ADR-0109](./0109-Web执行面扩到九视图与改写器端口在沙箱内构造.md)（本文修掉它登记的那一类缺口）、[ADR-0108](./0108-Web执行沙箱与产物下载.md)（沙箱执行与产物下载）、[ADR-0105](./0105-Web计划能力矩阵按事实齐备度分档.md)（计划分档）、设计 01 §5（`--output-dir` 的派生口径）、设计 02 §3.1.1

## 背景

A3-7 把 F07–F09／C11–C14 归为 `target-in-place`，判断是「计划把输出指向源文件自身」，并把原因写成「表单的 `outputDir` 没进计划」。A3-8 顺着这条线索查下去，发现缺口在**两端各一半**：

1. **前端根本没传**：`planChannel.ts` 里 F07 的注释就写着「Web 不传输出目录」，七个 mapper 的 payload 都没有连接目录字段（表单有输入框，值被丢掉）。
2. **后端也不认**：`crates/wasm` 的七个 `plan_c1X_core`／`plan_f0X_core` 的 `Params` 里没有该字段（serde 忽略未知字段），循环里直接写 `let output = file.path.clone()`。

任一端单独修都不够：只改前端会被 serde 丢掉，只改后端收不到值。两处同时接上，计划里的目标才真的落在输出目录。

## 决策

### 1. 目标路径在 wire 层派生，不在前端拼

`Params` 增可选 `outputDir`（camelCase 线协议），由 `web_output_path(output_dir, source)` 统一派生：

| 输入 | 结果 | 说明 |
|---|---|---|
| `"/out"` | `/out/a.csv` | 常规 |
| `out\sub\` | `/out/sub/a.csv` | 反斜杠换正斜杠、去尾斜杠、补前导斜杠 |
| `""` / 缺省 | `/out/a.csv` | 沙箱默认输出目录 |

理由：**路径归一只能有一处**。前端拼一次、后端再归一一次，两边口径一漂移就会出现「计划里写 `/out/x.csv`、staging 里是 `x.csv`」这类只在某些输入下复现的错位。派生规则与 `MemoryFs` 的键空间一致（`out` 与 `/out` 是同一个目录），也与桌面 CLI 的 `--output-dir` 分支同口径（只取源路径最后一段作文件名）。

### 2. 缺省是 `/out`，不是源文件路径

不用「缺省＝源文件」：那正是 A3-7 记下的缺陷——计划里 `target == source`，执行时目标已存在，`skip` 自我跳过（用户看到「成功但零产物」）、`overwrite` 原地覆盖源（用户丢掉原件）。也不要求前端必填：浏览器的输出语义是「产物在沙箱里、之后下载」，`/out` 是它的天然默认值；同一份表单重复出计划仍逐字节一致（计划幂等不受影响）。

### 3. 执行能力按动作族记账，扩到 16 个视图

| 族 | 视图 | 执行动作 |
|---|---|---|
| 读写 | F01–F03 | `split` |
| 读写 | F04、F06 | `merge`（F06 带 `csvMerge` 载荷） |
| 读写 | F05 | `split` + `csv` 载荷 |
| 改写器 | C01–C03 | `edit-content`（三个 rewriter 都在 kernel，ADR-0109） |
| 读写 | **F07–F09、C11–C14（本文新增）** | `csv-extract`／`csv-rows`／`csv-dedup`／`csv-filter`／`csv-sort`／`csv-columns` |

剩余 3 个视图的缺口不变：C07 要相对路径进 staging（`relative-paths`），F10／C08／C10 要 `DirectoryLister`／`ArchiveService`（`port-missing`）。`WebApplyGap` 因此删掉 `target-in-place` 一档——档位表只留**当前真实存在**的原因，不用历史原因占位。

## 被否的方案

- **在执行器里强制 `overwrite`**：会让 target==source 的计划「看起来成功」，实际用同一份内容覆盖源文件。A3-7 已明确否决：缺的是计划里的输出路径，就在计划侧补。
- **前端拼好每个文件的完整目标路径再传**：需要前端知道文件名归一规则（`displayPath`、尾斜杠、反斜杠），等于把内核路径语义抄一份到 TS；且与 `plan_f01` 既有的 `outputDir`（由 kernel 派生）两种风格并存。
- **要求用户为每个文件单独填输出路径**：桌面 CLI 也只给 `--output <file>` 或 `--output-dir <dir>` 二选一；逐文件填是负担，且没有对应的表单形状。

## 后果

- **好的**：F07–F09／C11–C14 在浏览器里能真执行、真出产物、真撤销（撤销回滚沙箱内的 `/out/*`，源文件从未被碰过）；`skip` 不再因「目标＝源」而整条跳过。
- **代价**：计划的 `target` 从此依赖 `outputDir`，同一个文件在不同输出目录下会得到不同的计划——这是**预期**（计划本来就该描述「写到哪」），C18 的幂等口径是「同一输入＋同一参数 → 同一计划」。
- **仍未解决**：沙箱里没有「目标已存在」的事实（`targetOccupied` 恒 `false`），因此计划不会给出「目标已存在」的冲突提示；在沙箱里这不是问题（每次执行前 `reset_sandbox`，产物路径由本次执行创建），但**不能**据此认为桌面端也不需要该事实。

## 推翻条件

若将来 Web 端支持「输出目录＝用户授权的真实目录」（OPFS 或 File System Access API 落盘），目标路径的派生要改由**目录句柄**给出，并恢复 `targetOccupied` 的真实探测；届时另开 ADR 推翻本文第 1、2 条，`web_output_path` 的字符串归一不再是唯一来源。
