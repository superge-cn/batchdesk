# 0105. Web 计划能力矩阵：按事实齐备度分档，不全就拒绝

- 日期：2026-11-21
- 状态：**已采纳**（A3-2 横向铺开落地：`web/src/lib/web/planChannel.ts` 的 `webPlanSupport` ＋ 16 个视图接线 ＋ 9 个视图显式拒绝；A3-3 追加：C08／C10 转为 `native`（**18／7**），C10 压缩侧单列 `archive-compress`）
- 相关：[ADR-0104](./0104-Web计划通道真计划不配假执行.md)（计划通道与「真计划不配假执行」）、[ADR-0102](./0102-字节级探测算法下沉kernel.md)（字节级事实）、设计 02 §2（事实采集层）、设计 05 §2（导出面）、AGENTS 不变量 11（Web 零强制力）

## 背景

A3-1 把 C02 一条纵切打通后，横向铺开要做的事看起来是「把剩下 24 个视图逐个接上
同一个机制」。但接的过程中暴露出一个必须先回答的问题：

**25 个 `plan_*` 都能调用 ≠ 25 个都能在浏览器里算出正确的计划。**

kernel 的计划入口收的是**事实 DTO**，桌面壳用真实 FS 采集这些事实。浏览器只有
File API：拿得到「用户手动选中的文件」的字节、大小、mtime，拿不到

- 目录里还有什么（条目枚举、目录计数、maxDepth）；
- 目标路径上是否已有文件（`existing_targets`／`target_occupied`）；
- 与桌面同算法的 blake3 全量哈希（前端没有同实现，算出来也不能对拍）。

缺这些事实时，内核不会报错——它会**照常算出一份计划**，只是结论是错的。
典型例子是 C09：`full_hash` 全为 `null`、`DuplicateReport` 为空，内核会得出
「没有重复文件」，用户看到的是一份格式完全正常、结论完全错误的计划。

## 决策

### 1. 二分档位，不做「尽力而为」

`webPlanSupport(view)` 只返回两种档位：

| 档位 | 含义 | 行为 |
|---|---|---|
| `native` | 事实齐备，能出与桌面**同口径**的计划 | 走 WASM `plan_*` |
| `unsupported` | 缺的事实会**改变判定结论** | 调用前抛 `E5001`，一次也不调 WASM |

不设「degraded（有缺口但能算）」档：一旦允许，就要为每个缺口解释「这个偏差
能接受」，而计划文档长得一样、用户无从分辨——这正是本项目一直在防的静默偏差。
缺就拒绝，代价是功能少，收益是**界面上的每份计划都是真的**。

### 2. 缺口用枚举表达，不用自然语言

`WebPlanGap` 四类（A3-3 后）：

- `directory-walk`：需要目录树（C04／F10／F11／F12／F13）；
- `content-hash`：需要 blake3 全量哈希与三阶段分组（C09）；
- `pending-wiring`：事实可采、采集链未接（C07 清单解析 ＋ 第二份独立选择）；
- `archive-compress`：C10 的**压缩**侧（`plan_c10_compress` 未导出，且浏览器没有本地目录打包的事实源）。

枚举让 lib 层不依赖语言包（`FeaturePages` 用 `Record<WebPlanGap, MessageKey>` 翻译），
也让测试能精确断言「拒绝原因是哪一类」，而不是匹配一句文案。

### 3. 拒绝发生在调用之前

`planWithFiles` 先查档位再取实现；`unsupported` 直接抛 `E5001`，**不 prepare 事实、
不调 WASM**。测试用 `expect(caller).not.toHaveBeenCalled()` 钉住这一条：拒绝不是
「算完发现不对再报错」，而是根本不开始。

### 4. 假计划必须自报家门

浏览器里没选文件时仍走既有 mock（这是 A3-1 保留的降级行为，也是既有测试的前提）。
但 mock 出来的计划会在预览区上方显示 `web-plan-demo`：**「以下为演示数据，不是真实计划」**，
并按档位补一句「选择文件后改用本机内核计算」或「浏览器版无法计算此功能：<具体缺口>」。

## 替代方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 25 个全接，缺的事实填默认值（如 `existing_targets=[]`） | 计划看起来正常、结论是错的；用户没有任何线索能发现「冲突没算」 |
| 只接 C02，其余仍走 mock 且不标注 | 界面上的假计划与真计划无法区分，等于宣称 25 个功能都可用 |
| 浏览器里对 unsupported 视图直接禁用整个功能页 | 会连带禁掉模板、参数编辑、上下文等只读能力；且既有测试大量依赖 mock 计划 |
| 前端实现 blake3 以支持 C09 | 与 Rust 实现的一致性无法保证，哈希口径不同会让重复分组与桌面不一致 |

## 后果

- **正向**：**18 个视图**在浏览器里出真计划（C01–C03、C08、C10、F01–F09、C11–C14）；
  **7 个**显式拒绝并给出原因（C04／C07／C09／F10–F13）；新增 `plan_*` 导出时，
  `contract.test.ts` 的「25 个入口逐个表态」用例会强制在矩阵里做选择（漏了会红）。
- **A3-3 的两处修正（重要）**：分档判据不是「能不能调」，而是「事实是否齐备」——
  - **C08 可以 `native`，前提是改输入形态**：相对路径只能从**目录选择**
    （`webkitdirectory` 的 `webkitRelativePath`）拿到。普通多选时相对路径为空，
    此时拒绝（`E1001`）而不拿扁平文件名顶上——那会把「子目录里的 a.txt」当成
    「根目录下的 a.txt」，扩展名规则照样命中、产物路径却是错的。相对路径还要剥掉
    浏览器自带的第一段（被选目录名），才与桌面 `collect_tree_files(source_root)`
    的 `rel_path` 同口径。
  - **C10 的条目事实一直是齐备的**：中央目录就是完整清单（ADR-0103 已落地读取器），
    A3-2 把它归到 `pending-wiring` 只是「没接线」。接线后仅两处已知偏差：
    `existingTargets` 不传（无 OPFS 列举 → 不预判「目标已存在」，少一类冲突提示、
    不改变结论）、压缩侧按 `archive-compress` 拒绝。
- **负向**：C09 重复文件查找、F10 目录清单、F12 批量改名、C04 目录内名称替换
  在 Web 形态不可用——这是能力边界，不是缺陷，已记入 TRACEABILITY。
- **未闭合**：C07 仍 `pending-wiring`（要清单文件＋源目录**两份独立输入**，且清单解析
  须与内核的编码感知 CSV 管线同口径，不能在前端另写一套）；
  OPFS 执行器仍缺（设计 02 §3.1），真计划只能看不能执行。
