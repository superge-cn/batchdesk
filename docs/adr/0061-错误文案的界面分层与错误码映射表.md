# 0061. 错误文案的界面分层与错误码映射表

- **状态**：已采纳（2026-11-03，设计 06 §3 与设计 09 §5 的实现落地，`error.<code>.*` 文案族首批）
- **日期**：2026-11-03
- **决策者**：开发代理（工程实现决策；码位含义、可重试性、码位集合均取自设计 06 §2，本 ADR 不改码位）
- **关联**：设计 06 §2／§3（码位表与 key 约定）、设计 09 §5（错误文案三层）／§8（实现落地）、设计 01 §7；`web/src/errors.ts`、`web/src/ErrorBanner.tsx`、`scripts/check_locales.py`、`docs/adr/0059`（文案资源层）

---

## 1. 问题

设计 06 §3 定了 key 约定（`error.<code>.summary/detail/action`）与一条硬约束：**文案不得暴露路径、文件名、许可证载荷或堆栈；`detail` 仅进诊断日志**。但界面一直是这样显示错误的：

```tsx
<strong>{error.code}</strong> · {error.message}
{error.detail && <div className="muted">{error.detail}</div>}
```

`error.message` 直接来自壳层 `IpcError`——它是 Rust 侧写给开发者看的英文串，常常带**绝对路径**与内部标识（例如 `this shell slice does not support plan kind: f13`、`invalid params: unknown key logging.retentionDays`）。这同时违反两条：文案没本地化（设计 09 §2 禁止）、技术细节进了界面（06 §3 禁止）。三处界面（C09 工作台、23 个功能视图、设置区）各抄了一份同样的 JSX，改一处漏两处。

落地时还要回答四个具体问题：

1. 后端 `message`／`detail` 到底给不给用户看？——06 §3 说 `detail` 只进日志，但 `message` 没说。
2. 码位没收录文案时怎么办（新码位、E6xxx 未实现的功能）？
3. 前端自己产生的校验提示（"请填写要扫描的目录"）算不算"错误"？它们被塞成了 `{code: "E1001", message: t(...)}`，占用错误码空间却带着具体指引。
4. 53 个码位要一次写全吗？

## 2. 候选与结论

| 议题 | 候选 | 结论 |
|---|---|---|
| 后端 message／detail | a) 原样显示（现状）；b) 都不显示，只显示码位＋本地化摘要；c) 收进可展开区 | **b**。06 §3 的原话是"detail 仅进诊断日志"，`message` 与 `detail` 在本仓库里是同源的技术串（壳层把 `KernelError.message` 与 hint 一起塞进这两个字段），拆开只显示一个没有意义。界面上保留**码位**作为支持句柄——这比一句英文更有用 |
| 未收录码位 | a) 显示空白；b) 显示 raw key；c) 退回 `message` 原文 | **c**。宁可让用户看到一句英文，也不要空白或 `error.E6011.summary`；同时 `describeError` 返回 `localized: false`，让调用方／测试能区分"本地化成功"与"兜底" |
| 前端校验提示 | a) 继续用错误横幅＋码位；b) 改成提示条（`banner-info` / `role="status"`） | **b**。"还差一步"不是系统错误，不该占用码位；改走提示条后既保留具体文案（"请填写要扫描的目录"），也不让码位表被表单校验污染 |
| 覆盖范围 | a) 一次写全 53 个码位；b) 先收口"界面真会遇到的" 21 个，其余走兜底并登记 | **b**。53 个里有 E4xxx（云端，未建）、E6xxx（AI，未实现）、E5xxx 其余（诊断日志、更新），现在写等于替未实现的功能编文案。收口标准是"壳层会返回的 11 个＋计划/执行条目里会出现的 10 个内核码" |
| 组件复用 | a) 三处各自改；b) 抽 `ErrorBanner` | **b**。三处 JSX 逐字相同，抽出来后"以后改错误呈现"只改一处（这正是上次 `labels.tsx` 收口的同款问题） |
| 门禁 | a) 只靠人写；b) 扩展 `check_locales.py` | **b**。新增第 8 项：映射表里的每个码位在两语言包都必须有 summary＋action；语言包里不得出现映射表之外的 `error.*` 码位（防止有人加了文案却没接映射，或删了映射留下死文案） |
| `detail` 的 key | a) 也补 53×2 条 detail 文案；b) 不建 detail 的 key，技术行取后端原文（仅日志） | **b**。06 §3 自己写了"detail 仅进诊断日志"，界面资源不需要它；给每个码位再编一句"技术细节"文案是纯浪费，且容易把路径写进去 |

## 3. 实现

- `web/src/errors.ts`：`ERROR_TEXT_KEYS`（21 个码位 → summary/action 两个 key，`as const satisfies` 让 **tsc 校验每个 key 真的存在于语言包**）、`ERROR_CODES`、`isKnownErrorCode`、`describeError(t, error) → { title, action?, localized }`。
- `web/src/ErrorBanner.tsx`：统一横幅（`role="alert"`，码位＋摘要＋建议动作＋关闭）。C09 工作台、功能视图、设置区三处替换为该组件。
- 语言包：每个码位两条（`error.<code>.summary` / `.action`），中英各 42 条；两包 395 → **437** key。
- C09 工作台的两处表单校验（缺扫描目录、快速哈希窗口非法）由 `setError(...)` 改为 `setNotice(...)`。
- `scripts/check_locales.py` 第 8 项（见上表）；`KEY_DOMAIN_RE` 增加 `error` 域，让第 6 项（源码引用的 key 必须存在）也覆盖错误码 key。

## 4. 已接受的坑与边界

- **剩余 32 个码位未接入**：E1006、E2003／E2007／E2008、E3xxx 其余、E4xxx、E5xxx 其余、E6xxx、E9xxx 之外的长尾仍走"退回后端原文"分支。设计与台账都写明这是**已落地的首批**，不是"错误文案已全部国际化"。
- **`E6011` 之类的未收录码位会把英文原文显示给用户**：这是刻意的兜底，不是遗漏；上线前若启用 AI 功能，必须先补该族文案（否则用户看到英文技术串）。
- **不显示 `detail` 可能降低可支持性**：用户报障时只剩码位。缓解是壳层已把细节写进操作日志／诊断日志；`detail` 进界面的方式留给"可展开详情"，属设计 09 §5 的"（日志/可展开）"里未做的那半。
- **文案语气与术语由开发代理起草**：内容取自 06 §2 的"含义"列，但"建议动作"是我按操作语义写的（例如 E3002 建议改"替换并计数"策略）。这类面向用户的措辞应经产品／文案复核——已在 CHANGELOG 与开发计划里标注，不写成"已定稿"。
- **码位 → 文案的映射表是手写的**：加一个码位要改三处（errors.ts、两个语言包）；门禁会挡住"只改两处"的情形，但挡不住"码位含义写错"。
- **未做**：`detail` 的可展开 UI；错误码到"操作建议"的跳转（例如 E2009 直接跳到保护名单设置）。

## 5. 验证

- `check_locales.py`：2 × **437** key、源码引用 **426** key、**21 个码位两段齐全**；先红实证＝在 zh 包塞一个 `error.E6011.summary`（孤立码位），门禁同时报"en-US 缺 key"与"码位没进映射表"，删除后恢复绿。
- `errors.test.tsx` 6 项：已知码位本地化且不含后端原文、英文下切英文、未收录码位兜底且 `localized=false`、21 个码位两语言包齐全且无占位符、横幅渲染码位/摘要/动作/关闭、未收录码位不渲染 raw key。
- `tsc --noEmit` 0 错（`ERROR_TEXT_KEYS` 的 `satisfies MessageKey` 在编译期校验 key 拼写）。
- 全量 `vitest run`：**10 → 11 文件、44 → 50 项**全绿。

## 7. 补记（2026-11-04）：其余 32 个码位已收口，本 ADR 的分批边界不再是缺口

§4 当年把范围切成「先接界面真会遇到的 21 个码位，其余回退原文」。补齐剩下的 32 个时没有
推翻任何判断，只是把边界收掉，两点值得记下来：

1. **回退原文不是契约，是没做完。** 06 §2 码表对每个码位都给了语义（`E2007 冲突且策略为 skip`、
   `E6004 工具调用不在 allowlist`……），所以"给未实现的功能编文案"这个顾虑在这里不成立——
   写的是**码位含义**，不是功能承诺。因此本批按 06 §2 逐码起草，不新增语义、不带路径/堆栈（06 §3）。
   E6xxx 对应 F15 尚未实现这一点，在台账与 `TRACEABILITY` 里都写明了：**接入文案 ≠ 功能可用**
   （不变量 11/12：Web 端零强制力，AI 的强制力只在产物执行路径）。
2. **把"人记得去补"换成机器记得。** `check_locales.py` 第 ⑧ 项从"映射表内码位两段齐全"升级为
   **与设计 06 §2 码表逐码对齐**（码表有、映射没有 → 红；映射有、码表没有 → 红）。同时给门禁
   加了自校：解析 06 码表得到空集合就直接报"门禁自校失败"——否则将来表头格式一改，这条检查会
   变成永不失配的假绿。反向证据：临时删掉 `E6004` 的映射后门禁红，恢复后绿。

另一处会自己骗自己的地方也顺手消掉了：`errors.test.tsx` 用 **E6011** 当"未收录码位"的样例，
本批 E6011 成了已知码，样例若不改，测的就是"已知码走未收录分支"这种不存在的路径。已换成
06 里根本不存在的段号 `E8999`。**"用某个码代表未知"的测试，在码位被正式收录那天会静默失效**——
以后加码位时要连带检查这类样例。

## 8. 补记（2026-11-04）：两处"横幅之外"的泄漏，与把它交给机器的第 ⑨ 项

本篇 §3 只换成了**三处横幅**（C09 工作台／23 功能视图／设置区）。同日建的另外两处一直没换，
本批实测把它们抓了出来：

- `web/src/TaskHistory.tsx`（「任务与撤销」视图，与设计 12 v0.17 同批建）自己抄了一份横幅 JSX，
  直接渲染 `{error.code} · {error.message}` 与 `error.detail`；
- `web/src/App.tsx` 的执行结果表把条目级 `entry.error.message` 同时写进单元格文本与 `title`
  悬停提示——**表格不是横幅，所以"逐处替换横幅"的收口方式天然看不见它**。

先红是实录的：新用例断"码位＋本地化摘要、且不含后端原文"，改前失败信息就是界面文本
`E2002 · permission denied while reading /home/operator/private/notes.txt`（绝对路径进界面，
正是 06 §3 禁的那一类）。改后两处都只经 `describeError`／`ErrorBanner` 出口。

**教训不是"再补两处"，而是"逐处替换"这个做法本身不可靠**：错误呈现的形状不止横幅（还有表格、
tooltip、内联提示），只要出口靠人记，下一处新 UI 就会再漏。因此 `check_locales.py` 加第 ⑨ 项：
`web/src` 下非测试源码不得读取 `error.message`／`error.detail`（含 `error?.message` 形态），
允许清单只有两处出口——`errors.ts`（码表外码位的兜底）与 `lib/ipc/index.ts`（IPC 归一化层，
它读的是 JS `Error`）。并配自校：`ErrorBanner.tsx` 缺失时报"界面错误文案没有唯一出口"，
避免这条检查在出口文件被改名后静默变成永不失配的假绿。反向证据：临时放入
`web/src/__gate_probe.tsx`（一行 `return <div>{error.message}</div>`）→ 门禁红并点名
`__gate_probe.tsx:3`，删除后恢复绿（exit 0）。

**门禁的边界（不夸大）**：第 ⑨ 项是文本形态的静态检查，认的是 `error.message`／`error.detail`
这一写法；写成解构（`const { message } = error`）或换属性名就绕过。不做 AST 解析是因为
门禁只用标准库、且本仓其余文案门禁同为正则形态——宁可挡得住"最常见的那一种抄法"，
也不为此引入解析依赖。

§4 末条"未做：`detail` 的可展开 UI"本批**改判为待人工裁决**，不在本篇里自行定案：06 §3 的 key
定义行写"可展开详情"、同节正文与 v1.4 落地边界写"进日志不出界面"，09 §5 又写"（日志/可展开）"
——三处口径不一致，而"要不要让用户在界面里看到技术细节"是产品行为（AGENTS「何时停下来问人」）。
已登记为 [OQ-38](../OPEN-QUESTIONS.md)；在此之前界面维持现状（只显示码位＋摘要＋建议动作）。
