# 0016 F04 合并计划与编码统一语义

- 状态：已采纳
- 日期：2026-10-30
- 关联：[设计 01 §3.1/§5/§5.1](../design/01-内核接口与IPC契约.md)、[方案 v1.19 §5.15](../baseline/产品方案-v1.19.md)、[TC v0.3 F04](../testing/测试用例库-TC-v0.3.md)

## 1. 背景

F04「TXT 合并」要求按给定顺序把多个文本输入追加成一个输出；方案 §5.15 明确
「顺序追加写入，编码不一致时先统一解码再按目标编码写出」。设计 01 §5 原先把
F04 描述为 N:1 分组（N 条 entry 共享 `groupId`、`target` 相同），但该形态有两个
工程问题：

1. 多条 entry 逐条写同一目标时，apply 失败/取消只能留下部分产物，原子性无法保证；
2. 撤销需要 N 条 Journal reverse，且每条 forward 都是对同一路径的写入，语义重叠。

另外，合并产物的编码与 BOM 只能有一份，不能按输入逐段各写一次。

## 2. 决策

1. **动作与条目**：追加 `PlanAction::Merge`（`"merge"`），一次合并只生成一条
   entry；`PlanEntry` 追加可选字段 `merge{sources[], targetEncoding, invalid}`，
   `sources` 按合并顺序记录 `{path, encoding?, size}`。F04 不设 `relation`，N:1
   的输入清单由载荷表达（设计 01 §5/§5.1、ADR 编号见 §5 修订记录）。
2. **单条 entry 的理由**：apply 在内存中按序解码、转码、拼接后调用一次
   `write_atomic`，产物原子落盘；Journal 只需一条 forward=`WriteAtomic`（`dataRef`
   省略）与 reverse=`Quarantine`（新建产物进隔离目录）。目标已存在且用户选择覆盖
   时，先 `backup_to_quarantine`，reverse=`WriteAtomic{dataRef}`（与 copy 覆盖一致）。
3. **编码统一**：壳层逐文件采样并调用 kernel `detect`；plan 记录检测/确认结果。
   任一输入的编码无法确定时，整条 entry 记 `blocked` + E3001（hint 提示确认编码），
   apply 记 skipped，不猜测编码（ADR-0014 的人工确认原则）。
4. **BOM 只写一次**：每个输入用 `TargetEncoding::without_bom()` 转码，产物最前面
   按 `TargetEncoding::bom_prefix()` 写一次目标 BOM；输入自身的 BOM 由 `transcode`
   按源编码剥离。
5. **同名校验与默认安全值**：输出已占用时生成 `existing-target` 冲突并给出
   `resolution=skip`（默认不覆盖，不变量 7）；用户显式确认覆盖才走备份＋改写。
6. **变更复核**：`expected.size` 记首个输入大小；apply 对 `merge.sources` 中每个
   输入逐项复核大小、普通文件、占位文件与保护目录，任一不满足记 skipped
   （E2010/E2006/E2009），不产生半成品。
7. **本切片边界**：apply 逐文件整段读取后拼接（内存 O(产物大小)），大文件流式
   写入待后续切片；源编码检测窗口/块数必须由调用方显式给出（方案 §5.2 无数值）。

## 3. 后果

- 设计 01 §5 的 F04 分组语义由「N 条 entry + relation」修订为「单条 entry + merge
  载荷」；该修订属工程契约变更，已在 v1.10 修订记录登记。
- `.merge` 载荷是追加式可选字段：旧 plan 不含该字段时反序列化为 `None`，不影响
  既有 rename/move/copy/delete/edit-content/split 计划。
- 合并的进度粒度是一条 entry（无法按输入单独报告完成）；输入数很多时进度条会
  长时间停在同一条目，后续可按 `sources` 追加子阶段进度。
- 大文件场景当前会占用较多内存；接入流式写入前不得宣称支持超大文件合并。
