# 0093. 致命错误自动暂停：磁盘满与网络断共用同一暂停端口

- **状态**：已采纳
- **日期**：2026-11-13
- **决策者**：开发代理（工程实现决策；产品行为、错误码与阈值不变）
- **关联**：方案 v1.22 §5.15（C15 异常与恢复）、§4.9（断线重试＋自动暂停）、§5.12（介质自适应）；设计 06（错误码 `retryable` 列）；设计 04 §4.1（`NetworkRetry` 端口）；ADR-0029（C10 首切片）、`crates/kernel/src/retry.rs`、`crates/kernel/src/generic_apply.rs`、`src-tauri/src/tasks.rs`

---

## 1. 问题背景

TC-C15-EXE-05「并发可控与介质自适应」的缺口里有一条「致命错误自动暂停未做」。查证后现状是**做了一半**：

- 方案 §5.15 要求「致命错误（磁盘满、网络断）→自动暂停并给出可操作提示」；§4.9 进一步给了网络断线的重试参数（最多 3 次、退避 2/4/8 秒，之后暂停）。
- 代码里**只有网络断线（E2005）**走了这条路径：`perform_with_retry` 检测到 E2005 → 退避重试 3 次 → 调 `NetworkRetry::pause` → 壳层 `auto_pause` 把任务切到 `Paused` 并阻塞到用户继续（`TaskNetworkRetry::pause`）。
- **磁盘满（E2004）没有任何暂停路径**：它只在预检（`preflight.rs` 的 disk-space 检查）里作为整任务阻断出现；执行期写盘撞上 ENOSPC（os error 28/112）时由 `platform/src/fs.rs` 映射成 `E2004, retryable=true`，然后**当作普通条目失败**上抛——任务判 `Failed`，用户拿到一个死任务，而"清理磁盘后继续"这个最自然的处置动作没有入口。

这里有个口径问题：设计 06 把 E2004 标为 `retryable=true`，但实现里既没有重试也没有暂停，**`retryable` 目前是句空话**。

## 2. 候选与否决理由

| 议题 | 候选 | 结论 |
|---|---|---|
| 磁盘满要不要"先退避重试几次" | a) 与网络断线同参数（3 次 2/4/8 秒）；b) **第一次就暂停** | **b**：磁盘满不会在秒级自愈，退避 3 次只是把用户推向"任务失败"；网络断线有秒级恢复的可能，两者机理不同 |
| 暂停端口 | a) 新造一个 `DiskRetry` 端口；b) **复用 `NetworkRetry`** | **b**：两者的宿主动作完全同构（切 `Paused`＋阻塞到用户继续＋返回 Resumed/Cancel/Abort），再开一个端口等于把同一段壳层逻辑抄两遍。端口的**名字**保留（改名要动 6 个文件 53 处，收益不抵风险），但在 `retry.rs` 的文档里写明它现在承载"致命错误暂停" |
| 暂停粒度 | a) 整任务失败转暂停；b) **条目级暂停＋恢复后重试该条目** | **b**：与 E2005 同口径，已完成的条目不重做，Journal 语义不变 |
| 用户取消 | a) 直接失败；b) **按普通条目失败收尾** | **b**：`PauseAction::Cancel` 时把该条目计为失败并继续走既有收尾流程（方案 §5.13「单条目失败不阻塞整体」） |
| CLI 无暂停面 | a) 等待后重试；b) **沿用 `PauseAction::Abort`** | **b**：与 E2005 的 CLI 行为一致——中止整个任务，由用户改用 --resume/重跑 |

## 3. 决策

1. **E2004 在 `perform_with_retry` 里走暂停**：检测到 E2004（含 `Ok(Err(..))` 与 `Err(..)` 两种形态）→ 调 `retry.pause(error)`：
   - `Resumed`：重试**本条目**（不做无谓退避，用户已经处理过空间了）；
   - `Cancel`：该条目按普通失败收尾，不阻塞整体；
   - `Abort`：上抛错误，中止整个任务（CLI 路径）。
2. **壳层按错误码给文案**：`TaskNetworkRetry::pause` 原本硬编码"网络路径在 3 次退避重试后仍不可达"，改为按 `error.code` 分支——E2005 保持原文案（含"3 次退避重试"），E2004 给"磁盘空间不足（{message}）；已暂停，清理空间后点继续"。两种都带可操作动作，满足方案「给出可操作提示」。
3. **`retryable` 的语义落地**：E2004 的 `retryable=true` 从此有实现对应（暂停＝可恢复的重试），不再是空话。
4. **不动 E2003**：E2003（被占用）仍走方案 §5.13 的"执行时重试一次"，不并入暂停族——占用是秒级可自愈的（用户关掉程序就好），与磁盘满的处置动作不同。

## 4. 后果

- **内核**：`generic_apply::perform_with_retry` 增加 E2004 分支与 `disk_full_error` 辅助函数；`retry.rs` 文档更新。
- **壳层**：`TaskNetworkRetry::pause` 按码分支文案；`auto_pause` 不变。
- **错误码**：无新增；E2004/E2005 语义不变。
- **测试**：内核加 E2004 暂停-恢复-重试用例（照 `network_disconnect_is_retried_three_times_then_pauses_and_resumes` 的骨架），壳层加 E2004 文案用例。
- **不变**：E2005 的 3 次退避参数、CLI 的 Abort 行为、Journal 与撤销语义均未触碰。

## 5. 残余

1. **预检仍会先拦一次**：`preflight` 的 disk-space 检查在派发前就能发现空间不足（E2004 整任务阻断）。本 ADR 处理的是**执行期**才撞上的情况（例如多任务并发展望不足、或清理后又被填满）。两者不冲突，也不互相替代。
2. **介质自适应默认值未做**（方案 §5.12：I/O 密集 SSD/NVMe 默认 4、机械盘与网络盘默认 2；CPU 密集默认核数减一、上限 8）。`resolve_entry_concurrency` 的 `Auto` 目前只是透传计划值，没有介质探测。这需要 SSD/HDD 判别（Windows 上经 `IOCTL_STORAGE_QUERY_PROPERTY` 的 rotation rate，或 `GetDiskPerformanceInfo`），属独立切片，不在本 ADR。
