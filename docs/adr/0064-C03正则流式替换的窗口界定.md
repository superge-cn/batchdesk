# 0064. C03 正则流式替换：只给「算得出上界」的模式开窗口，算不出就整段

- **状态**：已采纳（2026-11-04，A 类流式改造第 5 批：补 ADR-0057 §4 留下的 regex 臂）
- **日期**：2026-11-04
- **决策者**：开发代理（工程实现决策；不改产品行为、错误码、阈值与线协议）
- **关联**：方案 v1.19 §4.8（大文件三档策略）、§5.14（C03「块读时保留『最大模式长度量级』的尾部重叠窗口，保证跨块的匹配不漏」）、§9.1（超大文件内存恒定）；
  [ADR-0055](./0055-C01流式转码编辑器与ContentRewriter明细返回位.md) §4（登记本议题）、[ADR-0057](./0057-C03流式替换的重叠窗口与正则边界.md) §2／§4（plain 与 cell 已流式、regex 留整段）；
  `crates/kernel/src/replace_content.rs`（`ReplaceRewriter::rewrite`／`rewrite_plain`／`regex_window_bytes`）

## 1. 问题

ADR-0057 把 plain 与 CSV cell 两条臂流式化，regex 留了整段：`regex.replace_all` 需要完整
haystack，而正则的最大匹配长度事先不知道，重叠窗口取小了就**静默漏替换/错替换**。
方案 §5.14 给的口径是「保留『最大模式长度量级』的尾部重叠窗口」——关键词是**最大模式
长度**：窗口必须 ≥ 匹配长度，否则不成立。所以问题不是"怎么调一个窗口值"，而是
「什么模式下这个上界算得出，算不出时怎么办」。

先把会静默出错的三类写死（本 ADR 的立论依据）：

| 失配面 | 例子 | 窗口化后的错误形态 |
|---|---|---|
| 无界量词没有上界 | `a.*b`、`\d+` | 任何固定窗口都可能小于实际匹配长度 → 漏替换 |
| `$`/`^` 把**每块**端点当文本端点 | `foo$`、`^\s+` | 每块末尾都算"行尾"→ **多替换**（改坏内容） |
| `\b`/`\B` 依赖被切掉的左邻字节 | `\bcat\b` | 块首字符的左邻不在缓冲里 → 边界判定与整段不一致 |

plain 臂之所以能取 `find.len()-1`，正因为字面串的长度就是匹配长度上界；正则没有这个性质。

## 2. 决策

**按「上界算不算得出」分派，算不出就保持整段。**

1. 新增纯函数 `regex_window_bytes(pattern) -> Option<usize>`：静态分析正则源码，返回
   匹配长度的**字节上界**；只要模式落在下面任一类就返回 `None`（＝不窗口化）：
   - 锚点与边界：`^` `$` `\A` `\z` `\Z` `\b` `\B`；
   - 无界重复：`*` `+` `{n,}`，以及 `?` 后接无界（`a*?`）；
   - 内联标志组 `(?i)` `(?s)` `(?m)` 之类（`(?m)` 直接改 `$`/`^` 语义，其余一并保守拒绝——
     拒绝的代价只是退回今天的整段行为，接受错的代价是改坏用户文件）；
   - 解析器看不懂的构造（未知转义、命名组扩展语法等）一律 `None`，**不猜**。
   能算时按「序列求和、交替取最大、有界重复 `{m,n}` 乘 `n`、字符类与 `.` 记 1、
   转义记 1」累加，再乘 4（UTF-8 单字符最多 4 字节）换成字节上界。
2. `ReplaceRewriter::rewrite` 的 regex 臂：`Some(bound)` 时走 `rewrite_regex_windowed`
   （64 KiB 块读入、缓冲保留 `bound` 字节尾巴、UTF-8 不完整尾部留到下一块，与
   `rewrite_plain` 同一套纪律）；`None` 时**仍走整段**，行为与本 ADR 之前逐字节相同。
3. 窗口内只判定「起点 < 安全边界（`len - bound`，EOF 时＝`len`）」的匹配，替换写出用
   `regex.replace(&text[start..end], replacement)`——切片从匹配起点开始，最左匹配就是它，
   因此**捕获组引用与转义展开复用 `replace_all` 同一实现**，不在内核里另写一套展开逻辑。

## 3. 为什么不选另外两条路

- **只靠调用方传窗口字节数**：上界由人填，填小了就是静默错替换。AGENTS 的默认安全是
  「宁可不做，也不静默改坏」，故排除。
- **窗口不够用时中途回退整段**：看着优雅，实际做不到——写出去的前缀覆水难收，而"窗口
  够不够"恰恰要读完才知道。所以判定必须在**执行前**静态完成，不做运行中换路。
- **把 `$`/`\b` 也窗口化（左邻拼接）**：正解要把左上下文塞进搜索起点，regex crate 没有
  「haystack 完整、只允许匹配落在内部区间」的 API（`regex-automata` 的 leftmost 接口有，
  但那要新增依赖——违反"新增依赖先过 cargo-deny 并在 PR 说明理由"）。本批用退回整段
  换零新依赖；若将来大文件上 `\b`/`$` 成为高频瓶颈，再单独提案引入 `regex-automata`。

## 4. 已接受的坑与边界

- **"算不出上界"仍是 O(文件)**：`.*`/`\d+`/带锚点/带边界的正则照旧整段读入。映射表与
  TRACEABILITY 的缺口列**不得**改写成"C03 已全流式"，只能写"窗口化限于可静态界定上界的子集"。
- 上界是**保守放大**（交替取最大、组内求和、UTF-8 按 4 字节），比实际需要的尾巴长，
  代价是缓冲稍大；不做缩小优化。
- 内联标志组一并拒绝，即使 `(?i)` 本身不影响长度——保守方向选"拒绝"，因为错替换比多读
  内存不可逆。
- 空匹配模式（如 `a*` 拒绝、`(?:)`）：`bound` 至少 4 字节；真出现零宽匹配（`^`/`\b` 类
  已被拒绝，`(?:)` 会给出 `Some(4)`），窗口纪律仍成立（起点判定与 `replace_all` 一致性由
  等价性测试守住，见 §5）。
- **不改契约面**：无新错误码、无新 `PlanWarning.kind`、无新 params、线协议与执行器签名不变；
  纯内部实现（同 ADR-0057 的口径）。

## 5. 验证

- 等价性（护栏，非红→绿）：`regex_windowed_matches_whole_file_across_chunk_boundaries`
  ——同一输入分别走整段与窗口化路径，逐字节比对；输入刻意让匹配横跨 64 KiB 块边界、
  让多字节字符被块切开、让末尾正好留一段不完整 UTF-8。
- 判定面（先红后绿的正反对照）：
  - `bounded_regex_patterns_get_a_window`：`\d{4}`、`[A-Za-z]{2,6}`、`abc`、`(foo|barbaz)` 等给 `Some`；
  - `unbounded_or_anchored_patterns_refuse_the_window`：`a.*b`、`\d+`、`foo$`、`^\s`、`\bcat\b`、
    `(?i)abc`、`x{2,}`、未知转义 → `None`（＝整段）。
- 回归：`cargo test --workspace --all-features`、`cargo clippy --workspace --all-targets -- -D warnings`、
  `cargo fmt --check`、`python3 scripts/check_docs.py`（全部以退出码判定）。
