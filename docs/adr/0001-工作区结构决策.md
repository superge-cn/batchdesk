# 0001. 工作区结构决策

- **状态**：已采纳
- **日期**：2026-10-26
- **决策者**：项目负责人（按 D-R4 决策）
- **关联**：方案 §13.5（与桌面版的内核复用边界）、§4.2（四层单向依赖）、§9.5（CLI 与 GUI 共用内核）

---

## 1. 问题背景

仓库刚初始化，需要一次性定下代码的组织方式。约束来自三处：

1. 核心引擎要**能编译为 WASM 供 Web 版复用**（方案 §13.5：引擎、任务队列、预览/撤销/日志框架复用；只有文件系统适配层与授权配置不复用）；
2. 桌面壳与 Web 前端**形态不同但共用同一内核**，不能让任何一方把对方"拉进"自己的依赖里；
3. P1 阶段要出 CLI（方案 §9.5：CLI 与 GUI 共用内核，避免二套逻辑）。

触发条件：现在是改结构成本最低的时点——一旦三方混在一个 crate 里，后续拆分要动全部模块路径与依赖图。

## 2. 候选与结论

| 候选 | 一句话定义 | 结论 |
|---|---|---|
| **A 多 crate workspace** | `crates/kernel`（核心引擎）+ `crates/cli`（P1 预留）+ `src-tauri`（桌面壳）+ `web/`（前端） | **选用** |
| B 单 crate 起步后拆 | 先全部塞进一个 crate，等 Web 版要做时再拆 | 否决 |

## 3. 选择理由

**B 为什么不够好**：WASM 目标的编译约束会从内核反向传导——如果内核与桌面壳同 crate，`crates/kernel` 就无法在不牵扯 Tauri 依赖的前提下独立编译为 WASM；等到 Web 版启动时才拆，动的是全仓库的模块路径与依赖图，且此时已有大量代码与 CI 配置绑在旧结构上。**"后拆"省下的是初始化时的半小时，付出的是 Web 版启动时的一次全仓重构**。

**A 的代价已评估**：多 crate 会让首次编译与增量编译稍慢，且需要维护 workspace 级的依赖版本一致性——这两项都是可接受的固定成本，且都能用 workspace 统一配置消解。

## 4. 后果与退路

- **后果**：① `kernel` 不得依赖 `src-tauri`／`web`，依赖方向单向（对应方案 §4.2 的四层单向依赖，由 CI 与本约定共同守护）；② 新增共享逻辑时，必须先判断它属内核还是属壳，**不允许为图省事塞进 `src-tauri`**；③ WASM 兼容性成为 `kernel` 的持续约束（不得引入无法编译到 WASM 的依赖）。
- **退路**：若因故放弃 Web 版，`kernel` 作为独立 crate 依然成立（CLI 与桌面壳共用它），**架构不动**；反之若要再加交付形态（如独立服务端批处理），只需新增一个消费 `kernel` 的 crate，**同样不动架构**。

## 5. 关联

- 方案 §13.5 的复用边界表：本决策是其中"引擎/队列/预览框架复用、文件系统适配层与授权不复用"在仓库结构上的落地；
