# 0004. 类型契约单一来源（specta 家族生成，Rust 为源）

- **状态**：已采纳（2026-10-27 用户评审确认）
- **日期**：2026-10-27
- **决策者**：用户评审确认 2026-10-27（起草：AI 协作）
- **关联**：方案 §4.2（命令通道）、§4.11.4（许可规则）；设计契约 [01-内核接口与IPC契约 §9 第 4 条](../design/01-内核接口与IPC契约.md)、[03-配置schema与迁移契约 §10](../design/03-配置schema与迁移契约.md)；ADR-0001（工作区结构，本次不新增 crate）

## 1. 问题背景

契约文档 01/03 已约定：线协议 DTO（IpcError、PlanDocument、ConfigDocument 等）在 Rust 侧定义、线上 camelCase；web/ 消费同一套类型。若 TS 类型与 Rust serde 结构**双侧手写**，任何字段改动都会静默漂移——这正是篇 01 §9 第 4 条要求"单一来源、防手写漂移"的原因。触发条件：三篇契约已把命令清单、DTO、事件面定到字段级，进入实现前必须定下生成机制，否则每个 DTO 都是一次手工同步。

## 2. 候选与结论

| 候选 | 一句话定义 | 结论 |
|---|---|---|
| A：tauri-specta 全链生成 | kernel/DTO 类型 derive `specta::Type`；src-tauri 用 tauri-specta 绑定命令与事件，构建期导出 TS bindings（含 invoke 封装与事件类型） | **选用** |
| B：schemars → JSON Schema → TS | Rust derive `JsonSchema`，经 JSON Schema 生成 TS 类型；命令封装手写 | 备选（退路） |
| C：双侧手写 + JSON round-trip 契约测试 | 不引依赖，靠固定样本双向反序列化测试拦漂移 | 否决 |
| D：JSON Schema 为源双向生成 | 手写 Schema，Rust（typify 类）与 TS 双向生成 | 否决 |

## 3. 选择理由

- **排除 C**：契约测试只能拦"已写出的字段"，拦不住"漏写的新字段/新命令"——漂移恰恰发生在漏写处；且命令名（篇 01 §4 清单）完全无覆盖。
- **排除 D**：把权威从实现挪到描述文件，Rust 生成链（typify 等）对枚举/标签/Option 语义的还原不可控，等于为规避一个依赖引入两套生成工具链与语义折损。
- **排除 B（留作退路）**：类型可生成但**命令签名面**仍需手写对齐，篇 01 §4 的命令清单与参数结构还是两处维护；留它作退路是因为它对 specta 生态零耦合。
- **选 A 的核心理由**：只有它同时覆盖**类型与命令调用面**——命令名、参数、事件 payload 一次导出，TS 侧拿到的是编译期校验的 invoke 封装，"新增命令只改 Rust"成为硬约束可执行。
- **合规性核查**：specta 是类型描述库，非 Tauri/桌面 API，不违反"kernel 不得依赖 Tauri"（不变量 0）；`specta::Type` derive 无 I/O，WASM 目标可编译（采纳执行时以 `cargo build --target wasm32*` 验证，见 §5）；线协议权威在 Rust 实现，与篇 01 §9.3"错误码位表冻结于 Rust 侧"方向一致。

## 4. 后果与退路

- **后果**：
  1. kernel 与 src-tauri 引入 specta 生态依赖（specta + tauri-specta）；**三者及 TS 侧导出器必须同批升级**，记入 PR 检查项（不变量 9 的"说明理由"含此项）；
  2. 生成的 TS bindings **提交入库**（`web/src/lib/ipc/bindings.gen.ts`），CI 以"重新生成后 diff 为零"作门禁——避免前后端构建顺序耦合，代价是 PR 里会出现生成物 diff；
  3. web/ 禁止手写 invoke 命令名字符串，一律经生成封装调用（评审可 grep 门禁）；
  4. kernel 的公开导出面增加 derive 宏标记，需复核 WASM 导出面不因此暴露授权/配额判定入口（不变量 11，关联 ADR-0002）。
- **退路**：specta 生态停滞或破坏性升级不可接受时，切换候选 B：批量替换 derive、手写一次命令封装；无架构级返工，仅丢"命令面自动对齐"一项收益。
