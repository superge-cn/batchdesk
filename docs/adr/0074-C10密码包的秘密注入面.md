# 0074. C10 密码包：密码是「执行期秘密」，计划只记布尔

- **状态**：已采纳
- **日期**：2026-11-05
- **决策者**：开发代理（工程实现决策）
- **关联**：[设计 01 §3.1／§5.1／§7](./../design/01-内核接口与IPC契约.md)、[设计 04 §2](./../design/04-文件系统适配层契约.md)、[设计 06 E3xxx](./../design/06-错误码与用户文案契约.md)、[设计 13 §2.1](./../design/13-CLI契约.md)、[方案 v1.19 §5.11](./../baseline/产品方案-v1.19.md)、[ADR-0029](./0029-C10解压安全边界与GBK名回退.md)（C10 解压首切片，密码包登记为缺口）、[ADR-0073](./0073-目标名合法性改为能力值.md)（同为「环境事实两期注入、计划文件不承载」）

## 1. 问题背景

TC-C10-EXE-04「密码包／密码错误」是台账里 33 条待人工之一，缺口写的是「密码包／密码错误未做（ADR-0029 登记）」。本轮真拿一个加密包去跑，发现缺口比"没做密码参数"要深：

```console
$ zip -P secret123 zipcrypto.zip a.txt b.txt
$ batchdesk c10 --extract zipcrypto.zip --output-dir out --max-total-bytes 1000000 --max-ratio 100
E3003: archive cannot be read
detail: unsupported Zip archive: Password required to decrypt file
```

三件事同时成立：

1. **检查阶段就死了**。`ZipArchiveService::inspect` 用 `by_index(index)` 逐条目打开——而 `by_index` 对加密条目直接返回 `UnsupportedArchive("Password required to decrypt file")`。所以加密包连"有哪些条目"都列不出来，计划根本生不成。
2. **因此 `plan_c10` 里那段 E3003 加密分支是死代码**。它判断 `entry.encrypted`，但真实的加密包永远走不到那里：`inspect` 先失败了。全仓 `encrypted: true` 也只有 0 处用例——这条分支从写下那天起就没被真实数据走过。
3. **AES 与 ZipCrypto 各有一条路**。`7z a -mem=AES256` 产出的包条目方法号是 99，未启 `aes-crypto` 时 `compression()` 返回 `Unsupported(99)`，会被现有的"压缩方法不支持"分支误判成格式问题——用户的密码是对的，得到的却是"格式不支持"。

再往下是这次真正要定的契约问题：**密码放哪儿**。这个项目的计划文件会被保存、导出、进处理模板、进 S03 崩溃恢复快照（`PersistedQueue` 把 `StoredJob::Apply{plan, options}` 整个序列化写盘）。密码只要进了 `PlanDocument` 或 `StoredJob`，就会沿着这四条路各落一次盘。而 C18 的计划幂等 harness 还要拿计划 JSON 做逐字节比较——密码进计划，等于把秘密写进测试基线。

## 2. 候选与否决理由

| 候选 | 做法 | 结论 |
|---|---|---|
| A. 密码进计划 | `PlanC10Input.password` → 写进 `params` | **否决**。计划会保存／导出／进模板／进任务快照，四个落盘点各一次；幂等 harness 与台账样例也会带上它；换机器打开模板就等于随包发密码 |
| B. 密码只进执行期，计划记布尔 | 计划期只收 `password_provided: bool`；执行期经 `ArchiveApplyContext.password` 传真正密码 | **选定**。计划里"要密码"这个**事实**可复核、可幂等，"密码是什么"这个**秘密**不落盘；缺席时执行期整单拒绝，而不是逐条失败 |
| C. 计划里存密码的哈希 | 存 `sha256(password)` 供执行期比对 | **否决**。哈希本身就是离线爆破素材（ZipCrypto 的口令熵普遍很低）；而且哈希不能用来解密，"比对"完还是得另传密码，等于多存一份风险 |
| D. 继续不支持 | 保持 E3003 | **否决**。TC-C10-EXE-04 关不掉；且用户拿到的报错是「格式不支持」，与"需要密码"是完全不同的处置动作 |

## 3. 决策

1. **检查与解密分开**。`inspect` 改走 `by_index_data(index)`（只读中央目录元数据，不需要密码），`extract_entry` 才要密码。这是前提：不先解决它，"这个包有没有加密条目"这个事实就拿不到，后面全是空谈。

2. **计划期只收布尔**。`PlanC10Input.password_provided: bool` 的语义是「执行期会提供密码」，不是「密码是这个」：

   | 情形 | 计划结果 |
   |---|---|
   | 含加密条目、`password_provided = false` | 整包 blocked **E3008**（替代原来的 E3003），hint 指向"提供密码后重新预览" |
   | 含加密条目、`password_provided = true` | 出计划，`params.passwordProvided = true`，加 `encrypted-archive` 警告（Caution）：密码错误会让整包失败，预览**不能**提前验证密码 |
   | 不含加密条目、`password_provided = true` | 出计划，加 `password-unused` 警告（Caution），`params.passwordProvided` **不置位** |

   第三条是有意的：计划只记"确实会用到密码"，避免把用户的误操作（选了错误的路径、包其实没加密）固化成计划事实。

3. **执行期两期同源靠"事实"而非"秘密"**。`ArchiveApplyContext.password: Option<&str>`；`ArchiveService::extract_entry(..., password, writer)`。三道门：

   - **前置门**：`params.passwordProvided` 为真而上下文没有密码 → **整单 `E3008`**，不进条目循环、不消耗授权、不写 Journal。这是"计划说能执行、执行期却没料"的唯一正确处置——拒绝开工，而不是干到一半逐条报错。
   - **逐条目兜底**：选中的条目 `encrypted` 而密码为空（旧计划文件、手改计划）→ 该条目 `E3008` 失败，不写文件。
   - **解密失败**：`ZipError::InvalidPassword`（ZipCrypto 的 12 字节头校验失败、AES 的 PBKDF2 校验值或 HMAC 尾校验失败都归这里）→ `E3009`「密码错误或压缩包已损坏」。`write_atomic_with` 失败即丢弃临时文件，不留半成品。

4. **空串等于没给**。`by_index_decrypt(b"")` 与"不给密码"是两回事（前者返回 `InvalidPassword`），所以在边界上统一 `filter(|p| !p.is_empty())`，不允许"空密码"绕过前置门。

5. **加密算法：ZipCrypto ＋ AES-128/192/256 都支持**。启用 `zip/aes-crypto`（新增 17 个 RustCrypto crate，均 MIT／Apache-2.0，deny 与 SBOM 由 CI 复验）。理由：加密方式由第三方工具决定（7-Zip／WinRAR 默认 ZipCrypto，勾了"加密强度"就是 AES-256），只支持一半会把"密码正确但解不开"误导成"密码错误"，处置动作完全错。实测两条路都通：`zip -P` 的包与 `7z -mem=AES256` 的包用正确密码都能读出原文，错误密码都返回 `InvalidPassword`。

6. **秘密的生命周期（壳层）**：密码随 `planOperation` 的 c10 参数进壳层（一次 IPC，内存），按 planId 存内存表；`applyPlan` 取用后即删；`Job` 只带一个运行期的 `secret: Option<String>` 字段，**不进 `StoredPlan`、不进 `StoredJob`、不进 `PersistedQueue` 快照**。崩溃恢复后内存里没有秘密 → 该任务以 `E3008` 失败并提示重新预览；这条不是缺陷，是"秘密不落盘"的必然代价，写在这里以免下次被当成 bug 去"修"。

7. **CLI 对称**：计划命令 `c10 --expect-password` 只声明"执行期会提供密码"（不读 stdin），执行命令 `apply --password-stdin` 才读秘密。避免"读一次再扔掉"的假动作，也让"秘密只在执行期进入进程"这条在 CLI 上同样成立。

8. **压缩侧不动**。加密**创建**是 C36（P1，方案 §5.11 之外的单列功能），本切片只做解密。`plan_c10_compress` 保持明文 ZIP 不变。

## 4. 后果

- **内核**：`PlanC10Input` 加 `password_provided`；`ArchiveApplyContext` 加 `password`；`plan_c10` 的加密分支从"死代码"变成三条真实路径；apply 加前置门与逐条目兜底。
- **平台**：`inspect` 改 `by_index_data`（加密与不加密都走同一条路，顺带少一次解压器构造）；`extract_entry` 收密码并映射 `InvalidPassword → E3009`、`PASSWORD_REQUIRED → E3008`；`zip` 特性加 `aes-crypto`。
- **错误码**：新增 `E3008`（需要密码）、`E3009`（密码错误或包损坏），`E3003` 回归"格式／方法不支持"。
- **依赖**：+17 个 crate（aes／cipher／hmac／pbkdf2／sha1／zeroize 及其传递依赖），全部 MIT／Apache-2.0；许可证与漏洞由 CI 的 deny job 复验，SBOM 随发布流程重生成。
- **不变**：限额（E3007）、路径穿越拒绝、GBK 名回退、逐文件 Journal 撤销都没动；密码不参与撤销（reverse 是 `Quarantine`，与秘密无关）。
- **测试**：见 §6 的落地统计。

## 5. 残余

1. **崩溃恢复拿不回密码**：S03 恢复出的加密包任务必然 `E3008` 失败。要改就得把秘密加密后落盘（另建 OS 安全设施通道），不在本切片。
2. **预览不能验证密码**：ZipCrypto 的头部校验只有 1/256 的判别力，AES 的认证码要读到条目末尾才算数。计划期不做"试解"（要么弱、要么贵），密码正确性只在执行期成立。UI 文案必须如实说"执行时才会知道密码对不对"。
3. **壳层的 `CaseSense` 仍是写死的 `Sensitive`**：`plan_kinds::store` 与 `plan_zip_shell` 都硬编码 `CaseSense::Sensitive`，没有走 `platform::fs::case_sensitivity()`。这是**全功能面**的既有偏差（不是本切片引入），Windows 上"目标是否已存在"的判定会与平台不符。留到 Windows 实机日前统一整改，本切片不改——改了会牵动所有 kind 的计划期望。
4. **前端只有输入框，没有"记住密码"或密钥库**：按方案 §8.5 的边界，密码不进配置、不进钥匙串，一次任务一次输入。
5. **C36（加密压缩）未做**：`plan_c10_compress` 仍产出明文 ZIP；写加密条目属于 C36 的独立决策（用哪种加密、兼容性怎么取舍）。
6. **`E3009` 分不清"密码错"与"包损坏"**：两种情况的判别信息在 ZIP 里本就不存在（CRC／认证失败长得一样），文案合成一句，处置提示给两条路。

## 6. 落地与验证

| 层 | 改动 | 断言 |
|---|---|---|
| 内核 | `PlanC10Input.password_provided`；`plan_c10` 的加密分支重写（E3008／`encrypted-archive`／`password-unused`）；`ArchiveApplyContext.password`；`apply_archive_plan` 前置门＋逐条目兜底；`select_entries` 与执行器的 `any(encrypted \|\| !supported)` 去掉 `encrypted` 那一半 | `plan_blocks_encrypted_entries_until_a_password_is_promised`、`plan_warns_but_does_not_record_a_password_for_a_plain_archive`（原 `plan_blocks_encrypted_entries` 拆成这两条：前者断 `E3008` 且 `params` 无 `passwordProvided`，后者断明文包给密码只发警告、**不**记事实） |
| 平台 | `inspect` → `by_index_data`；`extract_entry(..., password, writer)` → `by_index_decrypt`；`zip_error` 三分流（`PASSWORD_REQUIRED`→E3008、`InvalidPassword`→E3009、其余→E3003）；`zip` 开 `aes-crypto` | `crates/platform/tests/archive_password.rs` 6 项（见下） |
| CLI | `c10 --extract --expect-password`、`apply --password-stdin`（只剥 CR/LF、不 trim、空串 `E1002`），两者与 `--compress` 互斥 | `c10_encrypted_archive_is_blocked_until_the_plan_expects_a_password`、`c10_encrypted_archive_extracts_with_the_password_from_stdin`（含 `!plan_file.contains("secret123")`）、`c10_encrypted_archive_with_a_wrong_password_reports_e3009` |
| 壳层 | `AppState.plan_secrets`（内存、取用即删）；`Job.secret` 不进 `StoredJob`/`PersistedQueue`；`enqueue_undo`/`retry`/恢复派发传 `None` | `tasks::tests::the_archive_password_never_reaches_the_task_snapshot`（走完整队列解出文件，再序列化 `PersistedTask` 断言无 `secret` 字段） |
| 前端 | `FieldSpec.kind` 加 `"password"`；C10 页密码字段 `type=password`＋`autoComplete="off"`；填了才进 `planOperation` | `web/src/FeaturePages.password.test.tsx` 2 项 |
| 夹具 | `fixtures/archive/password/{zipcrypto,aes256}.zip`（第三方工具产出、破例入库，理由与 SHA-256 见该目录 README） | — |

`archive_password.rs` 的六项：`inspect_lists_encrypted_entries_without_a_password`（无密码也能列出条目与 `encrypted`）、`zipcrypto_archive_extracts_with_the_right_password`、`aes256_archive_extracts_with_the_right_password`（两者共用一条断言：产物内容逐字节对、`journal_lines == 3`）、`wrong_password_fails_the_entry_with_e3009_and_writes_nothing`（错密码 E3009、零产物，最后用 `undo_plan` 断言空目录能被清回去——比"零 Journal"更贴近真实契约，因为建父目录本来就会留一条）、`missing_password_refuses_the_whole_plan_before_touching_disk`、`empty_password_counts_as_missing`。

**先红实证**：改代码前先用探针跑原始报错（`E3003: archive cannot be read / detail: Password required to decrypt file`），确认 `encrypted: true` 在全仓零用例、`plan_c10` 的 E3003 加密分支不可达；探针文件用完即删，不入库。
