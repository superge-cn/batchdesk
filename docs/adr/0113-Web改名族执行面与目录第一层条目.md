# ADR-0113：Web 改名族的执行面与「目录第一层条目」口径

- 状态：已采纳·A3-11 落地（2026-11-22）
- 相关：ADR-0105（计划能力分档）、ADR-0108（执行沙箱）、ADR-0109（改写器端口）、ADR-0111（staging 按计划的源口径）、ADR-0112（C10 归档端口）；设计 02 §2.1／§3.1.1／§3.4
- 影响范围：web/src/lib/web/planChannel.ts、web/src/lib/web/applyChannel.ts、web/src/FeaturePages.tsx、crates/kernel/src/rename.rs（仅 serde 属性）、crates/wasm/src/lib.rs（F12 拆 core）

## 1. 背景

A3-10 收口时，Web 侧可**计划**的视图 19／25、可**执行**的视图 19／19；剩下 6 个不可计划的视图被记作两类缺口：

| 视图 | 原归因 | 事实 |
|---|---|---|
| C04 名称替换 | `directory-walk` | 条目＝目录里的名字列表 |
| F12 批量改名 | `directory-walk` | 同上 |
| F13 正则改名 | `directory-walk` | 同上（**前端没有这个视图入口**） |
| F10 目录统计 | `directory-walk` | 需要目录树（文件数/目录数/深度/占位文件） |
| F11 批量建目录 | `directory-walk` | 计划只要 root＋清单文本；缺的是「目标目录已有什么」 |
| C09 重复文件 | `content-hash` | blake3 全量哈希 + 三阶段分组 |

逐个核对后发现：**C04／F12 的缺口不是「拿不到目录」，而是「浏览器里必须让用户选整个目录」**——目录选择（`webkitdirectory`）给的 `webkitRelativePath` 正好是条目需要的名字列表。这与 A3-9 纠正 C08 的「port-missing」是同一类错误：按功能名联想，没回到执行臂与实际输入去核。

## 2. 决策

### 2.1 条目口径＝桌面的「目录第一层」（不递归）

桌面的 C04／F12 采集用 `std::fs::read_dir`（单层），跳过符号链接，目录项本身也进条目（改名会作用于子目录名）。浏览器的对应口径：

- 根层文件 → `根名/文件名`；
- 子目录 → 相对路径的第一段（`sub/b.txt` 贡献 `sub`），去重；
- 更深层的文件**不单独成条目**（否则浏览器会比桌面多改一批文件，两端结果不同）。

**空子目录拿不到**：`webkitdirectory` 只给文件，空目录没有相对路径。这是能力边界，界面在字段提示里说明（`feature.field.dirWebHint`），不假装能改。

### 2.2 子目录条目的子树必须进 staging

条目是 `素材/sub`（第一层），但执行臂对目录的 `rename` 会搬走整棵子树。所以 staging 登记的是**用户选中的全部文件**（键＝`根名/相对路径`），而不是只登记条目本身——否则目录改名后产物里只剩一个空目录。

这与 ADR-0111 的政策一致：staging 键按**计划的源口径**拼，C04／F12 与 C07／C08 共用 `RELATIVE_ROOT_VIEWS`。

### 2.3 `existingTargets` 为空是「如实」，不是「弱化」

浏览器的目录选择只给名字，没有目标文件系统可探测。而 Web 的执行目标是**会话沙箱**——每次执行前 reset，沙箱里本来就没有这些名字。所以「计划不报目标已存在冲突」与执行环境一致，不是把计划打折。

（这与 F07–F09 的输出路径派生同理：计划要对齐它真正的执行环境。）

### 2.4 wire 层修一处历史不一致：`WebPlanF12Input` 补 camelCase

25 个 Web 计划入口里只有 F12 的入参结构没有 `#[serde(rename_all = "camelCase")]`（A2 早期写的，前端一直没接）。补上后与其他入口同形；`export_surface.rs` 的用例同步改成 camelCase 形态。

### 2.5 同一个 `scope` 有两种线协议形态

- C04／F13：规则里的 `scope` 是**字符串**（内核 `RenameScope::parse`，合法值 `full`/`stem`/`ext`）；
- F12：规则被直接反序列化成 `PlanF12Rule`，其 `scope` 是 `RenameScope` **枚举**（serde 形态 `Full`/`Stem`/`Ext`）。

前端在 `renameScope(raw, style)` 里翻译一次，不让两套形态漏到调用方；非法值在调 WASM 前 `E1002` 拒绝。

### 2.6 `planId` 由前端生成：26 字符 ULID

F12 的 Web 入参要求调用方给 `planId`（其余 24 个入口在 WASM 内生成）。前端按 ULID 规则生成（时间 48 bit＋随机 80 bit，Crockford base32，首字符 ≤ `7`），与 `kernel::plan::is_ulid` 同口径；不引入依赖（`crypto.getRandomValues` + `BigInt`）。

### 2.7 顺手清掉档位表的两处不实

- **F13 删除**：Web 前端没有这个视图入口（`navCatalog` 无此项），档位表不留永远查不到的死条目（A3-9 的教训）。将来若加视图，先走 `pending-wiring` 兜底再按实际缺口归位。
- **F11 归因补全**：它的计划只要 root＋清单文本，缺的是「目标目录已有什么」（冲突判定），**且执行产物是空目录、浏览器无法交付**（下载不了目录）。两处都挡在计划侧，`directory-walk` 的归因保留但注释写清两条理由。

## 3. 替代方案与取舍

| 方案 | 结论 |
|---|---|
| 用 `showDirectoryPicker()`（File System Access）取真目录句柄 | **不用**：需要安全上下文与用户手势，Chromium-only；`webkitdirectory` 已能拿到本决策需要的全部事实（名字与相对路径），且与 C07/C08 现有交互一致。真需要空目录或目录元数据时再另开 ADR |
| 让条目递归（把深层文件也当作改名对象） | **拒绝**：与桌面 `read_dir` 单层不一致，同一目录在两端会得到不同的改名集合 |
| 只登记第一层文件，不登记子树 | **拒绝**：目录条目的 rename 会搬走整棵树，子树不在沙箱里就只剩空目录 |
| F12 的 `scope` 让内核同时接受小写 | **不采纳**：线协议形态由内核定义（`PlanF12Rule` 是内核结构），前端负责翻译；给枚举加 alias 会把容错散到内核 |

## 4. 后果

- Web 计划面 **19 → 21**／25，执行面 **19 → 21**／21（C04、F12 全链路：计划 → staging → 执行 → 产物下载 → 撤销）。
- 剩余不可计划 4 个：C09（`content-hash`）、F10／F11（`directory-walk`，理由已写清）、F13（前端无视图，走 `pending-wiring` 兜底）。
- 已知边界（如实记录，不当作完成）：
  - 浏览器里改**目录名**时，目录本身无法下载（产物清单只列文件）；子目录里的文件会以新路径出现在产物里。
  - 空子目录、符号链接、系统隐藏项看不到（`webkitdirectory` 的能力边界）。
  - Web 侧依然不知道目标目录里已有什么（沙箱为空，故计划不报该冲突）。
- 推翻条件：若产品要求「浏览器里改一个磁盘上的真实目录」（而不是生成可下载的副本），需要目录授权＋OPFS 落盘（ADR-0108 §1 的推翻条件），本决策的「产物下载」链路随之重做。
