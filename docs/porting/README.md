# 移植来源判定与台账

> 权威：方案 §4.11（三层分类、L2a 五步、成本红线、许可证规则）、AGENTS 不变量 #9/#10、[CONTRIBUTING §4](../../CONTRIBUTING.md#4-硬纪律四条) 移植不豁免。
> 本目录是**执行载体**，不是基线；不新增复用层级，不改变 §4.11 的任何规则。

## 1. 先回答两个问题

| 问题 | 答案 |
|---|---|
| 哪个功能从哪个项目移植？ | **不预先固定**。方案 §4.11.6 只给“参考方向”，不是批准来源；每个功能在开发启动时按 §4.11.2a 选源并判定许可证，通过后写入台账 |
| 移植哪些部分？ | **只抽核心判定与计算逻辑**，落入 `crates/kernel` 的变换器层；不引入来源项目的 I/O、UI、配置管理、线程模型、日志、冲突/预检实现 |

**默认规则**：未在 [`feature-source-map.md`](./feature-source-map.md) 中登记“已批准 L2a”的功能，一律自建；不得以“方案里有参考项目”为由直接复制代码。

## 2. 层级与判定

| 层级 | 动作 | 记录要求 |
|---|---|---|
| L1 库级依赖 | 直接用 crate；先过 `cargo-deny` | Cargo.toml/Cargo.lock、SBOM、许可证白名单；不写“移植”台账 |
| **L2a 移植改造** | 复制/改写核心算法代码 | **PDR + 台账行 + 文件头 + NOTICE（Apache 类）+ 测试**；GPL/AGPL 禁止 |
| L2b 设计借鉴 | 只看思路/字段/测试语料，不复制代码 | 台账记录“仅参考”；无需 SBOM/版权声明；结论回填方案或 T 语料 |
| L3 应用级 fork | 不采用 | 如有人提出，按 §4.11.1 否决，不进入台账 |
| 自建 | 默认路径 | 台账注明“自建”；无需来源记录 |

## 2.5 先 triage，不要逐模块找源

**不要为每个功能模块都找开源项目。** 先按下面五类分流，只有 L2a 才进入“搜索候选源 + PDR + 许可证判定”：

| 类别 | 处理 | 典型对象 |
|---|---|---|
| **必须自建** | 不搜索移植源 | 预览/撤销/日志三件套、Journal、授权体系、工作台 UI、配置/UiState、任务队列、C37 模板与持久化 |
| **L1 库级依赖** | 选 crate/进程外；过 `cargo-deny` 与 SBOM，不写 PDR | 哈希、编码检测、CSV、ZIP、EXIF、正则、图片、压缩等成熟库 |
| **L2a 移植改造** | 搜索 2–3 个候选源 → PDR → 许可证判定 → 台账“已批准” → 才写代码 | 代码量小、算法可隔离、许可证干净的核心算法 |
| **L2b 设计借鉴** | 只记录参考，不复制代码、不需要 SBOM | 冲突枚举完备性、token 语法、测试语料 |
| **进程外调用** | 不内嵌代码；按 4.11.4 判定 | C21 转换引擎（LibreOffice headless 类） |

**第一轮先做全功能 triage 表**（见 [`triage.md`](./triage.md)：功能编号、候选层级、理由），只把落在 L2a 的短名单送去做源搜索。L1 候选用 Cargo 生态解决；L2b 只记参考；绝大多数业务功能应自建，不应为了“复用”而引入外来架构。

## 3. PDR（Porting Decision Record）门禁

**任何 L2a 代码在合并前，必须先有批准的 PDR。** 流程：

```text
功能启动
  → 填 PDR（来源/版本/许可证/拟移植部件/排除项/适配/测试）
  → 许可证判定（4.11.4；GPL/AGPL 直接否决）
  → 技术评审（4.11.3 成本红线、接缝成本）
  → 台账登记“已批准”
  → 才允许写代码
  → PR 附 PDR 编号 + 台账行 + 文件头/NOTICE + T 语料回归结果
```

- PDR 模板见 [`PDR-template.md`](./PDR-template.md)；首个已批准示例见 [`PDR-001-C09`](./PDR-001-C09-重复文件查找.md)（2026-10-29）。
- 许可证判定不通过或不确定 → **停在 PDR 阶段**，按 AGENTS“许可证判断悬置”处理，不写代码、不猜许可。
- C21 转换引擎：按方案 11.5 仅允许**进程外调用**，不内嵌；许可证边界仍待法务（OQ-01）。

## 4. 选源检查清单（照抄到 PDR）

1. **同语言优先**：Rust 优先；非 Rust 只做进程外调用，不嵌入。
2. **版本可钉**：记录仓库 URL、tag/commit、文件路径；不只写“GitHub 某项目”。
3. **许可证干净**：读 LICENSE、文件头、NOTICE；记录 SPDX；GPL/AGPL 不作蓝本，弱 copyleft/未知 → 法务，不自行判定。
4. **代码量在红线内**：按 §4.11.3 的 <500 / 500–2000 / 更大三档；更大回退 L1 或自建。
5. **算法可隔离**：待移植部分不依赖来源项目的 UI、配置、线程、日志、I/O。
6. **可测**：能用本项目 T 用例/语料表达预期；不能只靠“来源项目测试通过”。
7. **可维护**：上游活跃度、安全记录、依赖树；不引入无法维护的子系统。
8. **有退路**：写清若上游停更/许可证变化时如何替换或自建。

## 5. 移植边界（哪些部分要／不要）

| 来源项目部分 | 处理 |
|---|---|
| 核心算法、判定规则、数据变换 | **可移植**到 kernel 变换器层（纯函数） |
| 边界条件、错误分类、测试样例 | 可对照并转成 T 用例/语料；不直接复制测试代码，除非许可证允许并登记 |
| 文件 I/O、路径处理、编码流 | **不移植**；走本项目 FsAdapter/流式管道 |
| UI、交互、工作台布局 | **不移植**；按 U/设计 12 自建 |
| 配置管理、参数模型 | **不移植**；按设计 03 的 ConfigDocument/Recipe 模型 |
| 线程/并发/任务队列 | **不移植**；走 C15/本项目队列 |
| 日志、冲突策略、预检 | **不移植**；必须接本项目 E1xxx–E9xxx、C19、S01；自带平行实现 = 评审打回 |
| 授权/许可证判断 | **不移植**；只依赖 LicenseService |

改造后必须满足 §4.11.2a③：plan/apply 两段式纯函数、统一错误码、冲突策略、预检；**不允许自带平行实现**。

## 6. 记录与验证

### 6.1 台账

每个 L2a 在 [`feature-source-map.md`](./feature-source-map.md) 有一行；L2b 只记录“仅参考”。台账列至少包含：功能编号、层级、来源/版本、许可证判定、移植部件、排除项、适配/测试、状态/负责人/日期。

### 6.2 文件头（L2a 强制）

```rust
// Ported from <repo URL> @ <tag/commit>, <original file path>.
// License: <SPDX>. Copyright (c) <year> <holder>.
// Modified for batchdesk: <one-line summary>.
```

- MIT/Apache 类保留版权声明；Apache-2.0 保留 NOTICE 并声明修改（§4.11.4）。
- 文件头只证明来源，不替代 PDR/台账/SBOM。

### 6.3 PR 证据

- PDR 编号 + 台账行链接；
- 来源 URL/commit、许可证文件/SPDX、NOTICE（如适用）；
- 移植文件清单与排除项；
- T 用例/语料回归结果（不因“来源成熟”豁免）；
- 评审人确认“没有多抄 I/O/UI/配置/线程/日志/冲突/预检”。

### 6.4 后续门禁（建议）

实现期增加 `scripts/check_porting.py`：校验 L2a 文件头、台账行、许可证黑名单与 PDR 状态；未落地前由 PR 评审人工执行。

## 8. 常见问题

**Q：方案里写了 rmlint/fdupes，是不是就移植它？**
A：不是。§4.11.6 明示“仅思路参考、未经许可证判定、非依赖承诺”。只有 PDR 批准并登记台账后，才存在“从该项目移植”的事实。

**Q：可以先写代码后补台账吗？**
A：不行。L2a 的许可证与边界必须在代码前判定；先写后补无法证明没有引入不允许的代码。

**Q：L2b 需要文件头和 SBOM 吗？**
A：不需要；但台账要记录“仅参考、不引入代码”，结论回填方案/T，避免日后误认为已批准来源。

**Q：移植后发现需要改来源的 I/O 才能用？**
A：停。I/O/UI/配置/线程/日志/冲突/预检不移植；改用本项目适配层/框架，或重新评估是否自建。
